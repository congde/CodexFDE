# 日常研发入口

日常研发统一从工作台首页的“事项与决策”开始。已有服务时沿下表完成一项需求；尚未运行时，先按[平台运行参考](personal-platform.md#1-运行一个明确的工作台)核对环境、数据目录和启动参数。课程任务从[当前讲手册](../README.md#16-讲学习路线)执行。

## 从问题走到可验收候选

| 当前要做什么 | 页面位置与动作 | 看到什么后继续 |
|---|---|---|
| 确认开发哪个项目 | 在“管理项目”核对源码位置、解释器及项目质量命令 | 所属项目明确；客户源码与工作台数据分别登记 |
| 说明真实问题 | 在“事项与决策”创建事项，记录来源、目标与不做范围 | 事项绑定正确项目，后续讨论留在同一事项 |
| 调研和澄清 | 请 Codex 检查已有实现，回答本轮问题，核对引用 | 目标、验收条件、文件范围与验收人明确 |
| 决定交付路径 | 展开“本事项的交付路径”，填写判断理由 | 常规、关键业务与课程保留分步确认；局部快捷路径仍须人明确核对和授权 |
| 启动本轮修改 | 确认需求与技术方案，再授权执行；快捷路径可合并此操作 | 工作台创建隔离候选，保留执行前检查、真实 Diff 与执行后项目 Eval |
| 作出接受决定 | 在“本轮成果”核对当前候选、报告、正常与失败行为，填写验收依据 | 指定验收人接受或退回；检查通过仍停在人审 |
| 写回或发布 | 接受候选后另行确认集成；发布按[具体运行配置](personal-platform.md#4-预览发布和回退)授权 | 原项目与候选仍有效，实际结果和失败回执可回查 |

项目准备的边界见[项目驱动交付](项目驱动交付.md)。署名记录本机操作责任，不等同于账号身份认证。

## 遇到阻断怎样继续

| 原因 | 在同一事项中怎样处理 | 保留什么 |
|---|---|---|
| 实现不符合原要求 | 选择“实现错误”，填写实际失败及修复依据，核对新轮后另行授权 | 原目标、写集、已消耗预算、旧候选与失败报告 |
| 技术方法不合适 | 选择“技术方案错误”，重新调研；业务条件未变化时可继承原需求确认 | 原确认来源，新技术方案仍需确认 |
| 业务要求变化 | 选择“需求变化”，重新澄清并确认新版本 | 首次判断、旧合同、失败与修订 |
| 环境或进程故障 | 选择“环境问题”；可复验候选重跑原检查，中断任务核对后准备新轮授权 | 当前文件与原回执；不自动重放写代码 |
| 执行授权过期 | 在方案页填写核对依据，选择“核对原合同并续期（不执行）” | 原计划及确认；需求、源码、命令、配置和预算一致才续期，随后单独授权 |

预算耗尽或原调用用量不可核验时，重新讨论并确认新的预算；候选越界、来源不可读或经验版本被撤回时，先处理具体原因。续期和返工不能绕过这些条件。服务重启与运行暂停的处理见[运行与分工](personal-platform.md#3-在同一事项内控制运行与分工)。

日常维护可能从全绿基线开始。新需求仍须增加对应验收；已有检查通过不证明新需求已经实现。L04 以后的课堂隔离实验另有起始红灯、范围内 Diff 和执行后绿灯要求，按当讲合同执行。

完成一次执行后，读取对应候选的报告和修改，复验正常与失败路径，再具名审核。返工、服务重启或后续集成都应沿用原事项的证据链，不重建一条无关联的成功记录。

可复用经验先保存为带来源和适用范围的候选，经过审核后供后续事项召回。召回、人工采用、执行效果是三个不同事实；详见[工作台范式与闭环建设](../architecture/工作台范式与闭环建设.md)。
