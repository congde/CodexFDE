# 实操手册执行与排错

如果你还没装好工具，先按 [L00 第一次操作](../courses/L00/L00｜课前准备：装好工具，跑通第一次环境自检.md#第一次使用先分清三个窗口)走一遍。工具已就绪、只是读不懂操作说明时，先看下面这几项；发生具体错误再查后面的对应部分。

<a id="first-operation"></a>

## 操作位置与结果怎么读

**先认位置。** 普通话要求发到 Codex 对话框；`python`、`git` 等命令放到终端；文档和代码在文件编辑器里查看。文件路径表示位置，当前目录表示这一个终端正在操作的文件夹。先核对当前目录，再运行命令。

**再认代码框。** 代码框上方写“终端命令”才在终端执行，写“提示词”就是发给 Codex 的消息。`powershell` 对应 Windows，`zsh` 对应 macOS；只执行自己系统的一组。`text` 只表示普通文本，要根据框前说明判断用途。需要输入实际路径、编号或数量时，先按本步要求替换示例。

**最后读结果。** 输出是程序实际打印的文字，退出码是它结束时交回的数字。退出码 `0` 不代表整个需求已经验收；非 `0` 也不一定是操作错误，可能正是本步要求观察的拒绝。把实际输出、退出码与本步预期逐项对照。服务是持续运行、等待页面或其他程序请求的程序；运行服务时不返回输入行通常是正常现象，按本步要求另开操作终端。

| 手册里的词 | 在实际操作中怎样判断 |
|---|---|
| 红灯 / 绿灯 | 本次检查未通过 / 通过；先查检查内容与原始输出 |
| 需求说明（Spec） | 这次要做什么、不做什么、什么结果算对 |
| 修改对照（Diff） | 实际改了哪些文件、哪几行；对照允许范围 |
| 隔离候选 | 本轮修改与检查的副本；不自动写回原项目 |
| 复验 | 用原要求再次运行并核对结果，检查的是当前这版 |
| 验收 | 指定的人根据结果决定接受或退回，并记录依据 |

卡住时先保留当前目录、实际动作和完整输出。请 Codex 只解释这个错误，给一个最小检查步骤，说明位置和预期；理解结果后再继续。自己的账号凭据不放进求助内容。


先确认正在操作哪个仓库。CodexFDE 保存工作台与课程；FlowERP 保存客户业务，两者各用自己的虚拟环境和运行目录。下面的命令从 CodexFDE 根目录运行。

## macOS：选择 zsh、恢复环境，再跟当前讲次

macOS 同学使用“终端”或 VS Code 终端中的 zsh。L00 提供安装与克隆步骤，L01～L16 实践手册在需要终端差异的步骤分别给出 PowerShell 和 zsh 代码块；只选自己系统的一组。标为“通用”的纯 Python、Git 命令可直接执行。`text` 也可能是发给 Codex 的提示词，应先看代码块前的“在哪里”说明。

首次安装在自己的 CodexFDE 根目录执行（已有 `.venv` 就跳过创建）：

```zsh
python3.11 -m venv .venv
./.venv/bin/python -m pip install -e .
source .venv/bin/activate
```

新开终端需要重新激活环境。L02、L03 沿用 L01 隔离区时，该目录可能没有 `.venv`；按 [L01 中断恢复](../courses/L01/实践操作手册.md#故障定位与中断恢复)回到参考仓库激活原环境，再进入 `00-isolation.json` 中的原隔离目录。不重新创建起点。之后运行本文下方的源码与解释器检查，`workbench.__file__` 应指向自己的练习区。

在后续已有独立 `.venv` 的控制仓库中，每个新终端先运行：

```zsh
setopt INTERACTIVE_COMMENTS
source .venv/bin/activate
python -X utf8 -c "import sys,workbench; from pathlib import Path; print('当前目录:', Path.cwd()); print('Python:', sys.executable); print('虚拟环境:', sys.prefix != sys.base_prefix); print('源码:', workbench.__file__)"
```

| 操作 | macOS / zsh 约定 |
|---|---|
| 示例目录 | L00 默认 `~/work/CodexFDE`；实际安装在别处时使用自己的路径 |
| 路径含空格或中文 | 始终用双引号，例如 `cd "$HOME/work/课程练习"`；交互输入路径时不加外围引号 |
| 项目解释器 | `.venv/bin/python`；不要复制 Windows 的 `Scripts/python.exe` |
| 续行 | 行末 `\`，其后没有空格；PowerShell 的反引号不适用 |
| 保存退出码 | 紧接被检查命令运行 `printf '退出码：%s\n' "$?"`；中间不插入其他命令 |
| 环境变量 | `export FLOWERP_PROJECT_ROOT="实际客户仓库绝对路径"`；每个新终端重新设置 |
| 文件哈希 | `shasum -a 256 "文件路径"`；不要用 Linux 专有的 `sha256sum` 作为 Mac 必备入口 |
| 服务窗口 | 每个窗口激活环境；服务持续运行，另开操作窗口；用 `Ctrl+C` 停止自己启动的服务 |

`python` 不存在或指向系统环境时，先激活本讲环境。zsh 显示 `quote>`、`dquote>` 或 `heredoc>` 时，通常是少复制了引号或整段结束标记；按 `Ctrl+C` 取消，重新完整复制对应代码块。代码块含注释且终端提示 `command not found: #` 时，先运行 `setopt INTERACTIVE_COMMENTS`。不要通过安装 PowerShell 来绕过手册中的 Mac 步骤。

两种终端使用相同的 Spec、任务编号、候选、测试和人工审核条件。非零退出码仍须按当讲预期判断：业务红灯、环境错误与人工待审分别记录。

L05 的会话脚本会开启 `ERR_RETURN`，用于在退出码与预期不符时停止当前代码块。若沿用该终端进入下一讲，先运行下方命令，恢复默认的退出行为，再按当讲要求记录预期失败：

```zsh
unsetopt ERR_RETURN
```

## 沿用前一讲时，先核对代码和解释器

L01 的隔离区默认借用参考仓库的 `.venv`，隔离区内没有 `.venv` 不一定是准备失败。L02、L03 沿用该成果时，先按 [L01 手册的“故障定位与中断恢复”](../courses/L01/实践操作手册.md)激活原参考环境、回到原隔离区；不要重新创建 L01 起点覆盖进度。已有独立环境则激活自己的环境。每个新终端都需重新选择解释器。

在实际练习目录运行以下只读检查：

```text
python -X utf8 -c "import sys,workbench; from pathlib import Path; print('当前目录:', Path.cwd()); print('Python:', sys.executable); print('虚拟环境:', sys.prefix != sys.base_prefix); print('源码:', workbench.__file__)"
```

`虚拟环境` 应为 `True`，`源码` 必须位于本次练习目录。解释器来自参考仓库可以成立，源码误指向参考仓库则不能继续验收个人实现。激活失败时先解决环境，不继续使用终端中残留的系统 Python。

## 先确认每条路径属于哪个项目

| 对象 | 源码归属与路径基准 |
|---|---|
| 控制工作台 | CodexFDE 的 `workbench/`、`agent/`、工作台 Eval 与测试；根目录没有客户业务包和客户页面 |
| 客户产品 | 独立 FlowERP 仓库的 `flowerp/`、`web/`、业务 Eval 与测试；使用客户自己的虚拟环境 |
| 当前课程教学候选 | L04+ 部分实验仍将两仓库源码组合到临时目录，路径相对于命令返回的候选根目录；这不是新的客户源码仓库 |

课程的 `write_scope` 是候选中的路径上限，不能据此在 CodexFDE 根目录新建 `flowerp/` 或 `web/`，也不能直接修改已登记的客户源仓库。先保存任务编号、候选绝对路径及来源记录，再确认具体允许文件。候选中的 `eval/`、`tests/` 可能包含不同项目的检查，不能只凭同名目录判断归属。

来源记录由实际准备方式决定：源码快照使用 `.course/product-source.json`，实验副本使用 `.course/experiment-source.json`，旧标签候选使用工作台返回的基线与隔离记录。来源不足时先补查；不得拿当前客户仓库的绿灯代替候选验收。候选修改不会自动写回任一源仓库。

当前组合候选机制仍待迁移为两个独立项目候选；本文说明现状，不表示该迁移已经完成。已有候选按原任务续做，不用它作为新的控制仓库源码快照。

## 先检查环境和课程入口

Windows（PowerShell）：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m workbench.cli environment-check
.\.venv\Scripts\python.exe -X utf8 -m workbench.cli course-status
.\.venv\Scripts\python.exe -X utf8 -m eval.harness --suite blocking
```

macOS（zsh）：

```zsh
./.venv/bin/python -X utf8 -m workbench.cli environment-check
./.venv/bin/python -X utf8 -m workbench.cli course-status
./.venv/bin/python -X utf8 -m eval.harness --suite blocking
```

没有 `.venv` 时，Windows 先运行 `py -3.11 -m venv .venv`，再运行 `.\.venv\Scripts\python.exe -m pip install -e .`；macOS 使用上方安装步骤。

`course-status` 默认只在本地检查。`course_ready` 表示课程合同与逐讲起始标签通过检查；另看 `session_materials.ready`，确认 L04～L14 配套材料齐全且提交号匹配。两者均不证明学生已经完成练习或验收。需要缺失时返回非零退出码，可在原命令后加 `--require-baselines --require-materials`。

### 提示配套版本缺失或不一致，怎么办

先看报错中的讲次、标签和原因，保留已有练习。终端停在 CodexFDE 根目录，运行 `git remote -v` 核对来源。需要联网核对远端时，运行自己系统对应的命令：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m workbench.cli course-status --check-remote
```

```zsh
./.venv/bin/python -X utf8 -m workbench.cli course-status --check-remote
```

此选项默认查询 `origin`；其他已登记远端可写成 `--check-remote 远端名称`。查询只读，不下载或覆盖标签；网络失败会报告查询未完成，不能当成远端缺失。

| 检查结果 | 下一步动作 | 完成判断 |
|---|---|---|
| 本地缺少标签，远端版本正确 | 确认仓库来源后运行 `git fetch origin --tags`，再重试原操作 | `session_materials.ready` 为 `true`，原操作不再因该版本报错 |
| 远端也缺少标签 | 由课程维护者发布清单指定的标签，或提供带 `course-materials.bundle` 的完整课程包；源码 Download ZIP 缺少 Git 版本记录 | 使用仓库时重新查询远端并下载标签；使用完整包时在新目录解压并运行首次使用脚本，再检查本地配套版本 |
| 标签存在但提交号不一致 | 对照报错中的期望与实际提交号，请维护者核对清单、仓库和发布版本；保留练习，在新目录获取匹配材料 | 版本检查通过后重试；不使用 `--force`、修改清单或删除验证来绕过 |

本地材料齐全并不证明远端已发布。维护者在发布前核对 `session_materials.remote.ready`；`--check-remote` 遇到远端缺失、提交不一致或查询失败均返回非零退出码。

工作台安装自检不要求客户项目。需要检查客户环境时运行 `python -X utf8 -m workbench.cli environment-check --product`，或用 `--product-root` 指定独立仓库路径。它在客户解释器中检查包来源，失败返回非零退出码；不启动服务或初始化业务数据。

默认 Eval 只验证工作台。客户业务检查在独立 FlowERP 仓库执行；本讲的显式业务用例由工作台通过独立进程委托，不要向工作台环境安装或复制 `flowerp/` 来绕过缺失项目。

### 安装名与导入名不同，怎么判断

`pip install -e .` 的日志中出现 `flowerp-fde-camp`，表示安装了 `pyproject.toml` 登记的课程项目。Python 按实际代码包名导入，本仓库使用 `workbench`、`eval` 等；安装名与导入名不必相同，无需修改项目名或目录名。

在 CodexFDE 根目录运行旧命令 `import workbench, eval, flowerp` 时，缺少 `flowerp` 不能据此判断 Python 版本有问题。L00 自检应按[当前课前准备手册](../courses/L00/L00｜课前准备：装好工具，跑通第一次环境自检.md)运行 `import workbench, eval`，看到 `imports-ok` 且紧接着检查的退出码为 `0` 才通过。需要客户业务时，按下一节配置独立 FlowERP，并用 `environment-check --product` 检查它自己的环境。

L04+ 的组合教学候选可以同时包含两个仓库的代码；只有进入实际候选、确认来源记录并核对模块路径后，才按当讲手册导入候选中的 `flowerp`。不能把这类候选检查命令直接复制到 CodexFDE 根目录执行。

### 已登记 FlowERP，命令仍提示找不到项目

当前命令的客户项目解析读取默认工作台运行目录的登记；在 `.runtime/l04-learning` 等自定义目录的页面登记，不一定会被另一个终端自动发现。先在该操作终端显式指定客户仓库，输入实际绝对路径：

```powershell
$env:FLOWERP_PROJECT_ROOT = (Read-Host '独立 FlowERP 仓库绝对路径').Trim().Trim('"')
python -X utf8 -m workbench.cli environment-check --product
```

macOS（zsh）/ Linux：

```zsh
printf '独立 FlowERP 仓库绝对路径（不加引号）：\n'
read -r FLOWERP_PROJECT_ROOT
export FLOWERP_PROJECT_ROOT
python -X utf8 -m workbench.cli environment-check --product
```

退出 0 且 `ok: true` 后才继续需要客户项目的步骤。非零时查看 `checks` 中失败项：仓库路径错误就纠正路径，客户 `.venv` 缺失则回到该仓库完成安装。新终端需重新设置；服务进程使用它启动时的环境。

**实验源码来源：** 业务观察脚本会自动转到独立客户解释器；需要修改代码的实验在新目录组合两个仓库的源码，并写入 `.course/experiment-source.json`，记录原文件路径和哈希。候选 Eval 使用该副本的业务检查。检查环境通过后即可按手册继续；已有记录按原会话续做，重跑故障实验使用新输出目录。修复前后证据保留在本次会话的实际运行记录中。

<a id="course-result"></a>

## course-submit 返回以后怎么做

适用于 L04 起的课程提交。带 `--execute-code` 的命令会实际执行，可能需要数分钟；尚未返回时保留终端，不重复提交。结束后立即保存退出码（PowerShell：`$LASTEXITCODE`；macOS/Linux：`echo $?`）和完整输出，再按下表处理：

| 看到什么 | 下一步 |
|---|---|
| 退出 0，`task.status` 为 `review` | 保存 `task.id`、`isolation.path` 和报告；在该候选上按本讲步骤独立复验，再交人审核。待审核不等于已接受 |
| 退出非零，但返回了 `task.id` | 先按原编号查 `task.error` 与事件中的失败原因，保留原候选；不要马上重新创建任务 |
| `rework` | 核对执行失败、Eval 或红绿差分的具体原因，按本讲返工步骤处理 |
| `failed` / `dead_letter` | 保留终态记录，修复前置问题后再按本讲规则创建新任务，并关联原编号 |
| 参数错误、缺标签或尚无任务编号 | 本次尚未取得业务失败证据；核对参数、课程版本、标签及客户环境后重试 |
| `isolation` 为空或没有候选路径 | 先查准备与执行事件；不要猜目录，也不要把控制仓库当候选继续检查 |

在同一控制目录查询原任务，两类终端均可用，输入运行目录的绝对路径和真实编号：

```text
python -X utf8 -c "import subprocess,sys; r=input('原工作台运行目录绝对路径：').strip(); t=input('真实 Task ID：').strip(); (r and t) or sys.exit('路径和编号不能为空'); sys.exit(subprocess.run([sys.executable,'-X','utf8','-m','workbench.cli','task-show',t,'--runtime-dir',r]).returncode)"
```

页面没有任务时先核对网页与 CLI 的运行目录。`review`、`completed` 不能直接重复 `task-run`；重开终端也不需要重新初始化。课程候选未必自带 `.venv`，可在候选目录调用已确认的控制解释器，先核对 `workbench.__file__`、`eval.__file__` 及候选中的 `flowerp.__file__` 均指向该候选，再运行检查。

`unittest discover -s tests -v` 还包含读取客户源码的课程集成测试，运行前须准备并指定独立 FlowERP。全量 CI 在 `.runtime/flowerp-project` 检出固定客户提交并创建独立虚拟环境；版本固定在 `.github/workflows/eval.yml`，升级该版本时需要重新验证课程缺陷夹具。日常工作台 Eval 与安装自检不需要客户仓库。

## 按失败位置处理

| 现象 | 核查与下一步 |
|---|---|
| 找不到 `gateway`、`agent.ops` 或旧 Hook | 这是旧版本入口；使用当前讲义及 `python -m workbench.cli --help`，不要恢复旧模块 |
| L00 自检提示找不到 `flowerp` | 使用当前 L00 的 `import workbench, eval` 命令，核对 `imports-ok` 与退出码 `0` |
| 业务步骤找不到独立 FlowERP | 在首页登记 FlowERP，或设置 `FLOWERP_PROJECT_ROOT`；用 `environment-check --product` 核对客户自己的 `.venv` |
| 隔离候选提示找不到 `flowerp` | 核对实际候选目录、源码来源与准备记录；不能借当前客户仓库的包绕过候选缺失 |
| 不认识 `--report` | `eval.harness` 使用 `--report-path`；`workbench.ci_evidence` 使用 `--report`，两者参数不同 |
| PPT 链接不存在 | `slides/` 与 `.pptx` 不随 Git 发布，见[课件获取说明](../README.md#课件怎样获取) |
| 用例不存在、报告为空 | 停止执行，核对候选、检查名称和环境；不能把环境错误当作产品起始红灯 |
| 检查通过但任务仍待审核 | 先独立复验，再由具名审核者决定；绿色检查不自动完成产品验收 |

## 保存能复现的证据

记录仓库路径、提交或候选身份、完整命令、退出码、报告与首次错误。修复后在同一候选、同一检查口径下复验，另存修复后的结果，不覆盖首次失败。课程实验中的模拟身份和示意输出不能用作学生本人证据。

工作台默认报告在 `.runtime/reports/`。需要另存时指定一个新路径，例如 `python -X utf8 -m eval.harness --suite blocking --report-path .runtime/reports/manual-recheck.json`。这条命令验证当前工作台，不替代客户业务用例或课堂迁移任务。


## 开课前批量验证实验

先完成上面的双仓库安装与客户环境检查。在 CodexFDE 根目录、已激活的虚拟环境运行：

```text
python -B -X utf8 scripts/audit_course_experiments.py --output-dir .runtime/course-labs-check-01
python -B -X utf8 -m unittest tests.test_course_experiments -v
```

第一次命令逐项运行本地实验模式，核对预期退出码、报告存在性和导入错误；末尾 `failed` 应为空，命令退出 0。每项完整命令与输出保存在指定目录，汇总为 `summary.json`。再次检查改用 `course-labs-check-02` 等新目录；只复查一讲可追加 `--lesson 9`。故障模式的预期退出 1 或 2 会记录为检查通过，因为此时验证的是系统确实拦截了错误。

第二条命令验证来源边界、文件交付、L05/L06 实验衔接、失败报告映射、事项重启后持久化和摘要导出；维护夹具不充当学生作品。任一命令非零时，根据首个失败项修复后复查，保留旧日志。

这两项用于开课前工具检查。学员仍须完成自己的实现、实际 Hook 接入、远程 CI 和具名复验；本地参考实验不会代替这些学习证据。
