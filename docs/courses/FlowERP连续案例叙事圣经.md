# FlowERP 连续案例叙事圣经

> 本文件约束 16 讲的案例人物、时间线、冲突和叙事口径，是课程大纲的教材化投影，不新增课程通过标准。

## 一、案例为什么要连续

本课程不是用 16 个互不相干的小故事包装 16 个工具。学生将在四周内加入同一个 FlowERP 项目，面对同一批业务对象、同一组同事和逐步扩大的交付责任。前一讲留下的错误，会在后一讲变成真实压力；前一讲升级的工作台能力，必须在后一讲救场。

[HBS Case Method Teaching](https://www.hbs.edu/case-method-project/about/Pages/case-method-teaching.aspx) 强调：案例应呈现决策者当时拥有的信息，并停在尚未揭示答案的决策点；学生要站在主角位置上说明自己会怎么做。[Cornell 的问题式学习说明](https://teaching.cornell.edu/teaching-resources/active-collaborative-learning/problem-based-learning)强调先呈现开放问题，再由学生界定问题、识别知识缺口、比较方案并报告结果。本课程据此采用“先决定，再分析；先承担后果，再抽象能力”的写法。

## 二、项目背景：青禾优选的四周救火期

“青禾优选”是一家为高校和小型企业提供办公设备采购的电商服务商。业务量不大，却同时运行自营商城、渠道订单、仓库、采购和财务。原有表格和零散脚本在订单增长后开始互相矛盾，公司决定在四周内把 FlowERP 从内部原型推进到可持续交付状态。

开营前一晚，大客户下单 20 台笔记本。系统显示可用库存只有 8 台，采购同事口头承诺“明天能补”，销售希望先把订单标成可交付。与此同时，工作台页面已经能打开，测试也有绿色结果。真正的问题是：这些信息是否属于同一时刻、同一业务口径和同一条证据链？

学生扮演刚加入项目的资深研发负责人。你不是旁观者，也不是替故事人物背诵正确答案；每讲都要在有限信息下签署一项决定，并为决定留下可复验证据。

## 三、固定人物与利益冲突

| 人物 | 职责与目标 | 容易提出的“合理请求” | 学生必须看到的隐藏风险 |
|---|---|---|---|
| 林默（学生角色） | 新任研发负责人，保证四周内形成可持续交付系统 | 希望先把眼前功能做出来，再补治理 | 速度会掩盖范围、证据和责任失真 |
| 周岚（运营负责人） | 确保订单按期履约，减少人工操作 | “先改状态，客户不能等” | 运营压力不能创造库存或绕过审批 |
| 陈予（仓储与采购） | 保证账实一致并及时补货 | “重复消息再入一次也没关系” | 重放、部分失败和幂等问题会放大库存 |
| 顾宁（质量与安全） | 保证失败可复现、变更可追溯 | 要求门禁、证据和独立复验 | 过度治理也可能阻断合法交付 |
| 唐禾（财务负责人） | 保证账、款、货与期间一致 | 要求具名审批和对账 | 页面成功不能替代总账与业务子账事实 |
| 客户与渠道 | 只关心可承诺日期和真实状态 | 希望立即得到“已受理/已完成”答复 | HTTP 成功、界面绿灯与业务成功可能不同步 |

人物不是用来制造戏剧化对白，而是代表真实组织中的目标冲突。每次对话必须带来一项新信息、压力或责任边界。

## 四、四幕十六讲故事弧

### 第一幕：你敢接手吗（L01～L04）

林默看到一个漂亮的终局演示，却无法证明它由当前代码和当前数据产生。运营催促直接修改库存状态，团队又没有跨会话规则。随后一句“把可用库存导出来”暴露了口径歧义。直到 L04，团队才第一次在固定 Spec 和受控写集内交付真实 Diff。

这一幕的情感推进是：**好奇 → 怀疑 → 立界 → 承诺 → 第一次承担交付责任**。

### 第二幕：绿色为什么仍不可信（L05～L08）

渠道重放一条收货消息，库存翻倍，原有测试仍然绿色。团队补上失败优先 Eval，却发现多个检查给出不同结论；本地 Hook 又可能被绕过，远程 CI 甚至出现“没有证据的绿色”。直到 L08，团队才完成从真实红灯到可信绿灯的远程证据链。

这一幕的情感推进是：**意外成功 → 事故暴露 → 证据混乱 → 质疑绿色 → 建立共同裁决**。

### 第三幕：自动化开始伤人（L09～L12）

取消订单后预占没有释放，失败日志太长而无法授权修复；自动修复器随后陷入无进展循环。为了加速，团队引入多个 Agent，又发生共享文件冲突。最后，采购入库要求具名审批，迫使团队承认有些责任不能交给自动化。

这一幕的情感推进是：**救火 → 失控 → 分工 → 冲突 → 接受人的责任不可外包**。

### 第四幕：系统能否离开作者（L13～L16）

客户和跨团队成员需要通过 API 查询任务，仓库人员需要可操作 Web 页面；反馈进入后又可能污染质量门。最终，林默必须在陌生环境、未知小需求和公开答辩中证明：FlowERP 与工作台不依赖作者记忆，也不是一个只能演示的壳。

这一幕的情感推进是：**对外承诺 → 公开状态 → 接受批评 → 现场证明系统可以长期运行**。

## 五、逐讲事故与结尾钩子

| 讲次 | 开场事故 | 本讲必须作出的决定 | 结尾留下的问题 |
|---:|---|---|---|
| L01 | 终局页面能打开，但证据时间和数据来源不明 | 是否接受项目并冻结什么基线 | 决定怎样跨会话保留 |
| L02 | 运营要求直接把采购单改为已审批 | 哪些规则长期有效，合法替代路径是什么 | “导出库存”到底指什么 |
| L03 | 仓储、销售对“可用库存”给出不同口径 | 哪些事实已确认，哪些必须拒绝猜测 | 谁能按合同改代码而不越界 |
| L04 | Agent 提议顺手重构并新增字段 | 授权读写集、预算和独立复验者 | 正常测试是否漏掉重复消息 |
| L05 | 同一收货消息重放后库存翻倍 | 先修代码还是先固定失败 | 多个 Eval 谁给最终结论 |
| L06 | 文本、JSON、退出码出现冲突 | 哪个入口是唯一裁决者 | 人会不会忘记运行它 |
| L07 | 缺货订单失败，但留下了部分状态 | Hook 阻断什么、绝不能做什么 | 远程 Runner 是否真的复验 |
| L08 | CI 绿色但无日志和报告 | A/B/C 三次 Run 哪次可合并 | 下一次失败怎样压缩为任务 |
| L09 | 取消订单后库存仍被占用 | Repair Task 可以授权哪些改动 | 修复若不收敛怎么办 |
| L10 | 三轮自动修复没有任何进展 | 何时继续、何时成功、何时安全停止 | 能否并行提速 |
| L11 | 多 Agent 同时修改采购文件并冲突 | 哪些任务可并行，谁负责最终集成 | 审批责任能否交给 Graph |
| L12 | 工程审核通过，但采购没有具名审批 | 两个状态机如何分离、怎样恢复 | 外部团队怎样查询过程 |
| L13 | API 返回 202，客户以为补货完成 | 受理、执行、审核、成功各由什么证明 | 页面会不会显示旧状态 |
| L14 | Web 页面保留昨天的绿色 | DOM/API/SQLite/ERP 谁是事实源 | 用户反馈能否直接改门禁 |
| L15 | “按钮不好用”被误写为阻断规则 | 怎样保留来源、分诊并形成独立任务 | 系统离开作者还能运行吗 |
| L16 | 陌生电脑上抽到一个此前未实现需求 | 是否能够现场签署、交付并解释风险 | 由真实教学数据进入下一轮改进 |

## 六、每讲正文写作规则

1. 标题之后先出现案例正文，不先出现课程合同、CLO、术语定义或通过标准。
2. 案例正文至少包含时间、地点、人物目标、已有证据、未知信息、时间压力和决策点。
3. 在学生提交首次判断前，不揭示参考仓库如何实现，也不把本讲技术名词写进正确选项。
4. 对话只在改变决策信息时出现；禁止用人物轮流念知识点。
5. 技术概念第一次出现时，必须回答“如果没有它，故事中的谁会承受什么损失”。
6. 图片作为案例展品，图注写“能证明什么、不能证明什么”，不能只写页面名称。
7. 讲义正文面向学生；课程合同、CLO、形成性评价和持续改进数据放入可折叠的教师区。
8. 每讲结尾不做概念汇总，而是留下一个会在下一讲爆发的未解决矛盾。

## 七、案例开篇模板

```markdown
## 连续案例｜第 N 幕：一个带动词的标题

**时间**：周三 16:40　**地点**：仓储群 / 研发会议室 / 客户现场

用 3～6 个自然段呈现事实、人物目标、证据和压力。不要解释技术答案。

> **决策时刻**：你是林默。距离承诺时间只剩 40 分钟。你准备批准什么、拒绝什么？请先提交决定和三条证据需求，再继续阅读。

### 案例展品

图片或日志。图注同时说明证明边界。

### 这一讲结束时

写新的产品状态、新的工作台能力，以及尚未解决、会引向下一讲的问题。
```
