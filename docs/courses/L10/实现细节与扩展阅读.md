# L10 实现细节与扩展阅读

先读[辅导资料](辅导资料.md)，看懂本讲案例；准备实现或排查具体问题时，再按需查本文。这里保留控制规则、源码边界与实验入口，不要求先读完才能开始。

## 继续还是停止：把判断顺序写成规则

控制器的判断顺序会改变结果。例如空报告中的失败数可能是零，所以必须先判断报告是否有效，再判断是否通过。

建议按下面顺序设计自己的控制器：

| 优先顺序 | 问题 | 决定 |
|---:|---|---|
| 1 | 报告是否完整，必需用例是否执行，是否属于当前候选？ | 不能确认则停止正常修复，转入诊断 |
| 2 | 当前候选是否满足原要求，实际修改是否在范围内？ | 满足则结束自动修复，交人复验与审核 |
| 3 | 还剩检查轮次、时间和可用的模型用量预算吗？ | 任一不足则停止并交回剩余工作 |
| 4 | 与之前相比有没有新信息或可证明的改善？ | 重复无进展或来回振荡时停止 |
| 5 | 下一次修复是否仍在授权范围内？ | 越界则交回人；否则生成下一份任务 |

达到要求后不需要把轮数用满。达到预算时也不应把 `stopped` 改成 `success`。前者说业务结果合格，后者说控制器执行了停止规则，是不同结论。

### 怎样判断“有进展”

最简单的办法是比较失败集合。设上轮失败集合为 `{合法发货, 草稿拒绝}`，本轮只剩 `{草稿拒绝}`。在要求和用例没有改变、也没有新增严重问题的前提下，可以认为有进展。

但只比较数量不可靠。上轮失败 `{合法发货, 草稿拒绝}`，本轮失败 `{库存重复扣减}`，虽然从两项变成一项，风险可能更大。此时应调查新增问题，而不是机械奖励“失败更少”。

还有两种容易漏掉的情况：

- **连续相同**：A → A。重复修复没有改变失败，应该停下来看假设是否错误，或者是否根本没有改到被检查的文件。
- **来回振荡**：A → B → A。修好这里又弄坏那里，说明修复没有同时满足两项约束。比较更早的失败集合，才能识别这种回退。

当前 [agent/loop.py](../../../agent/loop.py) 的 `_signature` 取阻断失败的名称，再与紧邻上一轮比较。它能识别连续相同，但不会仅凭这个比较识别 A → B → A；同一用例内部失败原因改变时，也可能仍被判断为无进展。这是一种简单且保守的策略，适合看懂控制流程；个人设计可增加原因摘要、关键状态或历史集合比较，并说明付出的复杂度。


## 给下一轮什么上下文，才不会越修越偏

失败后把全部聊天原样塞回模型，会重复大量背景；只发一句“还没好”，又丢失了原要求。下一轮最需要的是一份围绕当前问题整理的交接材料：

| 材料 | 发货例子 | 用途 |
|---|---|---|
| 固定要求 | 已预占可发货；草稿、取消、已发货不可再发 | 防止只解决眼前一个红灯 |
| 当前候选及实际差异 | V1，恢复了合法发货分支 | 让模型知道当前起点 |
| 剩余失败与原证据 | 草稿仍被放行，附复现条件和报告位置 | 把调查聚焦到未解决部分 |
| 已尝试方案 | V0 曾把所有状态一律拒绝，已证明不可取 | 避免重新走回旧错误 |
| 范围和剩余预算 | 只改确认的实现文件，还剩一次检查机会 | 约束下一步动作 |

原报告、完整 Diff 和运行输出留在可追溯的位置；摘要负责告诉模型先读哪些材料。这样既控制上下文长度，又保留核验入口。遇到新证据推翻旧假设，应更新摘要，而不是让过时结论一直占据开头。

**Loop History** 就是这条交接链的逐轮记录。最低限度应能连起：本轮检查了哪版、结果怎样、据此派了什么任务、实际改出哪版、为什么继续或停止。只写“第一轮失败，第二轮成功”，无法支持下一位接手者判断。

这是同一事项内的上下文管理。把经验审查后用于下一项需求，是后续记忆与流程复用的工作，不由一份 History 自动完成。


## 预算与异常，决定了能否安全交回

时间、轮数与 Token 是三种不同限制。轮数控制尝试次数；时间控制等待多久；Token 是模型处理输入输出的用量单位，用量预算控制本次愿意投入多少模型资源。

假设预算为 3,000 Token，前两次修改累计使用 2,700。启动第三次并不能保证只用 300，执行器必须支持足够明确的限制，否则只能在返回后知道是否超支。因而“用量达到上限后不再启动”是停止策略，不能宣称它保证实际消耗绝不超限。缺少用量记录时写“未知”，不能把未知按零累计。

同样，主命令超时不代表所有子进程和外部动作都已停止。退出前需要说明最后观察到的阶段，核对是否产生新文件或未完成写入。这里最有用的是把两个版本分开记录：

```text
最新候选：V2
最后完成检查的候选：V1
V1 检查结果：草稿发货未被拒绝
停止原因：生成 V2 后达到用量预算
当前结论：V2 待复验，不能沿用 V1 的失败或通过结论
下一步：先检查 V2，再决定是否继续修改
```

这段是交接格式示例，不是当前程序保证输出的字段。安全退出的价值就在这里：下一位知道该先检查哪版，不必凭聊天猜测。

如果保存 History 本身失败，应输出可取得的错误并停止，不能再声称记录已可靠落盘；若某一步的结果不确定，就把不确定性留在交接中。


## 亲手观察三条轨迹，再建设自己的 Loop

先用以下小实验把“次数”和“结论”对上。在课程仓库根目录，用已安装项目的 `.venv` 执行 PowerShell 命令：

```powershell
.\.venv\Scripts\python.exe -X utf8 docs/courses/L10/examples/loop_control_lab.py converge
.\.venv\Scripts\python.exe -X utf8 docs/courses/L10/examples/loop_control_lab.py repeated
.\.venv\Scripts\python.exe -X utf8 docs/courses/L10/examples/loop_control_lab.py last-repair
```

它们给真实控制器喂入**合成报告与执行替身**，不调用 Codex，也不修业务代码。比较输出中的 `result.status`、`checks` 和 `executor_calls`：

| 模式 | 应观察到的检查 / 修改调用次数 | 控制器状态 | 应怎样解释 |
|---|---|---|---|
| converge | 2 / 1 | converged | 第二次检查看到通过；只是控制实验的收敛 |
| repeated | 2 / 1 | stopped_no_progress | 连续失败相同，停止 |
| last-repair | 1 / 1 | stopped_max_rounds | 修改后没有下一次循环内检查，最新候选待复验 |

包装脚本退出码为 0，只说明预设现象被观察到；例如成功观察到“无进展停止”，也会退出 0。必须读内部状态，不能把这个 0 当成 FlowERP 发货通过。

之后按[实践操作手册](实践操作手册.md)第 3～4 步，把控制现象与真实发货、同一候选的改动对应起来；第 5～6 步建设并执行自己的 Loop；第 7 步让同伴复核。手册中的教学预设补丁和执行替身都不替代个人 Codex 执行。

源码阅读截至本次核对仍有几个明确边界：基础 Loop 默认只生成任务，显式启用执行才调用修改；它没有把严格报告校验完整接入所有判断；末轮可能留下未复验修改。因此，默认运行一次出现绿灯，不证明你的客户发货规则已通过。个人结果要同时给出工作台控制结论和 FlowERP 业务结论。

**迁移练习**：三轮失败依次为 A、B、A，你会继续吗？先解释 A、B 对应的业务条件，再判断是否振荡。若第二轮之后只剩 20 秒，而一次完整检查通常需要约一分钟，不应再启动一轮无法完成核验的修改。把你的判断和同伴反例写入[提交模板](SUBMISSION.md)。

本讲对应 CLO-4。能设计一条真实收敛轨迹，也能如实交回一条未收敛轨迹，才说明你掌握了这个控制器；更多源码与实验细节见[参考详解](参考详解.md)。
