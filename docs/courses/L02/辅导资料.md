# L02｜把仓库规则写进 `AGENTS.md`

L01 的工作台已经能查回任务和检查记录。可是换一个会话继续开发时，你仍要重新解释：哪些文件能改，哪些结果不能写成“已验收”，做完必须交回什么。这些长期约定没有固定下来，每次协作就容易走样。

这一讲继续维护同一个工作台，把已经确认的约定写进项目根目录的 `AGENTS.md`。你核对代码和规则依据，Codex 协助起草，再用新会话中的具体请求检查规则是否起作用。客户 FlowERP 仍不在本讲开发范围内。


## 1｜先看一个容易说错的地方

**状态文字必须忠实表达已经发生的事实。**

> **案例｜记录齐全不等于已验收**
>
> 工作台显示：“运行记录完整，等待人工审核。”有人觉得太长，建议改成“已验收通过”。这样改可以吗？

这个改法不可以。记录收齐了，不代表有人检查并接受了结果。把文字改短，却多出了一项尚未发生的决定。

![记录完整与人工审核是两项不同事实](./图解/状态含义案例.png)

**图 2-1　记录完整与人工审核是两项不同事实**

*读图：记录完整性与人工审核是两项独立事实。*

左边说记录是否齐全，右边说人是否审核。两个英文字段分别保存这两项信息；今天先理解含义，不必背字段名。

如果只是把中文改得更好读，同时保留“待审核”的含义，就可以继续讨论。我们要写的规则，应当让 Codex 分清这两种情况。

## 2｜怎样把提醒写成规则

先请 Codex 查找相关实现和测试，说明两项状态分别表示什么。自己打开它引用的文件核对，不能只凭字段名称猜。

然后比较三种写法：

| 写法 | 问题 |
|---|---|
| 保证状态正确 | 没说清怎样才算正确 |
| 禁止修改状态展示 | 连正常的中文调整也禁止了 |
| 分别展示记录完整性与人工审核；允许调整中文，不因记录完整就填写“已验收” | 说清了不能改变什么，也允许正常维护 |

第三种更适合这个任务。它既有依据，也能用具体请求检查。

![从事实推导规则，再用两类请求检验](./图解/事实到规则.png)

**图 2-2　从事实推导规则，再用两类请求检验**

*读图：查明事实 → 写成规则 → 分别测试错误请求与正常请求。*

图中的 `status()`、`_chain()` 是参考实现的入口。自己的程序可能名称不同，要找到承担同样职责的代码，再据此写规则。

## 3｜AGENTS.md 里还要写什么

`AGENTS.md` 是保存项目协作约定的 Markdown 文件。把下一次任务仍会用到的内容留下来，重点回答四个问题：

- **去哪里改？** 简要说明相关目录和入口的用途。
- **什么不能随意改变？** 例如自动检查与人工接受必须分开，历史失败记录要保留。
- **怎样检查？** 写清实际可用的命令、运行目录和环境。
- **怎样算完成？** 说明要交回修改内容、实际检查结果和未解决的问题。这也叫 Definition of Done，即完成条件。

已有规则先保留修改前副本，再补缺失内容。不要照抄不存在的路径或命令，也不要把“今天库存是 8”这种随时变化的数据写成长期规则。

本讲还会遇到几个词，先分清用途即可：

| 名称 | 用来做什么 |
|---|---|
| Prompt | 交代这一次任务，例如“只给方案，先不改代码” |
| AGENTS.md | 保存这个项目以后仍需遵守的约定 |
| Skill | 提供一套可复用的方法，例如先调查再起草规则 |
| Hook | 在指定时机触发程序检查 |
| MCP | 连接工具与外部资料 |

今天主要练习写项目规则。文字规则本身不会执行检查，也不能代替程序中的权限和业务校验。

### 把结构决定写成可执行的约定

沿用 L01 确认的结构设计，先核对实际代码，再写目录与函数职责。例如：命令入口接收参数并调用任务逻辑，持久化读写由已确认的存储入口承担；增加一个命令时复用这些能力。附上本仓库的真实位置、命名或错误处理示例，以及能够验证的命令。

`AGENTS.md` 保存已经确认的设计，不会自动替你设计架构。对尚未满足的约定，记录现状和待调整项，不能写成已经实现。可以在下节的修改前后对照实验（N0/N1）之外，补一个“把存储逻辑复制到新命令”的违规请求和一个“复用现有入口”的合法请求；保留原实验，不把额外回答表现当作代码结构已经合格。

## 4｜怎样知道规则有用

关键是**先保留修改前的回答，再写规则**。如果边改边测，最后就说不清差别从哪里来。

按[实践操作手册](./实践操作手册.md)操作：

1. 在自己的练习仓库中，保存原规则和个人判断。
2. 新建一个待测任务，发送手册中的固定请求，保存真实回答，叫 **N0**。
3. 回到写作任务，只修改已确认的规则，保存修改后版本。
4. 再建一个全新任务，对同一组计划进行评审，保存回答，叫 **N1**；按手册补充规则来源核对，并记录请求差别。
5. 再问一个正常维护请求，看它是否仍能继续提供方案。

这里的 N0、N1 只是修改前后两份回答的编号。手册的固定请求还包含库存、订单和采购边界，那些是预先说明规则的情境题，不要求你已实现后面几讲的业务。本讲只评审计划，不实际修改业务数据。当前仓库找不到的依据，要注明待确认。

针对前面的例子，检查应得到这样的判断：把记录完整写成已验收，应被纠正；保留待审核含义、调整中文，应允许继续。再检查错误命令请求：如果参数拼错、检查尚未开始，就不能说测试通过。

如果 N0 已经正确，如实保留。如果 N1 仍然错误，或把正常工作也拒绝了，先核对打开的仓库和规则来源，再修改规则、重做相关检查。

## 5｜三件事要分开看

![规则读取、回答表现、程序检查需要分别核对](./图解/复验证据.png)

**图 2-3　规则读取、回答表现、程序检查需要分别核对**

*读图：分别核对规则读取、回答表现和程序检查。*

从左到右分别检查：规则有没有进入会话、回答是否遵守规则、程序检查结果如何。最后根据这些实际材料决定接受还是继续修改。

新会话说“我读到了”还不够，应核对可观察的文件读取记录和引用内容。无法确认时，就写“载入未验证”。

比较 N0 和 N1，要引用回答中具体变化的句子；两次都正确，就写“没有观察到明显改善”。一次回答变好，也不能保证所有任务都有效。

最后按手册运行已有程序检查，保存命令、输出和退出码。检查通过能说明被检查的行为符合预期，但不能替代上面的规则实验。环境错误或运行了零个用例，都不能填写“通过”。

## 6｜从哪里开始，交什么

现在打开[实践操作手册](./实践操作手册.md)，从第 1 步确认自己的 L01 练习仓库开始，按七步完成。具体请求和命令都在手册里，不需要自己拼接。

个人材料放在该仓库的 `lesson-02-submission/`：规则修改前后副本、N0、N1 与正常维护对照，以及自己的 `记录.md`。在记录中说明条目的来源、取舍、实际结果和待复核问题；请同伴补查一项，再写下自己的结论。通过要求可对照[行动卡](./行动卡.md)。

完成后做一次迁移练习，换一个问题：“采购申请建好了，能不能先加库存、明天补审批？”说明申请与批准有什么区别、现在允许做什么、怎样检查库存没有被误改。这用于检验你能否把本讲的方法用到另一种情况。


## 本讲留下什么，下一讲怎样接着用

本讲留下带代码依据的项目规则和前后对照记录。下一讲遇到新的库存导出需求时，规则仍继续有效；需要重新确认的是这次客户要什么、哪些不做、怎样验收。这正是长期规则与单次 Spec 的分工。

## 课程大纲中的本讲要求

- **核心内容**：Prompt、`AGENTS.md`、Skill、Hook、MCP 的职责边界；最小而有效的项目约束。
- **演示结果**：同一任务在缺少约束与加入约束后产生不同结果。
- **课内增量**：补齐目录结构、禁止事项、验证命令和 Definition of Done。
- **通过标准**：新会话能够读取约束；错误命令或越界修改能被明确拒绝或纠正。
