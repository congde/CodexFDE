# 16 讲系统化精修蓝图

> 版本：2026-09-01
> 性质：课程合同的教学审计投影，不是第二份课程大纲
> 上位事实源：`docs/课程大纲-Codex-FDE行动营-个人研发自动化工作台.md`
> 机器投影：`workbench/course_mainline.py`

## 一、为什么要有这份蓝图

本课程不是 16 个 AI 工具演示，也不是 16 个 FlowERP 功能练习。它训练学生构建一套长期运行的个人 AI 研发工作台，并让这套工作台在真实 ERP 交付中不断升级。

每讲必须形成同一条因果链：

```text
上讲留下的真实问题
  → 本讲学生作出工程判断
  → 交付一个可观察的 FlowERP 状态
  → 新增或验证一项工作台能力
  → 主动制造失败并取得反证
  → 形成可归属于学生的学习证据
  → 把尚未解决的矛盾交给下一讲
```

本蓝图只负责审计详细讲义、任务卡和课堂实施是否忠于上位合同。如果本文件与课程大纲或机器投影冲突，以课程大纲为准，并同步修订本文件。

## 二、16 讲统一精修规则

每讲基础线必须同时满足以下五条：

1. **一个产品增量**：只交付一个能够被用户或下游系统观察的 FlowERP 状态；L01～L03 允许业务账不变，但必须形成基线、规则或签字 Spec。
2. **一个工作台增量**：只引入解决当前重复工程问题所必需的核心能力，不把后续章节提前讲完。
3. **一个主动失败实验**：学生必须亲自制造反例，先写预期，再观察权威状态，不能只观看教师成功演示。
4. **一组个人学习证据**：保留首次判断、运行或失败记录、修订说明与迁移证据；参考仓库全绿不等于学生达成。
5. **一个明确交接矛盾**：本讲结尾必须留下下一讲必须解决的问题，避免课程退化为互不相干的功能目录。

### 内容分层

| 层级 | 用途 | 是否进入基础通过线 |
|---|---|---|
| 基础线 | 全体学生必须完成的唯一案例、动作和证据 | 是 |
| 迁移线 | 换业务对象或换技术实现，验证能力能否迁移 | 否，可用于提高任务 |
| 挑战线 | 外部框架、多仓库、多租户、云部署等扩展 | 否，不得补偿基础线缺失 |
| 教师证据线 | 达成率、误区、增值、复评与持续改进数据 | 不作为学生作业，由真实开课采集 |

同一案例可以贯穿多讲，但每讲只能解决当讲约定的问题。后续技术不得反向成为前置通过条件。

## 三、四阶段学习弧

| 阶段 | 课程 | 学生要完成的转变 | FlowERP 连续产品状态 | 工作台连续能力状态 |
|---|---|---|---|---|
| 接管与委托 | L01～L04 | 从“让 AI 写代码”转为“先理解、立规则、签合同、受控委托” | 基线冻结 → 规则保护 → 库存导出 Spec → 库存导出实现 | 接手报告 → `AGENTS.md` → Spec → 最小执行与摘要 |
| 质量证据链 | L05～L08 | 从“测试通过”转为“主动证明评测有效，并让本地与远端共用裁判” | 幂等入库 → 可用库存 → 销售订单 → 原子预占 | Eval → Harness → Hook → CI Evidence Envelope |
| 受控修复与协作 | L09～L12 | 从“一次修复”转为“可停止、可协作、可回退且保留人责” | 取消释放 → 合法状态迁移 → 采购申请 → 审批后入库 | Repair Task → Loop → Subagents → Graph/HITL |
| 产品化与进化 | L13～L16 | 从“本地脚本”转为“可访问、可操作、可反馈、可现场复验的系统” | 补货任务 → 真实操作页 → 反馈改进 → 陌生小需求 | Task API → Web → Feedback/Evolution → 冷启动与答辩 |

## 四、16 讲端到端审计矩阵

| 讲次 | 入口状态与唯一冲突 | 学生核心动作 | FlowERP 出口 | 工作台出口 | 主动失败实验 | 学生个人证据 | 交给下一讲的矛盾 |
|---|---|---|---|---|---|---|---|
| L01 | 陌生仓库与终局演示并存，无法判断“完成”层级 | 只读勘察、运行环境检查、冻结基线、修订接手报告 | 当前业务能力与状态形成可复验快照，业务账不变 | 四段式接手报告与四层完成状态 | 运行一条预测会成功但实际失败的真实命令，标记未知而非补写结论 | 首次判断、命令输出、事实修订、个人仓库迁移报告 | 一次会话中的判断无法约束后续任务 |
| L02 | 风险判断存在于人脑和聊天记录，跨会话会丢失 | 分类长期规则与本次需求，编写最小 `AGENTS.md`，做无规则/有规则对照 | 业务状态不变，领域红线进入仓库约束 | 目录边界、禁止项、验证入口、DoD 与就近规则 | 请求直接改库存或绕过审批，同时测试合法前端修改不被误伤 | 规则归属表、规则 Diff、拒绝/放行对照、合法替代路径 | 规则只说明不能破坏什么，仍未说明本次做什么 |
| L03 | “增加导出功能”有对象、字段、顺序和错误语义歧义 | 澄清来源，编写 `REQ-COURSE-L03`，机器校结构、同伴校语义 | 签字后的库存可用量导出合同，业务代码不变 | 可解析 Spec 模板、必要字段校验与来源追踪 | 删除必要字段；让另一组仅凭验收项复述需求并提出反例 | 初稿、澄清记录、解析结果、跨组复述差异、修订版 | 有了合同，但尚未证明 AI 能在边界内实现 |
| L04 | Spec 已签字，但 AI 的读写集、预算和人工确认点不明确 | 设计能力信封，委托最小实现，逐文件审 Diff，独立复验 | 稳定库存导出，包含固定字段、`available`、稳定排序及错误行为 | 受控执行入口、最小 Diff、结果摘要与剩余风险 | 诱导越过写集、顺手重构或写入秘密；独立复验不接受模型自述 | 授权清单、执行轨迹、Diff 审查、`inventory_export_is_stable`、摘要 | 现有测试可能与实现共享错误假设，缺少反证 Eval |
| L05 | 重复入库可能被普通示例测试遗漏 | 从损失反推反例，故意运行缺陷夹具，两次稳定红，再最小修复 | 同一 `receipt_key` 只生效一次，库存与事件不重复 | `receiving_is_idempotent` 业务 Eval、工程约束 Eval、红绿协议 | 对 `RECEIPT-001` 重放两次，检查数量和事件数；删除/放宽断言须被识别 | 风险—反例表、两次红灯、失败签名、修复 Diff、同命令绿灯 | 单项 Eval 可信，但多个结果还没有统一裁决语义 |
| L06 | Eval 分散，告警、阻断、异常和退出码可能互相矛盾 | 设计等级与报告 Schema，制造三类结果并三角校验 | 交付 `available = on_hand - reserved` 的权威口径 | 唯一 Harness、blocking/observing/error、JSON 报告与退出码合同 | 分别制造观察失败、阻断失败、执行异常并预测退出码 | 三份报告、预测/实测对照、等级评审、消费者字段说明 | 统一裁判仍依赖人主动运行，修改结束时可能漏检 |
| L07 | 本地开发完成事件没有可信、可恢复的自动护栏 | 审查 Hook 来源与信任边界，把统一 Harness 接入生命周期 | 创建销售订单；缺货失败且不污染库存/订单状态 | 项目级 Hook、超时、重入保护、失败反馈与恢复路径 | 违规修改触发阻断；超时、协议异常和恢复后三组事件都要复现 | 信任审查、事件输入、Harness 报告、阻断/恢复记录 | 本地通过不等于远端提交具有可追溯证据 |
| L08 | CI 可以绿，但可能没跑、跑错提交或没有证据 | 完成 A 缺证据、B 缺陷红、C 修复绿三次真实 Run 并互审 | 订单预占原子化，可用库存不为负；不新增第二项业务功能 | CI 复用 Harness，Evidence Envelope 绑定提交、命令、报告与 Artifact | A 证明假绿不可接受；B 让 `stock_never_negative` 真实红；C 同门转绿 | 三个 Run ID、commit、原始日志、Artifact、同伴法证判决 | CI 失败信息仍过于庞杂，修复者不知道最小行动范围 |
| L09 | 失败报告包含事实、推测和噪声，直接投喂会导致越界修复 | 冻结报告事实，生成并盲测一张最小 Repair Task | 取消订单释放预占，并保持重复取消语义稳定 | 报告到 Repair Task 的映射、授权写集、禁止项与完成证据 | 注入互相矛盾或缺字段的失败报告，验证映射器拒绝猜测 | 事实/推测分层、任务初稿、盲测反馈、修订版、单轮修复结果 | 单轮任务可执行，但连续失败时何时继续、何时停止未定义 |
| L10 | 修复可能无进展、振荡、引入回归或耗尽预算 | 先写控制合同，再运行成功收敛与安全退出路径 | 完成一条合法订单状态迁移，非法迁移保持原状态 | 最多三轮 Loop、失败签名、进展规则、轮次/时间/Token 预算 | 制造同签名无进展、A/B 振荡或预算耗尽，检查停止原因 | 控制图、Loop History、用量、stop reason、剩余失败与交接 | 串行 Loop 面对独立跨模块调查会浪费墙钟时间 |
| L11 | 并行可能缩短耗时，也可能产生写冲突和汇总税 | 画读写集/冲突图，并行只读任务，主 Agent 核验后串行集成 | 交付采购申请及其正常、非法输入路径 | 子任务合同、上下文隔离、证据化汇总和单/多 Agent 对照 | 故意提交两个共享写集任务，要求在执行前判定不可并行 | 初始排程、原始子输出、引用式汇总、冲突处置、净收益对照 | 多角色结论仍依赖一次会话，暂停、打回和人审不能恢复 |
| L12 | 阶段、回退、人审和异常被藏在聊天流程中 | 为状态、边和守卫写判决规则，运行暂停、打回、恢复 | 采购申请只有经具名审批后才能入库 | 可持久 Graph、checkpoint、具名 HITL、异常与最大轮数 | 匿名审批、重复审批、非法迁移、跨进程恢复分别复现 | 状态图、守卫表、Trace、具名决定、恢复记录 | Graph 仍是本地入口，外部使用者无法提交和查询任务 |
| L13 | 本地状态存在，但没有稳定资源身份和并发安全 API | 设计最小资源合同，提交、查询、竞争启动并重启复验 | 通过 Task API 完成一个补货需求并回链业务对象 | Task ID、`202` 受理语义、合法迁移、持久查询与稳定错误合同 | 两客户端竞争同一迁移；重启后查询同一 Task；非法迁移失败 | 请求响应矩阵、竞态记录、事件链、重启前后同 ID 证据 | JSON 对机器友好，但业务用户不能有效判断现状和下一步 |
| L14 | 后端状态真实，但页面可能静态、陈旧、吞错或重算业务结果 | 完成一个真实操作主路径，注入断网与未知状态，四方对账 | 用户可在页面发起/查看真实 ERP 操作与结果 | Web 状态文案合同、轮询/重试、证据下钻与无密钥边界 | 断网、未知枚举、字段漂移后不得保留旧绿灯 | DOM/API/SQLite/业务对象对账、失败重试、陌生人走查 | 用户暴露的问题还没有受治理地回到 Spec、Eval 和产品改进 |
| L15 | 反馈可能无来源、被篡改或未经审核直接改变质量标准 | 为真实 Task 写摘要，采集原文，复现分诊，具名决定并独立交付 | 由一条真实反馈形成并验证一个受控 ERP 改进 | 可追溯摘要、反馈状态机、Spec/Eval 候选与人工晋级边界 | 无来源、含敏感信息、不可复现或错误方案不得直接晋级 blocking | Delivery Summary、原始反馈、分诊决定、新资产、独立 Task 结果 | 完整链路仍需证明能在陌生环境处理此前未知的小需求 |
| L16 | 排练过的全绿演示无法证明迁移、发布和答辩能力 | 冷启动、随机抽题、现场交付未实现需求、失败打回、证据答辩 | 在旧账不损坏前提下交付一个此前未实现的受控小需求 | 可复验发布包、健康检查、证据索引、回滚说明与工程答辩 | 改变演示顺序、制造失败打回、重启复验、随机追问未证明边界 | 冷启动记录、Spec/Diff/正反用例、全链证据索引、答辩与技术债 | 进入真实运行后的长期反馈与下一周期课程持续改进 |

## 五、每讲发布门禁

详细讲义、任务卡或课堂材料在发布前逐项回答：

- [ ] 标题、核心内容、演示结果、课内增量、通过标准与课程大纲逐字对齐。
- [ ] 开头写明“基础线唯一性”，没有让迁移案例抢占主案例。
- [ ] 能说清本讲进入前的 FlowERP 状态和退出后的可观察变化。
- [ ] 能说清为什么当前业务冲突必然要求新增这项工作台能力。
- [ ] 线上精讲不超过 30 分钟，只完成问题框架、核心概念和关键示范。
- [ ] 线下活动包含学生预测、主动失败、权威状态检查、同伴反证和修订。
- [ ] 评价量规同时检查判断、实现、验证、证据和迁移，不按篇幅或代码量评分。
- [ ] 至少保留一次正常路径和一次失败路径；失败后不变状态有明确观察点。
- [ ] 学生证据能够绑定本人、版本、命令、时间和原始结果；截图与 Agent 自述不能单独证明通过。
- [ ] 结尾明确写出下一讲继承的未解决矛盾。
- [ ] 政策、平台和工具的易变信息已标注核验日期；扩展内容被清楚标为迁移或挑战。
- [ ] 教学设计、参考实现和真实教学效果三类事实没有混写。

## 六、课程级质量观测

真实开课后，按讲和 CLO 采集以下数据，不用模拟数据补齐：

| 观测对象 | 建议指标 | 用于改进什么 |
|---|---|---|
| 判断质量 | 首次误判率、未知标记率、修订后正确率 | 先修案例与支架，不先增加概念 |
| 失败学习 | 主动失败成功率、失败签名稳定率、错误归因率 | 反例强度与调试教学 |
| 证据质量 | 命令/版本绑定率、不可追溯项、假绿色识别率 | 证据模板与诚信门禁 |
| 迁移能力 | 新仓库或新需求独立复现率、教师口头补步骤数 | 判断是否真正形成个人工作台能力 |
| 协作责任 | 冲突预判率、具名审核完整率、越权修改率 | 团队边界与工程责任教学 |
| 学习增值 | 首次与二次提交变化、不同起点学生增值 | 分层教学与持续改进 |

这些指标是建设计划。只有在真实开课、获得合规学习记录并完成统计后，才能写成教学成效。

## 七、系统精修完成判据

“16 讲已经精修”至少意味着：

1. 课程大纲、详细讲义、任务卡和机器投影不存在主案例、产品增量或通过标准冲突。
2. L01～L04 可独立形成工作台 V0，L05～L15 每讲都有 ERP 可观察增量或真实修复，L16 能现场交付未知小需求。
3. 任意抽取一讲，都能从上一讲的失败解释为什么需要本讲能力，并从本讲证据解释为何可以进入下一讲。
4. 基础线可以在干净环境跟跑；挑战内容缺失不会阻断基础结业，基础证据缺失也不能被挑战成果替代。
5. 所有“课程效果”表述都能区分已验证仓库事实、课程建设计划和待校方/真实教学补证事项。
