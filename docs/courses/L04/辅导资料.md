# L04｜委托 Codex 执行一次最小变更

L03 已经把“库存导出”写成确认后的说明，也让工作台能够读取说明。但能读任务、保存记录，还不等于能组织一次开发。今天先补齐工作台的执行能力，再让它按同一份 Spec 交付库存导出。

因此这一讲有两张工作单：**A 建设工作台，B 用工作台开发 FlowERP。** A 要先被独立接受，B 才开始。你仍负责范围和接受决定，Codex 是开发伙伴，工作台负责把输入、执行和结果连起来。

## 1｜先完成 A：把“能记录”补成“能组织执行”

L01 留下了任务和检查账，L02 留下项目规则，L03 留下需求模板与解析器。现在要把这些接起来：读取确认需求，在允许目录调用 Codex，限制修改范围，收回实际差异和输出，再运行检查、停下来等人判断。这套最小交付能力在课程中称为 Workbench V0。

![先建设并接受工作台 A，再通过它交付库存导出 B](assets/reading-figures-v1/01-build-then-deliver.png)

**图 4-1　先建设并接受工作台 A，再通过它交付库存导出 B**

*读图：中间箭头有前提——A 已独立接受。A 通过不代表 B 的库存文件已经合格。*

先用一项范围很小的任务验证 A：它真的调用了 Codex 修改，还是只运行检查？工具失败时，任务会不会仍显示成功？改到未授权文件时，有没有如实记录和阻断？自动检查通过后，会不会擅自写成已经人审？

只运行几条检查命令，可以证明复验发生，不能证明工作台已经组织了开发。保留实际调用、差异与结果，请没有参与本次执行的人复验并记录接受决定。没有接受记录，就停在 A；具体操作见实践手册第 1～4 步。

## 2｜A 被接受后，B 才接收同一份库存说明

B 的需求直接来自 L03 的确认版 `FDE_SPEC.md`，不能到了开发时临时换题。它关联这份说明、已接受的工作台版本和本次候选代码。

**候选**就是这次准备修改和检查、还未被接受的代码副本。控制工作区保存规则和任务记录，独立 FlowERP 仓库提供客户源码，本次实现与复验都应指向同一候选。

![控制工作区、客户源码和本次候选各有职责](assets/reading-figures-v1/02-candidate-and-scope.png)

**图 4-2　控制工作区、客户源码和本次候选各有职责**

*读图：左边组织任务，中间提供客户源码，右边才是本次修改对象。图里的文件职责要换成调查后的实际路径。*

给工作台的委托至少说清：用哪份 Spec、在哪个候选做、允许改哪些文件、到什么条件必须停止、用什么检查交回结果。允许修改的文件清单称为**写集**；目录正确并不等于里面所有文件都能改。

范围要足以完成导出，又不能顺手包含采购页面重做等无关事项。确实需要额外文件时，先交回理由和影响，由你重新确认。提示词里的约定还需要执行控制和实际差异检查共同落实。

## 3｜让工作台执行，再收回实际结果

输入确认后，工作台启动一次 Codex 调用，不依赖你逐句输入“继续”；这叫本讲的**非交互执行**。它仍然有时间、范围和停止条件，不意味着无人负责或可以无限尝试。

执行结束先找到四样材料：使用的 Spec 与候选；实际代码差异（Diff）；真正执行过的命令、输出和错误；按原要求运行的检查结果（Eval）。若缺少它们，先查明执行情况，不能用 Codex 的“完成了”补齐事实。

例如：调用正常结束，CSV 也生成了，但把在库 8、预占 3 的可用量写成 8。结论应是“调用结束，业务检查失败”，而不是“已完成”。程序退出 0 的含义取决于哪个程序及其约定，不能把调用成功直接当作客户结果正确。

## 4｜拿实际文件与 L03 的要求逐项比较

L03 已经确定八列、保留明细、可用量按减法计算，导出不改变库存。现在要真正执行，而不是再写一份预期说明。

手册使用东仓在库 8、预占 3，西仓在库 12、预占 4，预期可用量分别为 5 和 8。西仓换了数据，是验证同一规则，不是修改 L03 的口径。以下只是一份教学预期：

```csv
sku,name,site,location,lot_id,on_hand,reserved,available
A,示例商品,东仓,E01,L01,8,3,5
A,示例商品,西仓,W01,L01,12,4,8
```

八列依次是商品编码、名称、仓库、仓位、批次、在库、预占、可用。两条明细不能合并成一条总数，否则客户不知道去哪里找货。

再换几种情形复验：记录打乱时仍按约定排序；空库存仍有八列表头；名称含逗号、引号、换行时，用 CSV 读取器读回仍是原内容。写出中途失败时，原有效文件应保留，不留下可被误用的半成品。

最后回头查库存和流水。导出只是读取，成功和失败都不应改变它们。CSV 数字正确只能证明输出的一部分，不能替代对业务状态的检查；同样，也要核对实际差异是否越过授权文件。

## 5｜把同一版本交给人，决定接受还是返工

![调用结束、检查通过与人工接受分别判断](assets/reading-figures-v1/03-finished-versus-accepted.png)

**图 4-3　调用结束、检查通过与人工接受分别判断**

*读图：检查通过后进入待审核，而不是直接完成。复验者需要看到同一版本、同一要求和实际结果。*

复验者从原 Spec 出发，查看差异，亲自重跑正常和失败路径，再记录接受、打回或证据不足。上午报告对应上午代码；下午若又改了排序，必须复验新版本。旧报告留作历史。

返工时先分对象：CSV 算错而工作台如实报红，修 B 的导出；工具明明失败，工作台却放行，先暂停 B、修 A 并重新验收工作台；没有有效报告时，先查环境、目录与版本。不要在证据不明时继续扩大业务修改。

## 6｜现在按 A、B 的顺序实践

打开[实践操作手册](实践操作手册.md)：第 1～3 步准备并建设 A，第 4 步由非执行者复验接受 A，第 5 步才通过工作台执行 B，第 6～7 步复验库存导出并记录人的决定。

交接摘要只需讲清：A 是哪版、由谁接受；B 根据哪份 Spec、修改哪个候选；实际改了什么、运行了什么；谁依据哪些结果作决定；还剩哪些风险。详细凭据用路径关联，失败证据保留。密钥、环境文件和运行数据库不作为提交材料。

完成本讲后，学生应能解释自己的范围判断、失败定位与修订，而不是只展示参考仓库能够导出。A 的工作台与 B 的客户结果都要有各自的依据。

再做一次迁移判断：客户临时要求给 CSV 增加采购成本列，这列不在原 Spec 和授权范围内。此时应先确认数据来源、查看权限和新增验收要求，再更新委托；原导出通过报告不能证明新增列也合格。说明这次改变影响 A 的执行机制，还是 B 的业务需求，并请同伴检查你的理由。

完整授权说明、故障分支与交接样例见[交付机制与故障选读](交付机制与故障选读.md)；[原有总览图](assets/lesson-overview.png)与[教师执行记录](assets/execution/README.md)保留供查阅。三张正文图均为教学示意，[设计与提示词](assets/reading-figures-v1/设计与提示词.md)可回查。

## 课程大纲中的本讲要求

- **核心内容**：非交互执行、工作目录、权限边界、结果采集与人工确认点。
- **演示结果**：读取第 3 讲 Spec，委托 Codex 完成一个小型代码变更并运行测试。
- **课内增量**：先由学生直接监督 Codex 补齐并独立验收 Workbench V0 的执行入口、写集检查、最小 Eval 和结果摘要，再由 V0 在授权工作区调用 Codex 交付库存导出；不额外包装为文件读写 MCP。
- **通过标准**：变更能够运行；基础测试通过；摘要包含修改文件、验证命令和剩余风险；密钥和环境文件未提交。
