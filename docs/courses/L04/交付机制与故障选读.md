# L04｜交付机制与故障选读

原完整说明保留在此，先按[辅导资料](辅导资料.md)读完 A、B 两次交接。实际执行仍按[实践手册](实践操作手册.md)。


本资料用一次库存导出解释“怎样把任务交出去，又怎样收回来”。先看例子和三张图；具体命令、提示词和记录格式见[实践操作手册](./实践操作手册.md)。

## 这一讲，不只是让 Codex 说“做完了”

L03 已经把“导出库存”写成了确认后的需求说明，称为 **Spec**。现在要真的做出导出功能：运行以后得到一份 CSV，也就是可以按表格读取的文本文件；里面的数量与位置符合约定，原库存不被改变。

继续用运营周宁和学员林舟的课堂故事。人物是虚构的，下面数字和对话是教学示例，不是客户记录，也不是你已经运行出的结果。

**交付要核对实际改动和业务结果，不能只接受执行者的完成声明。**

> **案例｜收到“已完成”，还缺什么依据？**
>
> 周宁问：“上次说清楚了，这次能把文件给我了吗？”林舟请 Codex 开发，收到一句“已完成”。但这句话还没有回答：改的是哪份代码？有没有改多？文件里的可用量算对了吗？谁重新检查过？

本讲要把这些问题接起来。完成时留下两个成果：**能组织这次交付的工作台，以及由它组织完成的库存导出。** 你决定范围，Codex 协助开发，工作台保存任务与结果，独立复验者和审核者核对后作出决定。

阅读只沿这一条线：**先搭好工作台 → 说清本次委托 → 在指定位置执行 → 核对实际结果 → 由人接受或打回。**

## 1 先分清两件事：A 搭工作台，B 做库存导出

### 1.1 为什么不能直接开始 B

前几讲已有项目规则、需求说明和读取说明的工具，但还要检查工作台能否真正组织一次开发：把任务交给 Codex、限制修改范围、保存结果、运行检查、停下来等人审核。

> **案例｜检查失败，工作台却显示通过**
>
> 假设库存导出检查已经失败，工作台却把失败吞掉，显示“通过”。即使这次碰巧生成了正确文件，你也不能放心使用它组织下一次交付。因此，先验证工作台是否可靠，再让它组织客户功能开发。

手册把两件事叫作 **Ticket A、Ticket B**。Ticket 在这里就是“工作单”，先记成 A、B 即可。

![图1：A先建设并独立验收工作台，B再通过已接受的工作台交付库存导出](assets/reading-figures-v1/01-build-then-deliver.png)

*读图：先接受工作台 A，再用它交付库存导出 B；两者分别验收。*

先看左边，A 接受的是工作台；中间箭头有前提——A 已被独立接受；再看右边，B 才开始实现库存导出，之后还要单独复验和人审。不是 A 通过，CSV 就自动合格了。

### 1.2 A 要做到什么，才可以交给别人检查

A 阶段，你直接监督 Codex 补齐个人研发工作台的最小版本，课程称为 **Workbench V0**。V0 是起步版本，不要求先做出一个大而全的平台。

用一项任务走一遍，检查下面五件事：

| 你要看什么 | 合格时应能回答 |
|---|---|
| 任务有没有依据 | 这次使用哪份确认后的 Spec，有哪个任务编号可以追查？ |
| 是开发还是只检查 | 这次真的调用了 Codex 修改代码，还是只复验已有代码？ |
| 执行有没有边界 | 在哪个目录、允许改哪些文件、到什么时间必须停止？ |
| 结果能不能回查 | 实际改了什么，运行了什么，输出和失败原因在哪里？ |
| 能不能正确停下 | 失败不能伪装成成功；检查通过后仍等待人工审核 |

“只复验”可以证明已有版本接受过检查，但不能证明发生了开发。不能把运行几条检查命令写成“已由工作台调用 Codex 实现”。

A 自查完成后，请没有参与本次执行的人独立复验并记录接受决定。**没有这样的接受记录，就先停在 A，不启动 B。** 没有合适的复验者时，如实记为等待复验，不用虚构姓名补齐。

### 1.3 A 通过以后，B 才接住 L03 的说明

B 的对象换成 FlowERP 客户产品。它要关联三项东西：已经接受的 A、L03 的同一份确认版 Spec，以及本次开发允许的范围。

这时不再只是你在聊天里随口让 Codex 改程序，而是由工作台创建任务、调用 Codex、接回结果并组织检查。你仍负责范围和决定，不是把责任交给了程序。

这个从“直接监督 Codex 搭工作台”到“通过工作台组织 Codex 交付”的切换，课程叫作**自举换挡**。先理解 A 到 B 的实际变化，不必先记住这个词。

### 1.4 用实现验证 L03 的设计

L03 留下的模块关系与技术约束，需要在 B 中接受验证。执行前核对实际候选仓库是否符合调查依据；执行后沿导出入口追踪库存查询和 CSV 输出，对照 Diff 检查是否复制业务规则、绕过权限或越出允许范围。再运行正常导出与写出失败检查，核对库存和流水仍不变。

图画得合理、CSV 一次正确，都不足以证明设计得到遵守。把设计约定、实际改动和检查结果对应起来。若现有接口不能支持原方案，保留旧版和修改理由，重新确认受影响的 Spec、写集与检查，再执行；不能静默换方案，也不为整理结构扩大到全库重构。

## 2 开始 B 之前，把委托说到可以执行

“按 Spec 做一下”还不够。Codex 即使知道要导出库存，也可能进入错误目录、顺手改了无关功能，或者使用修改前的需求。

### 2.1 先认清三个位置

**控制工作区**保存你的课程规则、需求与任务记录；**独立 FlowERP 仓库**保存客户产品源码；**隔离候选**是本次准备修改、检查和交付的一份代码。候选还没有被接受，所以叫“候选”，不是已经发布的正式成果。

![图2：控制工作区组织任务，独立FlowERP仓库提供客户源码，本次修改和复验指向隔离候选](assets/reading-figures-v1/02-candidate-and-scope.png)

*读图：左侧组织任务，中间提供客户源码，右侧才是本次修改和复验对象。*

左边负责组织，中间是客户项目，右边才是 B 本次修改的地方。图中箭头说明职责关系，不表示三个文件夹互相包含。复验时也要找到右边这份候选；去检查另一份已经正确的代码，不能证明本次修改合格。

图里的“导出实现、命令入口、测试”是文件职责，不是可直接复制的授权路径。要先调查实际候选，再把具体文件逐项列出来。客户源码不要复制回控制工作区。

### 2.2 用五个问题写清本次授权

| 问题 | 库存导出委托里应写清什么 |
|---|---|
| 按哪份说明做？ | L03 已确认文件的路径与版本，不能临时换成另一份讨论稿 |
| 在哪里做？ | 工作台返回的本次候选目录，不是凭印象找一个项目文件夹 |
| 哪些文件可以改？ | 完成导出所需的具体实现、入口和测试文件，逐项说明必要性 |
| 什么时候必须停？ | 明确超时上限；需要扩大范围、改变需求或无法继续时交回处理 |
| 怎样判断结果？ | 使用哪些既定检查，检查哪些业务结果与改动范围 |

这份授权说明叫作**能力信封**；其中“允许修改的文件清单”叫作**写集**。文件夹决定在哪做，写集决定能改什么，选对目录并不意味着可以修改里面的全部文件。

> **案例｜发现需要扩大修改范围**
>
> 例如，Codex 为了方便导出，提议顺便重做采购页面。这不属于本次目标，应先停止这部分工作。如果它发现导出确实需要修改一个未授权的公共模块，也先报告原因、必要文件和影响，由你决定扩大范围还是另开任务。

清单过窄可能做不完，过宽又可能把无关修改带进去。你要判断完成本次需求真正需要哪些文件，而不是一律授权整个项目。

写在提示词里只是约定；工作台还需要在执行环境中落实相应限制，并检查实际变化。事后发现越界，也不等于事前已经防住所有越界。

## 3 执行以后，怎样知道它真正做了什么

### 3.1 “非交互执行”不等于没人负责

准备好需求、目录、权限与检查后，由工作台启动一次 Codex 调用，等待它返回结果，这就是本讲所说的**非交互执行**：不依赖你在一次聊天中逐句输入“继续”。

它不等于可以无限运行，也不等于可以替人扩大授权。超时、调用失败或出现超范围要求时，仍要保存实际情况并交回处理。

工作台负责组织这次委托；Codex 调查并修改授权范围内的文件、运行工具；实际工具结果再成为判断依据。模型写下“我修改了文件”，不等于磁盘上的文件一定已经修改。

### 3.2 执行结束，先收回四样材料

每次任务都应有编号，英文 **Task** 就是这样的执行任务。围绕这个编号，你至少要找到：

1. **使用的输入**：哪份 Spec，哪个候选目录。
2. **实际代码差异**：哪些文件新增、删除或改了哪些内容，这叫 **Diff**。
3. **运行记录**：真正执行过的命令、输出、错误与结束情况。
4. **检查结果**：按要求检查了什么，实际观察怎样，哪些仍未验证。

按明确要求判断结果的检查，在课程中叫 **Eval**。不用先把它想成另一种神秘技术；例如“东仓在库 8、预占 3，导出的可用量必须是 5”，就可以做成一项可执行检查。

程序结束时通常返回一个数字，称为**退出码**。Codex 调用返回 0，只说明这次调用按自身约定正常结束，不代表所有业务要求都已满足。还要查返回的材料，而不是看到 0 就签收。

### 3.3 用一个错误版本理解“调用正常、结果错误”

**调用正常结束与业务结果正确，是两个不同结论。**

> **案例｜文件生成了，可用量却算错了**
>
> Codex 完成调用并生成 CSV，但把东仓可用量写成 8，忘记减去预占的 3 件。
>
> 正确判断是：调用已结束、文件已生成；应为 5 的值实际为 8，业务检查失败，本次不能接受。

这是教学反例，不是实际执行记录。它说明“程序没崩溃”和“产品结果正确”是两件事。

还有一种情况：CSV 数字正确，却多改了未授权的采购页面。业务检查可能通过，但范围检查不通过，仍不能交付。看结果时既要问“做对了没有”，也要问“有没有做多”。

## 4 轮到检查库存文件：具体看什么

检查标准继续使用 L03 的确认版说明。不要让 Codex 先实现一个结果，再倒过来改需求，让结果显得正确。

### 4.1 先对一份可以手算的预期

本讲手册的正常复验用东仓 8、3 和西仓 12、4 这两组输入。西仓数字与 L03 入门故事中的 4、1 不同，是换数据检查同一条减法规则，并不是改变可用量的定义。

下面是一份**手写的预期示意**，不是已经生成的运行证据。商品名、仓位与批次只用来帮助看懂各列。

```csv
sku,name,site,location,lot_id,on_hand,reserved,available
A,示例商品,东仓,E01,L01,8,3,5
A,示例商品,西仓,W01,L01,12,4,8
```

先不用逐个背英文。八列依次是：商品编码、名称、仓库、仓位、批次、在库量、预占量、可用量。

从右边三个数开始看：第一行是 **8 − 3 = 5**，第二行是 **12 − 4 = 8**。再看中间的位置：两条库存明细各占一行，不能合成“商品 A 可用 13 件”而丢掉位置。

L03 中只是在纸上写下这种预期；L04 要真正运行导出，用实际文件与预期比较。这就是两讲的区别。

### 4.2 算对两行，还需要检查这些情况

| 再换一种输入或情况 | 应看到什么 | 它能发现什么遗漏 |
|---|---|---|
| 故意打乱库存记录顺序 | 仍依次按商品编码、仓库、仓位、批次排序 | 只照输入顺序抄出，没有落实排序要求 |
| 没有库存记录 | 只有八列表头，没有数据行 | 空结果时丢了文件格式，或根本没生成有效结果 |
| 名称含中文、逗号、引号、换行 | 用 CSV 读取器打开后，仍还原为原来的名称 | 把名称中的逗号误当成分列符 |
| 写出文件中途失败 | 明确报错，原有目标文件保持原样 | 半份新文件覆盖了旧的有效文件 |
| 原来没有目标文件，写出又失败 | 不留下可被误认成结果的半成品 | 失败以后残留不完整输出 |

CSV 读取器是按 CSV 格式解释列与文本的工具。用它验证特殊字符，比目测一行有几个逗号可靠。具体命令和课程检查脚本在手册第 6 步，这里先理解每项为什么要查。

### 4.3 别忘了回头看库存有没有被改动

导出是读取，不应改变业务账。这叫**只读性**。除了看 CSV，还要比较导出前后的库存和业务流水；流水就是入库、出库等数量变化的记录。

> **案例｜导出不能改变库存**
>
> 例如东仓导出前在库 8、预占 3，导出成功后仍应是 8、3。即使文件写到一半失败，也不能把在库量改成 5，更不能新增一笔出库流水。

因此，**文件内容正确**和**原业务数据未被改变**都要有检查依据。只看一张表格截图，证明不了后者。

## 5 检查之后，由谁决定接受，失败又回哪里

### 5.1 为什么通过检查后还要等人

![图3：调用正常结束后还要核对业务与范围，检查通过后等待同一版本的独立复验和人工决定](assets/reading-figures-v1/03-finished-versus-accepted.png)

*读图：调用结束、检查通过、人工接受，是三个不同阶段。*

第一行只说明调用结束；第二行说明检查已通过、范围符合约定，因此准备交人审；第三行才是独立复验后作决定。图里的 `review` 就是“待人工审核”，不是已经交付完成。

检查只覆盖它实际检查的要求。审核者还要核对需求来源、版本、改动与未覆盖风险，判断这些材料能否支持接受。所以自动检查通过时，工作台应停在 `review`，不能直接替人宣布完成。

### 5.2 独立复验不是再读一遍 Codex 的总结

执行者容易沿自己的思路验证。复验者要从原 Spec 出发，找到**同一份候选**，亲自查看差异、重新运行检查，再看失败后是否留下错误文件或改动业务账。

> **案例｜上午的报告不能证明下午的版本**
>
> “同一份”很重要：假设上午的版本通过了检查，下午又改了排序代码，上午报告就不能证明下午版本。需要对修改后的版本重新检查；原报告留下作为历史，不删除，也不挪来充当新证据。

复验者最后记录实际姓名、检查对象、依据和决定。可以接受，可以打回，也可以说明证据不足、暂时无法判断。没有实际复验和决定时，任务就保持待处理，不代填“已接受”。

### 5.3 先分清坏在哪里，才知道修 A 还是修 B

| 你实际发现的情况 | 应先处理什么 | 修完以后做什么 |
|---|---|---|
| CSV 可用量写成 8，应该是 5；工作台如实报告失败 | 返工 B 的导出实现 | 保留原失败，对新候选重新运行原检查 |
| 写文件失败破坏旧文件，或导出改变了库存 | 返工 B 的文件保护或只读行为 | 重验正常路径和失败后状态 |
| 明明有失败，工作台却写“通过”；或漏报越界 | 暂停 B，先修 A 的执行与检查机制 | 重新独立验收 A，再重新确认并复验 B |
| 没有有效报告，或不清楚检查了哪个版本 | 先补查执行环境、记录和版本 | 取得有效结果后再判断，不猜测业务已通过 |
| Codex 需要修改未授权文件 | 交回范围决定 | 人确认新的安排后才继续，不自行越界 |

**产品做错了，修产品；组织交付的工作台失职了，先修工作台。** 两种问题也可能同时存在，不能修好其中一个就忽略另一个。

这也解释了课程所说的 FDE 现场、交付、能力循环：从使用者要库存文件的现场问题出发，检查产品交付，发现组织方式的缺口就升级工作台，再回到产品验证。它不是额外三套流程，而是同一次工作的不同关注点。

## 6 读懂以后，怎样接到实践手册

不要一次把所有命令交给 Codex。先知道自己现在在 A 还是 B，做到本步的完成条件，再进入下一步。

| 手册位置 | 你此时正在做什么 | 进入下一步前要拿到什么 |
|---|---|---|
| 第 1～2 步 | 准备记录，调查 A 缺什么 | A 的建设要求、允许范围与检查依据 |
| 第 3 步 | 直接监督 Codex 补齐工作台 | 实际改动、自查结果与未解决问题 |
| 第 4 步 | 由非执行者复验 A | 对具体 V0 版本的真实接受记录 |
| 第 5 步 | 提交 B，实现库存导出 | B 编号、绑定的 Spec、候选目录、实际修改与执行结果 |
| 第 6 步 | 独立复验 B | 同一候选的 CSV、范围检查和失败后状态证据 |
| 第 7 步 | 接受、打回或安排返工 | 对应对象的具名决定与交接说明 |

这里的“绑定”就是保留明确关联：以后拿着 B 编号，能找到它依据哪份 Spec、使用哪版工作台、改了哪个候选。文件路径和内容指纹用来帮助辨认这些对象，具体记录方法按手册完成。

### 6.1 交接摘要不用写成长报告

下面是填写提示，不是实际结果。方括号里的内容必须来自你的本次记录。

```text
A 的状态：[哪版工作台，由谁复验，接受还是待处理]
B 的对象：[任务编号、L03 确认版、候选位置与版本]
实际修改：[哪些文件，为什么属于本次范围]
实际验证：[命令、报告、退出码、检查到的业务结果]
人的决定：[谁，依据什么，接受／打回／证据不足]
剩余风险：[哪些还没有验证，下一步由谁处理]
```

这份摘要只是材料入口，不能代替原始输出和实际文件。密钥、环境文件和运行数据库不作为提交材料；失败记录要保留。

你最后应能说明自己怎样选择范围、读懂失败、修订和复验，而不只是展示“参考仓库已经能导出”。

### 6.2 遮住正文，试着回答四个问题

1. A 的工作台已经被接受，为什么 B 还要单独检查和人审？
2. Codex 返回 0，但 CSV 可用量写成 8 而不是 5，应怎样描述结果？
3. CSV 正确，但多改了未授权文件，可以接受吗？
4. 工作台把失败伪装成通过，应先修 A 还是只重跑 B？

判断提示：A、B 的验收对象不同；调用正常不等于业务正确；范围也是验收条件；工作台失职必须先修复并重新验收。若还说不清，分别回看第 1、3、2、5 节。

接下来打开[实践操作手册](./实践操作手册.md)，从第 1 步准备自己的记录。L05 将继续追问：检查只在正确代码上通过过，怎样知道它真的能抓住错误？本讲先把一次有边界、有证据、有人作决定的交付做完整。
