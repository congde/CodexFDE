# L05｜先设计失败，再编写 Eval

同一笔收货点了两次，怎样查出有没有重复记账？先按[手册开头](实践操作手册.md#开始前先留下自己的判断)写下你会检查什么，再阅读案例。今天要做好能抓错的检查，并用原检查判断修复是否有效。

Eval 就是按说好的要求检查程序行为。幂等入库表示同一笔收货重试时只记一次；另一笔真实收货仍要正常记账。你要核对实际库存和记录，不只看“成功”提示。

| 起点 | 本讲新增 | 交给 L06 |
|---|---|---|
| 已独立接受的工作台 V0 与库存导出 | 一份业务结果 Eval、一份工程约束 Eval；两次稳定识别缺陷后冻结检查 | 幂等入库修复与原标准复验；两份检查交给 Harness 统一执行和汇总 |

开始时先按[手册开头](实践操作手册.md#开始前先留下自己的判断)保留自己的判断，再阅读教学答案。随后按这条顺序完成，不需要先浏览所有附件：

1. [辅导资料](辅导资料.md)：沿“首次 A → 重试 A → 新收货 B”理解该读哪些状态、哪些错误会被漏掉。
2. [实践操作手册](实践操作手册.md)：在缺陷副本验证检查，在独立仓库验证范围，再将本人检查放入正式候选；冻结后由工作台组织修复。
3. [SUBMISSION：个人证据索引](SUBMISSION.md)：关联两次同因失败、检查版本、真实 Diff、同标准绿灯和具名决定。

[唯一当前课件](L05-先设计失败再编写Eval.pptx)：沿用既有课堂版本。本轮未重验 PPT 内容，命令与完成标准按当前手册。

附件随手册使用：[examples](examples/) 保留脚本与 Skill，[assets](assets/README.md) 保留配图和来源。需要深入机制或历史版本时查[参考说明](reference/参考说明.md)，归档稿不构成另一条必做路线。

遇到路径、解释器或输出错误，先回手册准备与排错步骤恢复同一候选；预置支架通过和历史截图不能代替本人实现、真实宿主运行或人审。
