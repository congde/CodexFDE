# L05｜实现细节与扩展阅读

本页保留原有详细说明与操作示例，供按需查阅。首次学习先读[辅导资料](辅导资料.md)，实际执行以[实践操作手册](实践操作手册.md)为准。文中教学预期不替代个人实测。

**本讲只追问一件事：程序说“成功”时，你拿什么判断它真的做对了？**

先读本文，再按[实践操作手册](实践操作手册.md)动手。命令、完整实验记录和源码解释保留在[参考详解](参考详解.md)，不需要先全部读完。

## 1｜点了两次收货，库存应该增加几次

**重复请求是否生效，要按业务身份判断，而不是按点击次数判断。**

> **案例｜同一笔收货重试，不应重复入账**
>
> 仓库原有 20 件商品，新到 8 件。操作员点击“收货”，页面没有及时响应，于是又点了一次。货没有再来一车，库存当然应该是 **28 件，而不是 36 件**。

这叫**幂等**：同一笔业务重复请求，只产生一次业务效果。这里判断的是“同一笔业务”，不是“两个请求的数量碰巧相同”。

给这笔收货一个稳定编号 A，重试时仍用 A；后来真的又到 8 件货，就用新编号 B。这个用于识别业务身份的编号，称为**幂等键**。每次重试都换编号，会把重试伪装成新业务；只按商品和数量去重，又会误拦另一批真实收货。

![同一笔收货重试与另一笔新收货的区别](assets/reading-figures-v2/key-example.png)

*读图：沿两行数字对照：重试 A 不增加库存和流水，新业务 B 才增加。*

库存依次是 20、28、28、36；流水总数依次是 1、2、2、3。期初的 20 件也通过入库建立，所以起点已有 1 条流水。第三步重试 A，库存和流水都不能增加；第四步是新业务 B，两者都应该增加。

如果程序返回 28，却多写了一条流水，你会放行吗？不能。账面记录已经重复，返回数字正确并不代表业务状态正确。

文中的业务数字是教学示例；参考仓库记录和你自己的运行证据要分开。你确认要求与授权范围，Codex 协助实现检查和修复，工作台组织执行与复验，审核者作出是否接受的决定。L04 已经建立工作台 V0，本讲是在它上面补强判断能力，不是另建一套 ERP 门户。

## 2｜Eval 不是一个分数，而是一条可执行的要求

**Eval** 在本讲就是：把明确要求做成可以重复运行、给出证据的检查。普通测试函数也能承担这个职责，不必先接入评分模型或复杂平台。

先用人能理解的话写检查，再把它交给 Codex：

1. 建立期初 20 件，保存真实库存和流水。
2. 用 A 收货 8 件，确认库存为 28，且只新增一条正确的流水。
3. 再用 A 提交同样的收货，确认库存仍为 28，流水内容与上一步完全一致。
4. 用 B 收货 8 件，确认库存为 36，并新增属于 B 的流水。

第二步的 28 来自业务算式“20＋8”，不是读取程序结果后把它抄成答案。如果第一次操作已经错成 36，第三步只检查“重试前后相等”，错误就可能漏过去。

同样，不能只查流水条数。程序可能删掉旧流水又新增一条，条数没变，内容却错了。检查应读实际保存的状态，比较业务相关字段；页面文案和返回值只是证据的一部分。

再补一个失败输入：数量为 0 或负数。正确结果不仅是“报错”，还应是相关库存和流水没有被改动。这使检查同时覆盖正常办理和拒绝错误输入后的状态。

这些例子验证的是约定范围内的顺序调用。它们不能自动证明并发、进程崩溃恢复或“同一键但内容不同”的冲突处理都可靠；参考实现也不能据此被说成已经具备这些能力。

## 3｜为什么要故意保留一个坏版本

如果只在正确程序上运行，检查通过，你还不知道检查能不能抓错。它可能根本没读流水，也可能压根没有执行。

所以先准备一个**缺陷基线**：已知带有某个错误、可重复检查的版本。本讲课堂对照中的错误是“重试时多写流水，但仍返回正确库存”。旧检查只看返回数量，会漏报；新检查读真实流水，就应该指出具体违反了哪条要求。

这一步不急着修产品。先保持候选版本、检查标准和初始数据一致，在独立、干净的测试环境中连续运行两次。两次都应因同一业务缺陷失败，并留下类似这样的原因：

> 重试收货 A 后，库存仍为 28，但流水由 2 条变成 3 条；违反“同一笔收货只入账一次”。

这才是有用的红灯。找不到模块、数据库打不开、命令打错，也可能让程序退出失败，但并没有证明重复入账被抓住。先解决环境问题，再取得业务失败证据。

这里有两个实验入口，别混在一起：课堂对照用“旧检查绿、新检查红”说明盲点；个人课程候选的起始检查也可能本来就是红的。不要为了追求课堂现象而削弱自己的检查，也不要把讲师临时候选当作自己的最终提交。

### 把“可能错在哪里”分成四类

| 失败类型 | 本讲的具体例子 | 应观察什么 |
|---|---|---|
| 逻辑错误 | 重试 A 又入账一次 | 库存与流水是否重复改变 |
| 边界缺失 | 数量为 0 仍被接受 | 是否拒绝，拒绝后状态是否不变 |
| 规范违规 | 没有按确认的业务身份识别重试 | A 重试和 B 新业务是否被正确区分 |
| 危险修改 | 为过检查删除测试或改无关文件 | 实际改动是否越过授权范围 |

先想到这些反例，再写检查，比最后看到一个绿色数字更有解释力。

## 4｜业务做对了，也不代表这次改动可以接受

> **案例｜功能修好了，却删掉了失败测试**
>
> 假设 Codex 修好了重复流水，同时删除了一个失败测试。业务演示看起来没问题，但交付过程越界了。

因此本讲需要第二类检查：**工程约束 Eval**，检查“这次是怎样改的”。你事先确认允许改哪些文件、哪些检查必须保留；执行后核对实际差异，包括新增、删除和重命名，不能只看已跟踪文件中的几行修改。

业务结果 Eval 回答“收货对不对”；工程约束 Eval 回答“有没有按授权范围修改”。两者不能互相替代。只查范围，可能放过业务错误；只查业务，可能放过为了变绿而改标准的行为。

检查标准也要保留版本或文件指纹。修复前后运行同一条命令，不代表用了同一套断言。若真的发现检查本身有误，应说明理由、保留旧记录并重新建立基线，而不是悄悄改掉期待值。

文件指纹只是识别内容是否变化的线索，不是自动证明内容正确或获得授权的签名。

## 5｜现在才让工作台组织真正的修复

到这里，你应有两个已经证明有用的检查。下一步不是继续给检查换名字，而是把它们放进个人工作台实际使用的候选中。

先完成“建设检查”的工作：确认自己的收货检查、范围检查及其依赖已经进入后续执行的真实工作区。只在准备目录里写好文件，而工作台运行另一份候选，不算接入成功。

再确认“修复产品”的工作：冻结检查标准，给 Codex 一份范围明确的修复任务。允许它修改收货实现，但不能为消除失败而删除流水断言、替换检查或修改未授权文件。

修复完成后，仍用原检查复验，并保留：

- 修复前连续两次业务失败的记录；
- 修改前后候选的身份及实际差异；
- 修复后业务检查与工程约束检查的结果；
- 独立复验者和审核者的结论，以及尚未覆盖的风险。

如果新业务 B 也不再增加库存，说明“所有后续请求都忽略”只是另一种错误。再换一组期初和收货数量复验，例如期初 11、收货 3、重试同一笔、再收新的一笔，正确库存应为 11、14、14、17。换数据用于排除写死答案，不是换掉原验收标准。

工作台新增的是可复用的检查方式；FlowERP 获得的是重复收货不重复入账的实际修复。参考演示通过不能替代你自己的候选、差异和复验记录；自动检查通过也不替代具名人审。

## 6｜读到这里，下一步怎么做

打开[实践操作手册](实践操作手册.md)，按顺序推进：

| 去做哪一步 | 先带着什么判断去 | 这一步做完应看到什么 |
|---|---|---|
| 实践 1～3：准备与缺陷对照 | 返回 28 可能漏掉什么？ | 同一缺陷被明确定位，而非环境报错 |
| 实践 4～5：范围与检查接入 | 检查是否在真实候选里？ | 业务检查和范围检查都进入实际执行 |
| 实践 6～7：真实修复与复验 | 是产品改好了，还是标准变弱了？ | 原检查下的前后证据，以及人工结论 |
| 实践 8：排查异常 | 当前卡在环境、检查还是产品？ | 说明失败原因后再继续，不伪造通过 |

先口头回答三题，再动手：

1. A 重试后库存是 28、流水却多一条，能不能通过？——不能，业务记录重复。
2. B 是新收货但数量仍为 8，是否应该拦住？——不应该，业务身份不同。
3. 连续两次都提示模块不存在，是否完成“缺陷两次失败”？——没有，还没验证到业务要求。

需要了解旧检查源码、讲师实测、隔离候选和完整理论时，再查[参考详解](参考详解.md)。本讲的关键不是背会 Eval 的英文，而是能指出：**哪条要求、被哪个输入触发、从什么状态看出违反，以及修复后如何用原标准重验。**
