# L15｜生成交付摘要并采集真实反馈

本次实践从你自己的 L14 交付继续，完成两件事：**事项 A 根据真实反馈交付一个小改进；事项 B 在另一个需求中检索并采用 A 的经验，再独立交付。** 两次交付分别保留任务、候选、检查和人的决定。

| 任务身份 | 它证明什么 | 在哪一步使用 |
|---|---|---|
| 原 L14 Task | 原交付的事实与反馈来源 | 第 1～3 步；第 2 步摘要引用它 |
| A 的新 Task | 本次反馈修复的结果，也是个人 Memory 来源 | 第 5～7 步；第 6 步重新导出摘要 |
| B 的新 Task | 另一事项采用经验后的独立结果 | 第 8～10 步；编号不同于前两项 |

先读[辅导资料](辅导资料.md)理解为什么这样做，再按下面十步操作。个人判断和实际结果统一写入[提交模板](SUBMISSION.md)。库存空 CSV → 销售空结果只是贯穿案例；开始前要检查你的版本，已经修复的行为不能再当成新需求。

> **终端约定：**命令从 CodexFDE 控制仓库根目录开始。Windows 使用 PowerShell，macOS 使用默认 zsh，每次只运行自己系统的代码块。解释器、路径或退出码异常，先查[执行与排错说明](../../reference/实操手册执行与排错.md)；macOS 路径约定见[对应说明](../../reference/实操手册执行与排错.md#macos-zsh)。

<a id="lesson-goals"></a>

## 本讲目标与完成判断

你与 Codex 的分工是：**你确认事实、范围和采用决定；Codex 协助整理材料、受控实现与提炼经验；实际责任人复验并审核结果。** 工作台组织这些活动，FlowERP 的新结果验证反馈和经验是否有用。

| 建设对象 | 本讲应留下什么 |
|---|---|
| 工作台 | 可回查的摘要和反馈；带版本、状态、过滤、引用与采用快照的最小 Memory/RAG 练习链。 |
| FlowERP | 一项实际采纳反馈驱动、此前未实现的小改进；后一事项另有独立候选和验证结果。 |
| 学生证据 | 首次判断、原反馈、失败与修订、两次任务、检索结果、采用理由和实际复验。 |

<details>
<summary>展开课程四项合同，交付前逐项核对</summary>

- **核心内容**：文档和周报导出、运行反馈、可治理 Memory、RAG 检索与引用评测、失败样本回流，以及记忆采用和自动改代码之间的人工边界。
- **演示结果**：生成交付摘要与结构化反馈；将审核后的经验登记为记忆，在另一事项中检索，输出带引用的上下文包并解释采用决定。
- **课内增量**：实现摘要、反馈记录和最小 Memory/RAG 练习链：记忆版本与状态、元数据过滤、可解释排序、Top-k 上下文包和采用快照；不增加新的 Agent 编排。
- **通过标准**：摘要可追溯；记忆保留来源、版本、边界和状态；撤回或跨项目记忆不会默认进入上下文；检索评测与引用完整性可复验；原始反馈和检索结果都不能未经人审直接改写阻断 Eval。

</details>

## 按这一条顺序操作

| 步骤 | 在哪里做什么 | 继续前留下什么 |
|---|---|---|
| 1 | 原 L14 事项：确认任务和环境 | 原 Task、运行目录、首次判断 |
| 2 | 控制仓库：导出并抽查摘要 | 索引、摘要、一句结论的来源 |
| 3 | 使用现场与工作台：采集反馈 | 原话、解释、建议三层记录 |
| 4 | 工作台：人审并收窄范围 | 接受或拒绝决定、事项 A 的需求 |
| 5 | 检查候选与工作台：交付事项 A | 新检查的真实红灯、正式 Task 和候选 |
| 6 | A 的正式候选：独立复验 | Diff、Eval、业务结果、具名审核 |
| 7 | 个人练习目录：保存经验 | 有来源、版本、边界与状态的 Memory |
| 8 | 新事项 B 与控制仓库：检索 | 个人查询、Top-k、指标、上下文快照 |
| 9 | 工作台：决定采用并交付 B | 采用理由、不同于 A 的 Task、新复验 |
| 10 | 使用现场：回收效果 | 实际反馈、适用边界、修订或停用记录 |

**不要同时操作 A 和 B。** 先完成 A 的修复和审核，再提炼经验；B 开始时使用新需求、新用例和新任务。

## 2. 从已有任务导出一份事实摘要

<!-- step-guide-2 -->

本步先建立交付索引，再从索引导出摘要。索引汇集原任务的证据；摘要是索引创建时的快照，不能自动代表最新状态。

**在控制仓库终端输入原运行目录与原任务。** 路径使用实际绝对路径，不输入示例占位符：

**Windows：**

```powershell
$l15Runtime = Read-Host '输入已有工作台运行目录绝对路径'
$l15Task = Read-Host '输入自己的真实 Task ID'
if (-not (Test-Path -LiteralPath (Join-Path $l15Runtime 'workbench.db') -PathType Leaf)) { throw '原工作台数据库不存在，请核对 L14 运行目录，不创建空库' }
python -X utf8 -m workbench.cli task-show $l15Task --runtime-dir $l15Runtime
if ($LASTEXITCODE -ne 0) { throw '原任务未找到，请先核对原数据库和编号' }
python -X utf8 -m workbench.cli course-release-index $l15Task --runtime-dir $l15Runtime
if ($LASTEXITCODE -ne 0) { throw '索引未生成，请保留错误并核对任务编号与原运行目录' }
```

**macOS：**

```zsh
prepare_l15_index() {
  printf '输入已有工作台运行目录绝对路径（不加引号）：\n'
  read -r l15Runtime || return 1
  printf '输入自己的真实 Task ID：\n'
  read -r l15Task || return 1
  if [ ! -f "$l15Runtime/workbench.db" ]; then
    printf '原工作台数据库不存在，请核对 L14 运行目录，不创建空库。\n'
    return 1
  fi
  python -X utf8 -m workbench.cli task-show "$l15Task" --runtime-dir "$l15Runtime" || return 1
  python -X utf8 -m workbench.cli course-release-index "$l15Task" --runtime-dir "$l15Runtime"
}
prepare_l15_index
```

确认查询返回的任务、状态与原记录一致，保存生成的索引路径。已有同一任务的 `workbench.release-index/v1` 索引也可继续使用；它必须位于原运行目录。此命令不批准或发布任务，缺项会列在结果中。其他执行路径缺少课程事件时，需补接来源，不能据此判断它从未执行。

**导出到一个新文件。** `$l15Index` / `l15Index` 是刚取得的索引路径，`$l15Digest` / `l15Digest` 是尚不存在的摘要路径；运行目录沿用上一段输入。

**Windows：**

```powershell
$l15Index = Read-Host '输入刚取得的交付索引绝对路径'
$l15Digest = Read-Host '输入一个尚不存在的摘要输出文件绝对路径'
python -X utf8 docs/courses/L15/examples/export_digest.py --runtime-dir $l15Runtime --index $l15Index --out $l15Digest
$LASTEXITCODE
```

**macOS：**

```zsh
printf '输入刚取得的交付索引绝对路径（不加引号）：\n'
read -r l15Index
printf '输入一个尚不存在的摘要输出文件绝对路径（不加引号）：\n'
read -r l15Digest
python -X utf8 docs/courses/L15/examples/export_digest.py --runtime-dir "$l15Runtime" --index "$l15Index" --out "$l15Digest"
printf '导出退出码：%s\n' "$?"
```

退出 0 后打开摘要。应能看到任务、需求、状态、修改、前后检查、人审及缺口，并有证据文件路径和指纹。随机挑一句完成性结论，回到原候选和报告确认它有依据。例如原任务是 `review`，摘要就应保留待审。

**做一次输出保护实验：**使用同一输出路径再次导出，应非零退出且旧摘要不变。再在自己的临时副本中制造缺失引用或指纹不一致，输出到另一新路径；应失败，且不生成成功摘要。原始证据保持原样。

## 3. 采集一条实际反馈，保留三层记录

<!-- step-guide-3 -->

请一位同伴在你的演示环境完成一次库存、采购、销售或财务操作，先说明记录用途并取得记录许可。选择一个具体场景，写下角色、日期、版本、输入与结果；同伴试用就如实写同伴试用。没有参与者时，自己的观察写作工程观察。

在原事项下分开保存三层内容：

| 层次 | 写什么 |
|---|---|
| 原始反馈 | 实际操作、看到的结果、反馈原话及原始文件。 |
| 工程解释 | 至少两种可能原因，区分它们所需的观察，尚未确认的假设。 |
| 处置建议 | 至少两种方案，各自收益、成本和风险；推荐范围及理由。 |

沿首页已贯通的反馈入口保存后，检查后端记录是否属于原任务且为 `pending_review`。如果入口尚缺能力，将接入缺口记为本次工作台建设项；函数级练习可在隔离目录调用 `workbench.feedback.add_feedback`，显式指定数据库路径。函数只检查非空字段，任务关联与权限还需核对。

在控制仓库终端查看原库的反馈：

**Windows：**

```powershell
python -X utf8 -m workbench.cli feedback --runtime-dir $l15Runtime
```

**macOS：**

```zsh
python -X utf8 -m workbench.cli feedback --runtime-dir "$l15Runtime"
```

不要用 `python -m workbench.feedback` 向不确定的默认库写入：它默认使用当前目录的 `.runtime/workbench.db`，不接受 `--runtime-dir`。

## 4. 观察审核与晋级边界

<!-- step-guide-4 -->

把第 3 步材料交给实际责任人，决定接受、拒绝或补充调查。接受后再收窄为**事项 A 的一项小改进**：明确本次改什么、暂缓什么，以及由谁确认业务口径。审核反馈不等于批准所有实现，也不直接改变全局质量门。

在自己的隔离记录中，先预测再验证三种失败：缺少审核人、未审核反馈直接建立 Evolution 候选、已有审核结论后再次改变决定。Evolution 候选是待审核的改进资产；它仍不能直接成为阻断规则。测试角色注明为夹具，真实审核记录使用实际责任人。

下面的仓库治理用例可以辅助理解这些边界：

**两端通用：**

```text
python -X utf8 -m eval.harness --suite blocking --case raw_feedback_cannot_become_blocking
```

**继续条件：**事项 A 的范围、审核人和理由已记录；非法操作被拒绝后，原反馈、任务与阻断规则保持原状态。既有用例通过只证明它覆盖的分支，你改动的新入口仍需自己的检查。若把反馈样本晋级为 Eval 候选，先写明前提、操作、预期、反例和范围，经人审后版本化。

## 5. 通过工作台交付一个尚未实现的小改进

<!-- step-guide-5 -->

本步路线只有一条：**确认需求 → 只新增检查 → 取得真实缺口 → 保存检查提交 → 工作台受控实现。** 先将事项 A 确认版的六段需求保存为 Markdown，验收段写出本次新增 Eval 名称。`course-spec --lesson 15` 若用于生成支架，也必须传 `--eval-case`；支架不替代本人需求。

本步会切换三次位置：控制仓库准备检查候选；进入检查候选运行并冻结检查；回控制仓库提交任务。解释器始终借用控制仓库 `.venv`，避免误跑主仓库源码。

<a id="51-准备可保存提交的检查候选"></a>

### 5.1 在控制仓库准备检查候选

保存控制仓库与解释器的绝对路径，随后创建一个准备目录。准备编号用于目录隔离，正式 Task 稍后才创建。

<details>
<summary>展开准备命令：选择 Windows 或 macOS</summary>

**Windows：**

```powershell
$l15Control = (Get-Location).Path
$l15Python = (Resolve-Path '.venv/Scripts/python.exe').Path
$l15PrepId = 'TASK-PREP-L15-' + [guid]::NewGuid().ToString('N')
& $l15Python -X utf8 -m workbench.cli course-prepare --lesson 15 --task-id $l15PrepId --runtime-dir $l15Runtime
$LASTEXITCODE
```

**macOS：**

```zsh
l15Control="$PWD"
l15Python="$PWD/.venv/bin/python"
l15PrepId="TASK-PREP-L15-$("$l15Python" -c 'import uuid; print(uuid.uuid4().hex)')"
"$l15Python" -X utf8 -m workbench.cli course-prepare --lesson 15 --task-id "$l15PrepId" --runtime-dir "$l15Runtime"
printf '准备退出码：%s\n' "$?"
```

</details>

保存返回的 `path` 和基线。这里需要 `mode: git_worktree`，基于 `course/l15-start`。缺标签或准备失败时，先处理基线，保留错误再继续。

**先核对客户源码来源：**标签候选是历史课程起点，不能称为“已组合当前独立 FlowERP 源码”。确认其中业务文件符合本次需求，保存实际版本与来源；不把候选内的业务目录恢复到控制仓库。`--source working-tree` 可生成记录两仓库来源与哈希的本地快照，但它属于另一 Git 库，不能直接替代下面要求的同库会话基线。当前客户源码与标签不一致时，先解决来源和基线衔接，不能跳过检查继续交付。

### 5.2 进入检查候选，只新增验收检查

让 Codex 按已确认需求只增加实际 Eval 与必要测试，暂不实现目标能力。输入候选路径、确认版需求路径、新用例名称，再切换目录。三个变量分别回答“在哪检查、按什么需求、检查哪项行为”。

<details>
<summary>展开检查命令：选择 Windows 或 macOS</summary>

**Windows：**

```powershell
$l15CheckCandidate = (Read-Host '刚返回的检查候选 path').Trim().Trim('"')
$l15Spec = (Read-Host '本人确认版六段式需求绝对路径').Trim().Trim('"')
$l15Case = Read-Host '实际新增 Eval 名称（与 Spec 验收段一致）'
Set-Location -LiteralPath $l15CheckCandidate -ErrorAction Stop
& $l15Python -X utf8 -c "from pathlib import Path; import eval.harness; root=Path.cwd().resolve(); print(root); print(eval.harness.__file__); assert Path(eval.harness.__file__).resolve().is_relative_to(root)"
if ($LASTEXITCODE -ne 0) { throw '先处理候选源码来源，暂不运行 Eval' }
& $l15Python -X utf8 -m eval.harness --suite blocking --case delivery_evidence_and_review_controls --case raw_feedback_cannot_become_blocking --report-path .runtime/l15-start/old.json
if ($LASTEXITCODE -ne 0) { throw '既有合同未通过，先查原失败' }
& $l15Python -X utf8 -m eval.harness --suite blocking --case $l15Case --report-path .runtime/l15-start/new.json

```

```zsh
check_l15_start() {
```

记录每组报告与退出码。报告路径用于首次运行；重跑前换新路径，保留原失败。PowerShell 在命令后立即读 `$LASTEXITCODE`；zsh 立即读 `$?`，中间不要插入其他命令。

| 既有合同 | 新增检查 | 下一步 |
|---|---|---|
| 通过 | 因目标行为缺失失败 | 保存检查提交，进入实现 |
| 失败 | 任意结果 | 先恢复稳定起点，分清旧失败 |
| 通过 | 通过 | 核对是否已实现，或断言没有检查目标 |

只有“旧合同退出 0、新目标因真实缺口退出 1”支持本次起点。未知用例、导入失败、零测试或无报告先排错；原行为已正确时保留结果，重新选择真实需求，不改坏代码制造红灯。

## 7. 把一次经验登记为可治理 Memory

<!-- step-guide-7 -->

从事项 A 已修复并审核的结果中提炼一条可复用经验：它为什么成立，什么条件下能沿用，换一个业务对象需要重新确认什么。你提供事实与决定，让 Codex 按[个人记忆集格式](reference/个人记忆集格式.md)整理自己的 JSON 文件，保存在个人练习目录。

先保存为 `candidate`。实际责任人检查来源、边界和隐私后，写入真实姓名与时间，再将这版经验改为 `active`。未审核的候选保持原状态；撤回时保留条目与理由，修订时保留旧版本。

逐项打开检查：

- `memory_id` 与 `version` 是本人的经验编号和版本。
- `source.task_id` 指向第 5 步的真实修复 Task，而非原 L14 Task。
- 证据路径能打开，指纹对应实际文件；适用与不适用条件都已写清。

## 8. 换一个事项，查询自己的经验

<!-- step-guide-8 -->

回工作台首页登记新事项 B，选择与 A 不同、仍未解决的小需求。例如 A 研究库存空 CSV，B 可以研究销售空结果，但先查当前版本。记录 B 的原问题，先判断哪些个人经验有关、哪些不适用，再让 Codex 将查询与 `relevant` 编号写入个人文件的 `queries`。

至少保留一条个人查询。确无合格经验时，相关项填 `[]`；不要运行后倒填预期。教学脚本按项目与 `active` 状态过滤，再用词语重叠分数排序，取最多 k 条结果；权限和业务适用条件仍由人核对。

**回控制仓库终端。** 输入个人文件、B 的实际查询、新上下文路径。显式传入 `--fixture`；遗漏它会读取课程教学条目。

**Windows：**

```powershell
Set-Location -LiteralPath $l15Control
$l15Fixture = (Read-Host '个人记忆集绝对路径').Trim().Trim('"')
$l15Query = Read-Host '新事项的实际查询'
$l15RagOut = (Read-Host '尚不存在的上下文包绝对路径').Trim().Trim('"')
& $l15Python -X utf8 docs/courses/L15/examples/memory_rag_lab.py --fixture $l15Fixture --query $l15Query --project FlowERP --top-k 2 --out $l15RagOut
$LASTEXITCODE
```

**macOS：**

```zsh
cd "$l15Control"
printf '个人记忆集绝对路径（不加引号）：\n'
read -r l15Fixture
printf '新事项的实际查询：\n'
read -r l15Query
printf '尚不存在的上下文包绝对路径（不加引号）：\n'

```

退出 0 后打开上下文包：查询应是 B 的问题；`memory_ref` 应回到第 7 步的个人编号与版本，形如 `你的编号@v1`；`source.task_id` 应回到 A 的新修复任务。保存 `snapshot_sha256`，再次输出需使用新路径，旧快照不会被覆盖。

## 9. 让 Codex 使用上下文，但不替人采用

<!-- step-guide-9 -->

把第 8 步上下文包与 B 的 Spec 交给 Codex。要求关键建议引用 `memory_id@v版本`、说明适用条件；无支持时明确写“未找到可用记忆”。你逐项回查引用，再记录采用、拒绝或补查决定、决定人和理由。存在冲突时保留两条材料，补查后再决定。

在 B 下保存采用记录和上下文快照，确认 B 的六段需求、允许文件及验收。然后按第 5 步路线准备新检查、保留真实起点、冻结检查提交、组织受控执行。**重新输入 B 的 Spec、用例、检查候选与基线，不沿用 A 的值。** 保存新 Task，并关联此次采用的 `memory_ref`、上下文路径和指纹。

按第 6 步独立核对 B 的实际 Diff、新增 Eval、业务结果与人审。经验帮助了哪一个判断，要具体写出；比如沿用“空结果保留列名”的原则，但销售字段、权限与组织边界重新确认。

**继续条件：**B 的 Task 不同于 A，采用决定与新交付能对应。高分或命中本身不代表采用成功。复用失败时，沿查询、记忆、建议、执行和业务结果查原因；修订或撤回经验后使用新快照复验，旧采用记录保留。

## 10. 回收效果，并完成跨事项证据

<!-- step-guide-10 -->

回到原反馈者，在修复后的版本上使用相同场景与输入，重做先前受阻的操作。记录是否能完成、判断是否清晰、有无新问题，不只填写“满意”。没有真实反馈者复验时，效果确认保持待完成。

检查提交材料是否把两次交付连起来：

| 对象 | 应能回查的证据 |
|---|---|
| 来源与事项 A | 原话、审核范围、Spec、真实失败、修复 Task、Diff、独立 Eval、业务结果、人审 |
| 个人经验 | Memory 编号、版本、来源、边界、状态及审核 |
| 查询与事项 B | 个人查询与相关项、Top-k、指标、快照、引用建议、采用决定、新 Task 与新复验 |
| 实际效果 | 原反馈者观察、适用边界、剩余问题；失败时的修订或停用 |

用[页面与反馈审查 Skill](examples/skills/feedback-evidence-review/SKILL.md)辅助抽查结论。先自己预测一个反例，再记录模型真实回应、漏判与修订；文件存在不证明审查有效。完成[提交模板](SUBMISSION.md)，保留首次判断、失败、修订、复验与迁移证据。
