# L15｜生成交付摘要并采集真实反馈

用户拿到库存导出文件，说：“导出坏了。”你和 Codex 查明原因，修好了它。这次交付应该怎样说明？下次做销售导出时，又怎样借用这次经验？**本讲用这两件事，讲清从真实反馈到小修复，再从小修复到经验复用的过程。**

先阅读这份资料理解每个决定的依据，再按[实践操作手册](实践操作手册.md)动手。这里的库存与销售导出是贯穿教学案例，人物、编号和手算数据均为示意；实践要使用自己的真实任务。如果当前版本已经解决了示例问题，就选择另一项实际缺口。

![库存问题经过修复与经验审核，供销售任务检索、采用和重新验证](assets/imagegen-20260920/00-overview.png)

**读图：**上排是事项 A，完成库存问题的调查、修复和经验审核；下排从右往左是事项 B，为销售导出查找经验、决定采用范围、重新验证。最下方表示复用失败后修订或撤回经验。A 和 B 有各自的需求、任务编号与验收结果。

本讲通过工作台组织学生、反馈者、审核者与 Codex 协作，交付与采用记录按手册保存；FlowERP 接受实际的小改进，检验这些做法是否有用。本讲沿用已有执行与审核路线，新增摘要、反馈以及最小经验检索练习。

## 1. 从“导出坏了”收窄到一个能验证的问题

### 先还原使用过程

CSV 是用分隔符组织行列的文本文件。用户下载的文件没有内容，可能是查询确实没有记录，也可能是筛选条件不对、没有权限，或者导出程序没有写出列名。只凭“导出坏了”，还不能决定改哪里。

![同一句导出反馈有多种可能原因，核对后才确定改进范围](assets/imagegen-20260920/01-clarify.png)

**读图：**四个分支表示待调查的原因，黄色箭头表示证据支持后才选定的修复。右侧列名仅为结构示意，实际字段以已确认的规格为准。

案例中的调查得到以下事实：用户有权查询本组织库存，筛选后的结果确实为空；程序从第一条数据推断列名，没有第一条就生成了零字节文件。因此，问题是**合法空结果丢失了文件结构**。解决办法是按明确的字段规格写列名，不再依赖第一条记录。

沿用 L03、L04 的库存八列规格，空结果应得到下面的一行表头，数据行数为 0：

```csv
sku,name,site,location,lot_id,on_hand,reserved,available
```

这次修复还要守住三个条件：有数据时仍正确输出；无权查询时明确拒绝；导出前后的库存和账本不变。把权限失败包装成“空文件”，会掩盖另一个问题。

### 把原话、解释和决定分开

| 记录 | 本案例写什么 | 为什么分开 |
|---|---|---|
| 反馈原话 | “导出坏了”，附使用条件与原文件 | 保留使用者实际说了什么 |
| 工程解释 | 合法空查询没有第一条记录，列名生成失败 | 解释需要观察和证据支持 |
| 处理决定 | 修复空 CSV 列名，保留权限与只读规则 | 决定本次允许改什么 |

人先确认问题，再批准改进范围，最后面对修复结果决定是否接受。这是三个决定：确认反馈不能替代开发授权，检查通过不能替代具名验收。

批准范围后，把要求写进 Spec，也就是本次任务规格；从规格形成 Eval，也就是能实际运行的验收检查。新增检查应能检出“空结果没有八列”的错误，同时保留正常数据、权限拒绝和只读反例。实践手册第 5 步会把这些检查绑定到本次任务。

**判断题：**如果你当前的空 CSV 已有正确列名，还能把它作为新修复吗？不能。保留这项回归结果，再调查一个实际未解决的问题。环境报错也不能充当目标行为失败。

## 2. 修复之后，摘要怎样让接手者查得清楚

交付摘要要回答“这次实际做了什么”，每个完成性结论都能回到原任务、候选代码、检查报告和产物。

实践中先在第 2 步为原 L14 交付导出摘要，方便反馈者了解起点；第 6 步再为 A 的修复导出新摘要。两份摘要格式相同，引用的 Task 和候选各自对应，不能换一个编号后沿用旧报告。

| 摘要中的一句话 | 应能回查的依据 |
|---|---|
| 合法空库存 CSV 现在保留八列 | 本次候选生成的空结果样本与字段检查 |
| 无权查询仍被拒绝 | 同一候选的权限失败检查或真实操作记录 |
| 检查通过，等待审核 | 检查报告，以及仍待决定的任务状态 |

如果只检查了 CSV，就写 CSV 的结果；如果还没有人接受，就保留待审。接手者随机挑一句话，应能找到支持它的材料。找不到时，应补证或缩小结论。

本讲用**交付索引**列出任务、状态和证据位置，再用[摘要导出示例](examples/export_digest.py)核对引用文件，生成 Markdown。文件指纹是根据内容计算的 SHA-256，用来检查引用的字节是否变化。它能发现文件被替换，不能证明报告的业务判断正确。

导出示例读取索引创建时的快照，不查询最新服务端状态。因此交接前还要核对状态是否变化。引用丢失、越界或指纹不符时应明确失败；再次导出要用新路径，保留旧摘要。

周报是在明确的时间窗口内汇总同类事实。把已验收、待审、返工和延期分开，同一任务的重试不计成多项交付。摘要和周报都以实际记录为依据。

## 3. 把一次修复变成以后能判断是否适用的经验

### 三种材料，各有用途

库存任务正在修复、暂停待审、已经结束时，保存的材料承担不同作用：

| 材料 | 回答的问题 | 库存案例 |
|---|---|---|
| 当前上下文 | Codex 这次根据什么工作？ | 当前需求、源码、失败样本与检查 |
| 任务检查点 | 同一任务上次做到哪里？ | 候选、报告、待审位置与剩余预算 |
| 跨事项经验记忆（Memory） | 新任务能借鉴什么？ | 合法空 CSV 应保留已确认列名 |

保存到磁盘的材料不会自动全部进入 Codex 的输入。新任务先查找相关经验，再读取必要的原始证据；上下文容量有限，整段历史全部塞入会增加干扰。任务检查点帮助继续原库存任务，经验记忆帮助判断新的销售任务，两者不能互相替代。

### 经验写到什么程度才有用

“导出时加表头”没有说明何时适用。更有用的记录应包含：

| 要素 | 本案例的内容 |
|---|---|
| 身份与版本 | 自己的记忆编号及版本，例如个人编号 `@v1` |
| 来源 | 库存修复 Task、已接受候选、反馈与原始证据 |
| 结论 | 合法空 CSV 仍输出已确认的列名 |
| 适用条件 | 已获授权、查询成功、结果为空、格式为 CSV |
| 不适用条件 | 权限失败、字段未确认、其他导出格式；销售字段不能照搬库存字段 |
| 状态与审核 | 是否审核、谁审核、何时审核，当前是否有效 |

版本用于区分原建议和修订后的建议；状态用于区分“保存过”与“现在可使用”。本讲教学记忆集使用四种状态：

![记忆从待审核成为有效记录，后续可被替代或撤回](assets/imagegen-20260920/03-lifecycle.png)

**读图：**`candidate` 是待审核；核对来源、结论和边界后成为 `active`，允许默认检索；`superseded` 是被新版替代；`revoked` 是撤回，默认排除。更新保留版本，撤回保留原因和旧采用记录。

审核者要打开来源证据，判断结论是否成立，不能只填一个“通过”。如果后续发现建议误用于权限失败，应修订边界或撤回相关版本。旧采用记录仍指向当时那一版，不能通过改写历史掩盖错误。

实践第 7 步使用[个人记忆集格式](reference/个人记忆集格式.md)保存自己的经验。教学脚本不会认证审核者，也不会替你核验源文件；这些判断由学生与实际责任人完成。

## 4. 新任务怎样找到这条经验

销售导出是新的事项 B。先把问题写清楚，例如：“本组织销售查询合法但结果为空时，CSV 应保留什么结构？”然后查找可以帮助回答它的经验。

**RAG** 的做法是先检索材料，再把命中的内容和引用交给 Codex，让它据此提出建议。本讲把过程拆成三步：

1. **过滤：**先排除不允许使用的项目和状态。
2. **排序：**比较剩余材料与问题的相关程度，取前 k 条，称为 Top-k。
3. **组织输入：**保留查询、命中内容、来源、适用条件和版本，形成上下文包。

项目、版本、状态等描述材料身份的字段叫元数据。治理过滤先于排序：撤回条目即使措辞完全一致，也不应默认进入输入。权限、业务对象与时间边界还要逐项核对；本讲[标准库实验](examples/memory_rag_lab.py)只自动按项目与 `active` 状态过滤，并按词重合排序。

### 手算一次排序，理解“高分”意味着什么

脚本规范大小写、去掉空白，再把中文拆成相邻二字片段。查询“空表列名”得到 `{空表, 表列, 列名}`，共 3 个。材料按同样方法拆词，分数是“重合词数 ÷ 查询词数”。

下表是专门用于手算的小样本；打分文本代表标题、正文、适用条件和标签拼接后的内容，不是学生的真实记忆集。

| 记忆 | 项目／状态 | 打分文本 | 结果 |
|---|---|---|---|
| MEM-01 | FlowERP／active | 空表列名固定 | 3/3 = 1.0000 |
| MEM-02 | FlowERP／active | 空表保留列名 | 2/3 = 0.6667 |
| MEM-03 | FlowERP／active | 列名按权限限制 | 1/3 = 0.3333 |
| MEM-04 | FlowERP／active | 空表没有记录也应保留表头 | 1/3 = 0.3333 |
| MEM-05 | 其他项目／active | 空表列名固定 | 项目不符，排除 |
| MEM-06 | FlowERP／revoked | 空表列名固定 | 已撤回，排除 |

Top-2 返回 MEM-01、MEM-02。MEM-03 和 MEM-04 同分，脚本按记忆编号升序，同编号再按版本降序，所以 Top-3 会先加入 MEM-03。这个分数衡量措辞重合，不能保证材料真正支持答案；换一种说法，也可能漏掉相关经验。

### 怎样判断检索有没有用

运行前由人判断相关材料，不能看完排名再倒填标准。假设 MEM-01、MEM-02、MEM-04 支持当前空结果问题，MEM-03 只讨论权限字段限制，不支持这个具体结论。权限规则仍需另外检查。

两个指标分别看噪声与遗漏：**Precision@k** 是前 k 个位置中相关材料的比例；**Recall@k** 是全部相关材料中被找回的比例。本脚本的 Precision 分母固定为 k，实际不足 k 时空缺也不算命中。

| 取多少条 | 取回相关材料 | Precision@k | Recall@k |
|---|---|---|---|
| Top-2 | 01、02 | 2/2 = 1 | 2/3 ≈ 0.6667 |
| Top-3 | 01、02，另有无关的 03 | 2/3 ≈ 0.6667 | 2/3 ≈ 0.6667 |
| Top-4 | 01、02、04，另有无关的 03 | 3/4 = 0.75 | 3/3 = 1 |

取更多条找回了遗漏，也带入干扰。应该根据当前问题和输入容量选择 k，必要时改进查询与排序，再用保留的标注复验。无可用经验的问题应允许返回空结果。

这些指标只说明给定语料和查询的检索表现。教学脚本对有相关材料的查询要求 Recall 为 1，另查无答案查询与无效条目泄漏；`pass` 不能证明 Codex 的建议或产品结果正确。

## 5. 找到了经验，仍要决定具体采用什么

### 引用先回答“建议根据什么”

上下文包为每条材料保留 `memory_ref`，如 `MEM-02@v1`，同时保存来源和边界。`snapshot_sha256` 标识这次输入快照，方便回查当时交给 Codex 的材料。

Codex 提出关键建议时，要引用对应的编号与版本。你核对三件事：引用是否在本包中，内容是否对应这版材料，它是否支持旁边的具体建议。历史材料中的指令也只是被引用内容，不能给自己增加权限。

### 用一个反例检验采用边界

假设库存经验被准确检索，引用也完整，Codex 却给销售 CSV 写了库存八列。销售交付仍然错误：旧经验支持“空结果保留明确列名”，没有支持“销售和库存使用相同字段”。

![库存经验提供原则，人的采用决定确定范围，销售规格与新候选独立验证](assets/reading-depth-20261003/mechanism.svg)

**读图：**蓝色四步把旧来源、采用决定、新规格和新候选分开；红框给出照搬库存八列的错误；绿框提醒分别报告检索、引用和交付结果。[可编辑源图](assets/reading-depth-20261003/mechanism.drawio)保留完整关系。

| 可以借鉴什么 | 销售事项必须重新确认什么 | 新检查怎样发现照搬 |
|---|---|---|
| 空 CSV 保留列名 | 销售字段与顺序 | 逐列比较销售 Spec，库存八列应失败 |
| 空结果是合法结果 | 请求已获授权、查询已成功 | 无权请求必须拒绝 |
| 导出只读取数据 | 本次销售数据与业务状态 | 比较导出前后权威状态 |

命中材料互相冲突时，并列保留来源与状态，交由责任人判断；没有合格来源时继续调查，不强行生成建议。

人逐项记录采用、拒绝或补查，以及理由和允许范围。高分和完整引用是判断依据，不能替人作决定。随后由工作台组织新的受控执行，保存 B 自己的 Spec、允许修改的文件、新 Eval、候选与具名验收。A 的报告和权限不随经验传给 B。

实践第 8～9 步会保存上下文快照与采用决定，并绑定不同于 A 的后续 Task。这样才能查明：哪条经验参与了哪个新任务，帮助了什么，哪里不适用。

## 6. 复用失败后，怎样改进下一次交付

不要把所有失败都归为“记忆不好”。先看失败发生在哪里，再决定改什么：

| 实际现象 | 优先核对 | 后续动作 |
|---|---|---|
| 没找回相关经验 | 查询措辞、项目和排序 | 保留空结果，调整后重跑同一评测 |
| 撤回经验进入上下文 | 状态过滤 | 修复过滤，复验撤回与跨项目反例 |
| 引用正确却照搬旧字段 | 采用理由与适用边界 | 修订边界，用新字段反例复验 |
| 建议正确却改了范围外文件 | 本次授权与执行控制 | 打回候选，按批准范围重新执行 |
| 检查通过但用户仍受阻 | 检查是否覆盖真实使用过程 | 回到原反馈者，同条件重做并补充验收 |

保留首次失败、当时的记忆版本、上下文与采用记录，再保存修订后的版本和复验。没有实际使用者的效果确认，就写“待复验”。脚本运行成功也不能据此声称工作台首页已经贯通全部 Memory/RAG 能力；实现范围见[工作台建设规格](../../architecture/工作台范式与闭环建设.md)。

本讲完成判断可以沿一条线回查：**原反馈 → A 的修复与接受 → 有来源的记忆 → B 的查询与引用 → 人的采用决定 → B 的独立结果 → 效果回流。**只完成保存或检索时，如实声明这一层，不把它写成跨事项闭环。

**迁移任务：**换成采购 CSV，你准备沿用什么原则？哪些字段、权限和业务状态要重新确认？设计一个能检出照搬错误的反例，再按[实践操作手册](实践操作手册.md#lesson-goals)执行，用[提交模板](SUBMISSION.md)保留自己的判断与实际证据。

Memory 保存结论、依据和适用条件；流程还要说明先做什么、何时停止。**工作流蒸馏**是从真实失败、修订与验收中，提炼有参数、有前置条件、有检查出口的工程做法。

例如，把导出修复提炼为“确认字段与权限 → 按当前规格生成结构 → 检查空结果、正常数据、权限拒绝和只读 → 人审核”。每次替换字段和对象，保留职责与检查；字段未确认或需要扩大授权时停止。

流程先成为有来源和版本的候选，经独立审核，在另一事项明确采用并试用，通过真实具名验收后再决定发布。失败则修订或停用，旧采用记录仍保留原版本。Skill 可以封装这些步骤，但文件存在不证明试用有效。这里增长的是团队与工作台的工程能力，不涉及模型训练或权重更新，也不增加本讲之外的 Agent 编排必做任务。

## 课程合同与配套材料

- **核心内容**：文档和周报导出、运行反馈、可治理 Memory、RAG 检索与引用评测、失败样本回流，以及记忆采用和自动改代码之间的人工边界。
- **演示结果**：生成交付摘要与结构化反馈；将审核后的经验登记为记忆，在另一事项中检索，输出带引用的上下文包并解释采用决定。
- **课内增量**：实现摘要、反馈记录和最小 Memory/RAG 练习链：记忆版本与状态、元数据过滤、可解释排序、Top-k 上下文包和采用快照；不增加新的 Agent 编排。
- **通过标准**：摘要可追溯；记忆保留来源、版本、边界和状态；撤回或跨项目记忆不会默认进入上下文；检索评测与引用完整性可复验；原始反馈和检索结果都不能未经人审直接改写阻断 Eval。

按问题查源码、机制与历史记录时，再打开[参考说明](reference/参考说明.md)。正文四张图均为教学示意，不能作为个人运行或验收记录。
