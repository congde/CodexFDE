# FlowERP 逐讲代码基线建设方案

> 状态：建设计划，不是已经完成的课程证据。本文只定义如何建设和验收基线，不创建占位标签，不把终态仓库测试结果记作学生学习结果。

## 一、历史审计结论

截至 2026-08-24，仓库可见历史只有 7 个提交。`dad7f5f` 一次性加入 FlowERP、Workbench、Eval、Loop、Graph、API、Web 和测试等约 1.6 万行核心代码，因此现有历史不能直接映射为 16 个逐讲阶段。

历史中的旧脚本允许把全部课次标签指向同一个 HEAD。该做法只能发布同一份快照，不能证明能力逐讲形成，现已被 `course-status` 的“提交唯一性和线性祖先关系”门禁否决。

## 二、基线语义

`course/lNN-start` 表示第 NN 讲开始前的权威代码状态，不是该讲完成态：

- 已包含上一讲通过验收的产品与工作台增量；
- 已包含本讲结构完整、能够稳定失败的 Eval；
- 尚未实现本讲目标产品能力；
- 不包含后续课次才能获得的实现、页面或自动化捷径；
- 从该标签创建隔离 Worktree 后，本讲必须形成“红灯 → 真实 Diff → 绿灯”。

每讲完成态必须另有一个正常提交，下一讲的 `start` 标签只能指向在其基础上准备好下一讲红灯夹具的后继提交。不得重写已经发给学生的标签。

## 三、建设分支

新建独立的线性 `course-mainline` 历史，保留 `main` 作为终态参考实现。课程分支不从 `dad7f5f` 的全量终态直接开始，而是从最小可运行仓库开始逐讲移植能力。

```text
course/l01-start
  → L01 接手证据提交
  → course/l02-start
  → L02 规则提交
  → ...
  → course/l16-start
  → L16 现场交付提交
```

标签创建属于课程发布动作，必须在每讲红灯和上一讲绿色均由非作者复验后进行。自动化只能检查和建议命令，不能在证据不足时批量创建标签。

## 五、发布门禁

基础结构检查：

```powershell
python -X utf8 -m workbench.cli course-status --require-baselines
```

该命令检查：16 个标签齐全；每个标签可解析为提交；16 个提交互不相同；相邻课次保持线性祖先关系。每个标签发布前还必须运行 `course-baseline-audit`，在临时 Worktree 复验上一讲绿色和本讲红灯；L15/L16 改为复验静态合同绿色，并把专属红灯延后到现场会话基线。

```powershell
python -X utf8 -m workbench.cli course-baseline-audit --lesson 8 --candidate-ref COURSE-COMMIT --evidence review.md
python -X utf8 -m workbench.cli course-baseline-publish --lesson 8 --candidate-ref COURSE-COMMIT --evidence review.md --confirm
```

审核通过的隔离候选必须先 `course-candidate-export` 生成 Patch 与 SHA-256 清单，再 `course-candidate-promote` 到 HEAD 与候选基线一致的干净目标工作区。提升动作只应用 Patch，不代替人工复查和提交；完成导出或失败/死信任务才允许 `course-worktree-clean`。

只有以下证据齐全才可发布某讲：起始标签提交、执行前报告、隔离 Worktree 身份、Codex 原始执行证据、范围内 Diff、执行后报告、具名复核和剩余风险。
