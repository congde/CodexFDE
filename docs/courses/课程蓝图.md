# 课程蓝图｜Codex AI 工程交付行动营

**用 Codex，搭建个人 AI 研发工作台；通过工作台组织人与 AI 协同，持续开发 FlowERP。**

这份蓝图用于把握教学顺序和每讲落点。16 讲标题以[课表](../课表｜Codex%20AI%20工程交付行动营.md)为准，完整内容与通过标准以[课程大纲](../课程大纲-Codex-FDE行动营-个人研发自动化工作台.md)为准；操作步骤从[学生总入口](../README.md)进入。

## 学完要能做什么

收到一个真实需求，能与 Codex 一起把它说清楚、做出来、检查结果，并决定接受还是返工。交付过程中，学生负责范围、授权和验收，Codex 协助调查、实现和修复，工作台保存任务、执行结果和人的决定。

最终交付两项相互配合的成果：

- **个人研发工作台**：接收需求，组织执行与检查，遇到失败能返工或停下，留下可追溯记录。
- **FlowERP 客户产品**：逐步具备库存、销售订单、采购和操作页面；每次新增功能或修复，都用来检验工作台是否有效。

最后一讲从干净环境启动系统，现场完成一个此前未实现的小需求，说明依据、失败处理和剩余风险。

## 四阶段怎样接起来

| 阶段 | 要解决的问题 | 工作台形成的能力 | FlowERP 的变化 |
|---|---|---|---|
| L01～L04：完成第一次交付 | 怎么把一句话变成范围清楚、结果可验的任务？ | 任务与证据记录、仓库规则、需求规格、受控执行，形成 V0 | L01～L03 不接入；L04 首次交付库存导出 |
| L05～L08：让检查可信 | 程序能运行，为什么仍可能交付错误？ | 设计反例，统一检查结论，在本地和远程自动复验 | 幂等入库、统一可用库存、订单创建、原子预占 |
| L09～L12：让返工与协作可控 | 失败后改哪里、改几轮、交给谁、谁批准？ | 生成修复任务，限制返工轮数，拆分独立任务，保存审核状态 | 取消释放库存、合法状态迁移、采购申请、审批后入库 |
| L13～L16：交给别人使用 | 离开作者的会话和电脑，还能继续交付吗？ | 任务接口、操作页面、反馈与经验复用、冷启动 | 补货交付、ERP 操作页、真实反馈改进、现场新需求 |

**关键转折在 L04。** L01～L03 由学生直接监督 Codex 建工作台；L04 先验收工作台 V0，再用它组织第一次 ERP 交付。此后每讲都从 ERP 的具体问题出发，补充工作台能力，再用产品结果检验这项能力。

工作台建设与客户交付分别保留证据：业务人员说明问题，学生与 Codex 完成范围内的实现，独立复验者核对候选、报告与业务结果。反馈回到后续事项，经确认和复验后才能成为可复用规则；教学人物的对话不能代替学生本人的学习记录。

这也是 FDE（Forward-Deployed Engineering）在本课中的用法：到现场弄清问题，完成一次交付，把反复需要的方法留下供下一次使用。

### 三个容易误读的地方

**同一个概念再次出现，不等于重新开始。** L01 手工写一次 Spec，L03 提炼模板并接入解析器；L04 使用最小检查完成交付，L05 验证检查能否抓错，L06 组织多项检查，L07 与 L08 分别解决触发和远程复验。L04 已经有人审，L12 才把等待、打回与恢复完整写成状态规则。

**产品能力持续积累，实验数据不持续累加。** 每讲的 20、8、10 等数字属于独立测试条件，不是同一数据库连续经营后的余额。隔离候选和故意缺陷用于形成可复现的学习起点，不能覆盖已接受的产品。参考快照里提前存在的业务能力只作为支架，不算学生已经完成后续讲次。

**复用必须落实到实际入口。** 同样叫 Harness，不代表加载同一份代码；通过了上一讲，也不代表新候选自动拥有原检查。按各讲手册记录来源、复制或登记原检查，运行后对照真实用例名。L06 到 L07 的具体操作见[检查接入手册](L07/L06检查接入手册.md)。

## 第一阶段：先完成一次受控交付

### L01｜以终为始：一次可验证的 AI 交付怎样完成？

从“帮我搭建个人 AI 研发工作台”开始。Codex 追问需求，学生取舍并签署首份 Spec（需求与验收约定），再把验收项变成测试、实现 Workbench V0.1。工作台能初始化、登记项目、记录任务和命令证据、检查状态，最后记录自身的建设过程。本讲不接入 FlowERP。

**验收重点**：需求能回指原始痛点和学生决定；同一测试实现前失败、实现后通过；修改在约定范围内。学生能解释为什么只有最终绿灯还不足以签收。对应 CLO-1（边界与责任判断）。[实践手册](L01/实践操作手册.md)

### L02｜把仓库规则写进 `AGENTS.md`

一次会话说清的禁区，换个会话可能被忘记。学生把目录边界、禁止事项、验证命令和完成标准写进仓库规则，让 Codex 在新会话分别处理危险请求与合法请求。FlowERP 尚未接入，先固化库存、订单与审批规则。

**验收重点**：保存两类请求的真实响应；越界请求被拒绝或纠正，合法任务仍能推进。学生用一条新请求说明该执行、追问还是拒绝。对应 CLO-1。[实践手册](L02/实践操作手册.md)

### L03｜把模糊需求变成可验收 Spec

“增加导出功能”没有说明导出什么、按什么口径、怎样算完成。学生与 Codex 澄清库存导出需求，确定目标、非目标、约束、验收用例与来源；实现 Spec 模板和最小解析器。本讲只确定合同，不修改 ERP 业务。

**验收重点**：完整 Spec 能被解析，缺失必要字段有明确错误；保留初稿、同伴指出的歧义与修订稿。学生能判断一个新要求是否超出范围。对应 CLO-2（定义需求与最小变更）。[实践手册](L03/实践操作手册.md)

### L04｜委托 Codex 执行一次最小变更

合同已明确，还需要控制 Codex 在哪里执行、能改哪些文件、怎样验证。学生先补齐并独立验收工作台 V0 的执行入口、修改范围检查、最小 Eval（可重复运行的验收检查）和结果摘要，再由 V0 调用 Codex 交付库存导出。

**验收重点**：分别保留 V0 验收与库存导出交付记录；检查实现前失败、范围内 Diff（文件修改差异）、独立复验通过。摘要列出修改文件、验证命令和剩余风险，仓库无密钥和环境文件。学生据此作出接受或退回决定。对应 CLO-2。[实践手册](L04/实践操作手册.md)

## 第二阶段：让质量检查能发现真实错误

### L05｜先设计失败，再编写 Eval

一次收货重试可能重复增加库存。学生先设计重复入库反例和工程约束检查，确认缺陷版本连续两次失败，再让 Codex 修复；同一入库幂等键应只生效一次。

**验收重点**：修复前稳定失败，修复后同一命令通过；检查库存实际变化和失败后的状态。学生能说明检查为什么能识别重复入账。对应 CLO-3（建立可信质量证据）。[实践手册](L05/实践操作手册.md)

### L06｜用 Harness 汇总证据和等级

库存查询与导出使用不同的可用库存口径，分散的检查又无法给出统一结论。学生让 Codex 协助统一口径，并建设 Harness——统一执行 Eval、汇总报告和给出是否放行结论的入口。

**验收重点**：阻断项失败返回非零退出码，观察项失败只告警；JSON 报告保留运行时间和失败原因，报告与退出码一致。学生用一份假绿报告解释哪里应阻断。对应 CLO-3。[实践手册](L06/实践操作手册.md)

### L07｜用 Codex Hooks 建立本地护栏

交付销售订单创建时，质量检查容易被忘记。学生选择合适的执行节点，配置 Hook（在指定节点触发的动作）调用已有 Harness；Codex 协助实现订单功能与接入检查。

**验收重点**：Hook 来源可查；违规时阻断，修复后通过；同时验证订单正常路径、失败路径及失败后数据。学生解释为什么选这个触发点，以及它与 Git Hook 的区别。对应 CLO-3。[实践手册](L07/实践操作手册.md)

### L08｜把同一套 Eval 接入 CI

订单多项商品预占必须整单成功或整单失败。本机绿灯还需要由远程 CI（自动复验流水线）检查同一候选版本。学生组织 Codex 完成原子预占与 CI 接入，由同伴核对代码版本、检查入口和报告来源。

**验收重点**：本地与 CI 使用同一入口；展示假绿、可信失败、修复后可信通过，非零退出码能阻断候选变更；失败不留下部分预占。学生独立识别一次版本或报告错配，合并由人决定。对应 CLO-3。[实践手册](L08/实践操作手册.md)

## 第三阶段：控制返工、分工与审核

### L09｜把失败报告翻译成修复任务

取消订单后，预占库存没有释放。学生从失败报告中提取复现步骤、允许修改范围、目标状态与验收命令，形成修复任务，再交给 Codex 执行；工作台增加报告到修复任务的映射。

**验收重点**：修复后取消能释放库存，任务可回指原报告；观察级告警不会自动变成阻断任务。学生能删去修复任务中夹带的无关重构。对应 CLO-4（控制修复与停止）。[实践手册](L09/实践操作手册.md)

### L10｜建立有停止条件的修复 Loop

订单状态迁移仍有错误，反复让 Codex“再改一次”可能没有进展。学生把执行、检查、生成修复任务串成 Loop（修复循环），设置最多三轮、达标即停、无进展或预算耗尽退出。

**验收重点**：展示一次收敛和一次未收敛记录；订单只按合法路径迁移，停止时如实列出剩余失败。学生面对新的运行记录，判断应继续还是交回人处理。对应 CLO-4。[实践手册](L10/实践操作手册.md)

### L11｜用 Codex 原生 Subagents 并行处理独立任务

交付采购申请时，测试补全与风险审查可以分工，但先要确认读写范围没有冲突。学生定义两个子任务的输入、输出和验收标准，主 Agent 汇总原始结果，再复验集成后的产品。

**验收重点**：采购申请可运行；保留任务身份、并行活动与原始子报告，每个结论可追溯。学生判断一组新任务能否并行，有文件写入冲突时改为顺序执行。对应 CLO-5（分工与人工审核）。[实践手册](L11/实践操作手册.md)

### L12｜用 Graph 显式表达状态、回退和人工审核

采购申请通过检查，不代表已获得入库批准。学生用 Graph（明确记录步骤和转换条件的状态图）组织开发、测试、审核、打回和恢复；Codex 协助实现流程，具名人员承担批准责任。

**验收重点**：未经批准不能入库；质量审核依据 Eval，采购批准能定位责任人；状态可保存、恢复，异常可见，循环有上限。学生说明匿名批准或中断时应停在哪里、哪些数据不能变化。对应 CLO-5。[实践手册](L12/实践操作手册.md)

## 第四阶段：让系统可使用、可接手、可改进

### L13｜把执行链路封装成任务 API

补货交付不能依赖某个人一直守着终端。学生与 Codex 把执行链封装为任务 API（供其他程序调用的接口），提供提交和查询两个入口；提交后取得任务 ID，并用它追踪补货交付。

**验收重点**：状态转换合法，失败原因可查，已完成任务在服务重启后仍可读取；核对任务状态与 ERP 结果。学生解释“请求已接收”为什么尚不能证明交付成功。对应 CLO-6（运行、交付与改进系统）。[实践手册](L13/实践操作手册.md)

### L14｜让交付状态在 Web 面板可见

接口可调用之后，还要让使用者知道任务进行到哪、失败后怎么办。学生组织 Codex 完成工作台最小任务面板，并交付覆盖进货、销售、库存与财务入口的 FlowERP 操作页。研发事项从工作台首页“事项与决策”进入，业务操作在客户产品中完成。

**验收重点**：实际走通提交、查看状态、检查报告与获取产物；页面、接口、持久化记录和 ERP 结果一致，失败可追踪，前端与仓库无密钥。学生发现旧绿灯时能指出应补查的记录。对应 CLO-6。[实践手册](L14/实践操作手册.md)

### L15｜生成交付摘要并采集真实反馈

使用者提出反馈后，学生先澄清问题、确定取舍，再与 Codex 交付一项进销存或财务小改进。工作台生成摘要并记录反馈；经审核的经验保存为带来源、版本、适用边界和状态的记忆，再在另一事项中检索，形成带引用的上下文包。这是本课的最小 RAG 练习：先检索相关资料，再提供给 AI 使用。

**验收重点**：反馈能追踪到需求、修改与产品结果；检索包含元数据过滤、可解释排序、Top-k 结果和采用快照，检索质量与引用完整性可复验。学生决定是否采用，撤回或跨项目记忆不能默认进入上下文，反馈和检索结果不能未经人审改写阻断 Eval。对应 CLO-6。[实践手册](L15/实践操作手册.md)

### L16｜在新环境接手，并完成现场新需求

由另一位同学按文档从干净环境启动系统，再现场提出一个此前未实现、范围受控的 ERP 小需求。学生通过工作台组织 Codex 完成澄清、实现、复验与审核，并准备结业检查表和五分钟答辩。

**验收重点**：展示成功任务、失败打回、结果导出与反馈写入；保留新需求本次的失败、修改、通过与具名验收记录。学生独立定位证据，解释一项剩余风险和一种停止条件。对应 CLO-1～6。[实践手册](L16/实践操作手册.md)

## 阅读材料与用词约定

本组材料面向能使用终端和编辑器、但不要求已有 AI 工程交付经验的读者。开始前先完成 [L00 环境准备](L00/L00｜课前准备：装好工具，跑通第一次环境自检.md)。正文解释为什么这样做，操作手册给出命令与排错，提交模板帮助整理自己的判断与结果；选读资料用于查细节。

先读辅导资料的业务问题与判断，再按实践手册执行，在提交模板记录自己的结果。正文中的图帮助理解因果，源码、旧实验和字段细节按需查询。课堂推演、参考仓库的运行和个人完成记录分别标注。

进入下一讲前，先核对当前交接成果。若缺少真实运行或人审，就保留待办，不能因为教材写着“上一讲已经完成”而把个人状态填成已完成。

正文图号采用“讲次－本讲顺序”，例如图 6-2 表示 L06 的第二张图。教学示意中的勾选、数据和人物决定用于说明规则，参考界面用于说明形态；它们都不是读者本人的完成记录。

### 容易混淆的用词，读到时再查

| 用词 | 本组材料中的含义 | 不能据此推出什么 |
|---|---|---|
| Spec（需求说明） | 本次任务的目标、范围与验收要求 | 写好说明不等于功能已实现 |
| Eval（检查） | 将实际行为与确认的要求比较 | 一项通过不代表全部业务正确 |
| Eval Harness（检查运行器） | 组织检查、保存结果并汇总判决 | 不等于整个研发工作台已闭环 |
| 候选版本 | 本次修改、复验和审核所针对的代码 | 仅有目录名不代表代码内容未变 |
| 复验 | 依据同一要求再次运行检查并核对结果 | 复验通过不自动代替人的接受决定 |
| 交付审核 | 审核人决定软件候选能否接受 | 不等于批准一张采购单 |
| 采购批准 | 业务负责人允许指定采购单继续执行 | 不代表货物已收到或库存已增加 |
| 参考实验 | 用课程提供的输入或缺陷观察机制 | 不等于已在个人候选中实现该能力 |

代码、字段和正式课题保留原名；中文解释以这里的含义为准。数字推演先读清起始库存、预占和目标订单，再计算操作后的变化。后续章节换数据时，重新建立测试条件。

## 每讲怎样组织学习和验收

入课前用 L00 补齐五项操作：找到文件和当前目录、区分对话与终端命令、运行命令、保存真实输出、查看文件修改差异。零基础学员提供示范和逐级提示，有经验学员减少提示、增加迁移题；交付标准相同。

每讲沿用一条学习顺序：

1. **教师示范**：用一个具体问题解释必要概念，展示在哪里操作、预期结果和失败后的处理。线上精讲不超过 30 分钟，页数和分段按内容安排。
2. **学生尝试**：先留下自己的范围判断或结果预测，再请 Codex 协助实现。行动课完成正常路径、失败路径和失败后状态检查。
3. **同伴复验**：对照同一版本检查结果，保留失败、修订前后版本与反馈。详细命令、排错与提交要求通过任务卡交接。
4. **独立检查**：换一个条件或小需求，学生不让 AI 代答，说明应执行、返工还是停止，以及判断依据。

教师分别记录两项结果：**工程是否通过**，看真实输入、预期与实际结果、退出码或权威状态、任务身份和修改版本；**学生是否掌握**，看能否独立解释与迁移，按“可独立／需提示／尚未达成”记录。参考仓库的绿灯不能替代学生的学习证据。

工作台的长期建设还包括把成功和失败提炼成可复用流程。跨事项复用须记录：召回了哪条经验、采用哪个流程版本、执行与人审结果，以及复用失败后的修订或停用；具体建设范围见[工作台范式与闭环建设](../architecture/工作台范式与闭环建设.md)。

## 备课与试讲如何使用这份蓝图

备课时按“本讲问题 → 工作台增量 → ERP 结果 → 学生独立判断”检查讲义、实践和课件，完整验收项回查课程大纲。库存不为负、入库幂等、订单合法迁移、采购人工审批、失败如实记录，贯穿所有练习。

先试讲 L01、L05、L14，记录完成时间、卡点、提示次数、首次与二次提交变化和独立检查结果。操作卡住就补示范，能运行却解释不了就补结果对照，无法迁移就增加等价小任务；后续课程再复查是否掌握。
