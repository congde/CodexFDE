# 课程蓝图｜Codex AI 工程交付行动营教师备课

**用 Codex，搭建个人 AI 研发工作台；通过工作台组织人与 AI 协同，持续开发 FlowERP。**

这份蓝图供教师备课、试讲和改进教学使用。16 讲正式标题以[课表](../课表｜Codex%20AI%20工程交付行动营.md)的“主题”列为准；学习目标、核心内容、演示结果、课内增量和通过标准回查[课程大纲](../课程大纲-Codex-FDE行动营-个人研发自动化工作台.md)。本文说明怎样把合同转成教学活动与评价，不另写一套逐讲合同。学生学习路线、逐讲材料和操作入口统一在[学生总入口](../README.md)。

## 学完要能做什么

备课先确定学生最终要独立完成的行为，再选择示范、练习与证据。核心行为是：收到真实需求，能与 Codex 一起把它说清楚、做出来、检查结果，并决定接受、返工或停止。学生负责范围、授权和验收，Codex 协助调查、实现和修复，工作台保存任务、执行结果和人的决定。

最终两项成果要同时用于评价：

- **个人研发工作台**：接收需求，组织执行与检查，遇到失败能返工或停下，留下可追溯记录。
- **FlowERP 客户产品**：逐步具备库存、销售订单、采购和操作页面；每次新增功能或修复，都用来检验工作台是否有效。

评价应检查学生是否能用自己建设的工作台交付客户需求，并在条件改变后继续判断。具体 CLO（课程学习目标）和逐讲要求以大纲为准，课程目标与专业毕业要求的正式对应关系由开课学校确认。

## 四阶段怎样接起来

四阶段的递进来自学生在交付中遇到的困难。教师先让学生看见困难，再引入能处理它的机制，避免先罗列工具、后补一个业务案例。

L00 先完成环境核验，课程已提供 `starter/` 项目壳，学生可按 L01 手册将它生成到空的个人目录。建议另建新工作台项目，参考选做从 0 搭建：与 Codex 确认架构 → 分步实现 → 本人复验 → 同目录 L01。两种起点都采用与参考项目对应的目录、根入口和设计文件位置，区分已有、后续预留与可选扩展。教师观察学生能否核对实际源码和解释器、说明模块分工并处理失败；现成壳或壳测试通过不能替代 L01 本人 Spec、红灯测试、实现、复验与自举。

| 阶段 | 教学上为什么接着做 | 教师要观察的判断变化 |
|---|---|---|
| L01～L04：完成第一次交付 | 先形成要求与记录，才有依据限制执行和接受结果 | 从“AI 写完了”转为核对要求、范围、同一候选和复验 |
| L05～L08：让检查可信 | 一次成功仍会漏错，已有检查还可能漏跑或检查错版本 | 从看绿灯转为主动设计反例，辨认检查与报告是否可信 |
| L09～L12：让返工与协作可控 | 有了可信失败，才谈得上压缩修复范围、限制轮次和分配责任 | 从要求“再改一次”转为判断改哪里、是否继续、能否并行和谁审核 |
| L13～L16：交给别人使用 | 受控流程还要经受查询、中断、真实反馈和陌生环境的检验 | 从依赖作者讲解转为由他人定位状态、恢复任务并独立完成新需求 |

**关键转折在 L04。** L01～L03 由学生直接监督 Codex 建工作台；L04 先验收工作台 V0，再用它组织第一次 ERP 交付。此后每讲都从 ERP 的具体问题出发，补充工作台能力，再用产品结果检验这项能力。

每次引入工作台能力，要明确它由哪次交付困难触发，又在哪次 ERP 交付中接受验证。若学生只解释了工具用法，没有指出它如何改变交付判断，教师应补充前后结果对照。

备课时先用一句具体问题串起本讲，再选择必要概念和示范。一个机制在首次出现的讲次讲清原理；后续讲从已经形成的能力出发，用新输入、反例或协作困难说明为什么还要改进。讲义解释判断依据，手册给执行位置、命令、结果与排错，提交模板关联本人材料。跨讲回查用直接链接，保留当讲独立完成所需的信息。

这也是 FDE（Forward-Deployed Engineering）在本课中的用法：到现场弄清问题，完成一次交付，把反复需要的方法留下供下一次使用。

## L01～L12 的连续学习路线

学生路线和 L01～L16 的逐讲材料已集中到[学生总入口](../README.md)。本节保留旧链接位置，备课时按上面的教学递进检查衔接。

### 三个容易误读的地方

**同一个概念再次出现，不等于重新开始。** L01 手工写一次 Spec，L03 提炼模板并接入解析器；L04 使用最小检查完成交付，L05 验证检查能否抓错，L06 组织多项检查，L07 与 L08 分别解决触发和远程复验。L04 已经有人审，L12 才把等待、打回与恢复完整写成状态规则。

**产品能力持续积累，实验数据不持续累加。** 每讲的 20、8、10 等数字属于独立测试条件，不是同一数据库连续经营后的余额。隔离候选和故意缺陷用于形成可复现的学习起点，不能覆盖已接受的产品。参考快照里提前存在的业务能力只作为支架，不算学生已经完成后续讲次。

**复用必须落实到实际入口。** 同样叫 Harness，不代表加载同一份代码；通过了上一讲，也不代表新候选自动拥有原检查。按各讲手册记录来源、复制或登记原检查，运行后对照真实用例名。L06 到 L07 的具体操作见[检查接入手册](L07/实践操作手册.md#l07-connect)。

## 目标、活动与评价怎样对应

备课从大纲选择本讲 CLO，并把其中一个可观察行为落到学生要作出的决定。活动应让这项决定实际发生，评价再检查决定的依据。不能只把“掌握某工具”写进目标，然后用是否运行过命令打分。

| 要培养的行为 | 学生参与的活动 | 教师核对的直接证据 |
|---|---|---|
| CLO-1：判断范围与责任 | 先写自己的初始判断，再比较合法请求、越界请求和替代方案 | 学生决定、规则来源、修订前后理由 |
| CLO-2：把要求变成可验收约定 | 与 Codex 澄清需求，同伴指出歧义，学生修订 Spec | 初稿、歧义标注、确认稿与对应验收项 |
| CLO-3：判断检查能否发现错误 | 预测反例结果，运行正常路径和失败路径，核对失败后状态 | 同一候选的输入、预期、实际结果、退出码与业务状态 |
| CLO-4：控制修复与停止 | 从可信失败中选择最小修复，判断继续、停止或交回人处理 | 允许范围、轮次、剩余失败与停止依据 |
| CLO-5：组织分工与人工审核 | 判断任务独立性，处理冲突，组织具名审核与打回 | 原始子报告、集成复验、状态转换与具名决定 |
| CLO-6：运行、交付与改进系统 | 在新环境换一个条件或小需求，由学生选择检查和交付判断 | 本次新输入、实际执行、独立说明与剩余风险 |

例如讲重复入库时，先让学生预测同一幂等键再次提交后库存是否变化，再运行缺陷版本；修复后仍用原要求复验，并增加“拒绝所有入库也会避免重复”的反例。教师据此判断学生是否理解检查辨识力。最终绿灯证明本次检查通过，学生能设计新反例并解释结果，才支持学习达成判断。

## 阅读材料与用词约定

材料面向先修能力不一致的学生，教师先用 L00 和首次实践辨认环境、命令行与判断能力的缺口。学生准备和阅读顺序见[学生总入口](../README.md)，教师按需要提供示范与逐级提示。

辅导资料负责解释问题、机制和判断；实践手册统一目标、起点、操作、提示词、输出、排错和完成判断；提交模板引用个人判断与原始证据；PPT 服务课堂示范。制作时保持同一版本、起点、案例、对象名称、操作链和验收标准，课外细节按需提供，不要求学生预先遍历所有附件。

材料写到“上一讲已经完成”时，教师仍须核对学生的实际交接成果；缺少真实运行或人审，就保留待办并安排补做。参考实现作为支架时，应标明学生还要实现和判断的部分。

正文图号采用“讲次－本讲顺序”，例如图 6-2 表示 L06 的第二张图。机制图要服务一个明确问题，与正文使用相同对象和数值，图下说明怎样读以及能得出什么结论；需要维护的图保留可编辑源图。教学示意、参考界面、真实运行与学生个人记录分别标注来源，图中的勾选、数据和虚构人物决定不能充当学生完成记录。

### 容易混淆的用词，读到时再查

教师在术语首次出现时给出下面的含义，并用当前案例解释；不要靠附录或堆叠名词补足正文的因果关系。

| 用词 | 本组材料中的含义 | 不能据此推出什么 |
|---|---|---|
| Spec（需求说明） | 本次任务的目标、范围与验收要求 | 写好说明不等于功能已实现 |
| Eval（检查） | 将实际行为与确认的要求比较 | 一项通过不代表全部业务正确 |
| Eval Harness（检查运行器） | 组织检查、保存结果并汇总判决 | 不等于整个研发工作台已闭环 |
| 候选版本 | 本次修改、复验和审核所针对的代码 | 仅有目录名不代表代码内容未变 |
| 复验 | 依据同一要求再次运行检查并核对结果 | 复验通过不自动代替人的接受决定 |
| 交付审核 | 审核人决定软件候选能否接受 | 不等于批准一张采购单 |
| 采购批准 | 业务负责人允许指定采购单继续执行 | 不代表货物已收到或库存已增加 |
| 参考实验 | 用课程提供的输入或缺陷观察机制 | 不等于已在个人候选中实现该能力 |

代码、字段和正式课题保留原名；中文解释以这里的含义为准。数字推演先读清起始库存、预占和目标订单，再计算操作后的变化。后续章节换数据时，重新建立测试条件。

## 每讲怎样组织学习和验收

入课前用 L00 补齐五项操作：找到文件和当前目录、区分对话与终端命令、运行命令、保存真实输出、查看文件修改差异。环境就绪后，学生可使用课程提供的页面壳；从 0 搭建作为参考选做，建议在新项目中与 Codex 确认架构和允许写集、分步实现，亲自核对首页、健康信息、失败提示和重启，保留首次判断、修改与修订。L01 在选定的同一个人项目中建设五个账本操作，保留本人需求与红绿证据。零基础学员提供示范和逐级提示，有经验学员减少提示、增加迁移题；L01～L16 的交付标准相同。

每讲沿用一条学习顺序：

1. **教师示范**：用一个具体问题解释必要概念，展示操作位置、预期结果、失败处理与完成判断。线上精讲原则上不超过 30 分钟，页数和分段按内容安排。
2. **学生尝试**：先留下自己的范围判断或结果预测，再请 Codex 协助实现。行动课完成正常路径、失败路径和失败后状态检查。
3. **同伴复验**：对照同一版本检查结果，保留失败、修订前后版本与反馈。按本讲实践手册执行详细命令与排错，用同讲 SUBMISSION.md 引用原始证据；同伴提出反证，学生据证据修订判断。
4. **独立检查**：换一个条件或小需求，学生不让 AI 代答，说明应执行、返工还是停止，以及判断依据。

教师分别记录两项结果：**工程是否通过**，看真实输入、预期与实际结果、退出码或权威状态、任务身份和修改版本；**学生是否掌握**，看能否独立解释与迁移，按“可独立／需提示／尚未达成”记录。参考仓库的绿灯不能替代学生的学习证据。

工作台的长期建设还包括把成功和失败提炼成可复用流程。跨事项复用须记录：召回了哪条经验、采用哪个流程版本、执行与人审结果，以及复用失败后的修订或停用；具体建设范围见[工作台范式与闭环建设](../architecture/工作台范式与闭环建设.md)。

## 双仓库与真实证据边界

工作台和课程材料位于 CodexFDE，客户业务代码、页面、数据库和业务测试位于 [FlowERP 独立仓库](https://github.com/congde/flowERP.git)。示范必须说明命令运行在哪个项目、使用哪个虚拟环境与数据目录。工作台 Eval 与 ERP 业务 Eval 分别验证，两者都通过仍需具名人审。L04 起组合源码形成课程快照时，记录各文件来源与哈希，不在本仓库恢复重复业务目录，也不把历史标签说成当前双仓库验证结果。

每次评价核对输入、预期、实际结果、退出码或权威状态、任务身份和修改版本。前后比较必须围绕同一要求；自然语言规则实验若改前已经正确，应如实保留结果，不能制造失败来证明改进。工作台建设证据、客户产品证据和学生学习证据相互引用，单项通过不替代另一项达成。

课程机器检查、事件持久化、单次反馈登记和教学人物故事不能证明跨事项闭环或真实学习效果。后端能力与首页已贯通的交互分别说明，建设计划按计划标注。

## 本地课件检查

课堂 PPT 不随 Git 发布，获取与存放方式见[学生总入口](../README.md)。各讲根目录与 README 保留一个当前课堂入口，旧课件放在 `reference/archive/slides/`。维护者记录讲次、文件名、版本与来源；版本整理不等于内容验收，操作和完成标准仍须与当前手册逐项核对。

通用生成器使用旧的公共课件输出目录时，新生成文件进入本讲 `reference/archive/slides/generated/`。完成内容与渲染核验后，由维护者选定当前课件并同步本讲 README；显式指定其他输出目录时沿用该目录。

默认 Git/CI 检查课程合同、已发布资源链接和教学设计；两项依赖本地 PPT 的检查默认跳过。跳过不等于通过。具备完整本地课件时，在仓库根目录单独执行：

```powershell
$env:CODEXFDE_VALIDATE_LOCAL_SLIDES = "1"
.\.venv\Scripts\python.exe -X utf8 -m unittest tests.test_course_pptx tests.test_course_ppt_endings -v
Remove-Item Env:CODEXFDE_VALIDATE_LOCAL_SLIDES
```

报告注明实际检查的文件、版本、命令与结果。结构、结束页检查不能替代逐页渲染与内容审核；逐页核对正文、图表、操作步骤和验收要求是否一致。固定 22 页是早期安排，不是当前所有课件的统一页数合同。

本蓝图不再保存逐页排程。现有 `scripts/build_course_slides.mjs` 采用历史排程格式，不能直接将本文作为现行课件的生成输入；重新制作前须另行适配与验收。本轮导航合并不表示 PPT 已重建或通过审核。

## 备课与试讲如何使用这份蓝图

备课时按“本讲问题 → 工作台增量 → ERP 结果 → 学生独立判断”检查讲义、实践和课件，完整验收项回查课程大纲。库存不为负、入库幂等、订单合法迁移、采购人工审批、失败如实记录，贯穿所有练习。

先试讲 L01、L05、L14，记录完成时间、卡点、提示次数、首次与二次提交变化和独立检查结果。操作卡住就补示范，能运行却解释不了就补结果对照，无法迁移就增加等价小任务；后续课程再复查是否掌握。每次修订保留问题来源、材料版本、采取的改法和复查结果，以真实学习记录判断改进是否有效。

本文承载教学目标、活动、评价与持续改进设计。材料检查与参考运行不构成教学效果认定；真实课堂实施、学生学习记录和改进效果仍须采集。涉及正式申报时另核对当时官方要求与校方材料，不用仓库测试替代真实教学证据。
