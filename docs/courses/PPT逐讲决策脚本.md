# PPT 逐讲决策脚本｜16 个独立课件 × 四个核心决策节点

> 这是决策课件的核心节点母稿，不是成品页数合同。每讲必须覆盖事故、证据、决策、后果与行动交接四个节点；成品可以在节点之间增加概念解释、证据拆解、状态图、失败路径和复盘页。完整操作仍由 VS Code 任务卡承载，完整课后复习仍由对应 Markdown 承载。

**沟通任务**：课程结束时，具备编程与 Git 基础的高年级学生应能在信息不完整的 FlowERP 现场作出可解释的工程决定，并愿意用仓库证据修订决定；因为 AI 研发工作台首先约束价值、范围、风险、责任和证明方式，然后才加速编码。

正式发布物采用 **16 个独立 PPTX**，文件位于 `docs/courses/ppt/LNN-*.pptx`。每讲页数不设统一上限，以陌生学生能够听懂本讲冲突、方法、证据和行动为准；不得把 16 讲重新合并成一份总课件。四个编号条目只是必须出现的核心决策节点，不对应固定页码。第一次签字应在第 2～4 页完成，且必须早于方法答案；末页明确切换到 VS Code，并要求学生取得新证据后回到 Markdown 完成第二次签字。

## 统一视觉和讲授规则

- 每张幻灯片只做一件事；标题必须是一句可讨论的判断，不用“概念介绍”“技术架构”等目录式标题。
- 事故页优先使用本仓库真实页面、日志、状态和报告；不使用与项目无关的装饰图。
- 决策页在投票完成前不显示正确答案。选项必须都“看起来有道理”，否则不能形成高阶判断。
- 后果与行动交接页显示进入 VS Code 的单一动作；完整命令留在任务卡。方法解释可以分布在签字后的若干页，但必须服务于本讲决策，不能退化为术语堆叠。
- 讲师备注记录提问顺序、停顿点和 `[Sources]`，不把内部提示放到可见页。

## L01｜终局与冷启动

1. **事故**｜“能打开”为什么仍可能完全不可接手：展示 FlowERP 页面与一个绿色测试结果。
2. **证据**｜作者不在场时，你还缺环境、数据来源、失败语义、启动和恢复证据。
3. **决策**｜40 分钟后是否签收？A 直接签收；B 全面重写；C 只读复验后给条件性结论。
4. **后果与交接**｜签收对象不是页面，而是可运行、可解释、可复验、可接手的系统；打开 VS Code 运行“课程/01 状态检查”。

## L02｜AGENTS 项目约束

1. **事故**｜运营要求“先把库存改成 100，晚上再补手续”。
2. **证据**｜缺货损失真实，但直接写库会破坏库存来源、审计和职责分离。
3. **决策**｜A 先改库；B 一律拒绝；C 拒绝越权动作并给出合法补货路径。
4. **后果与交接**｜好规则必须既能拒绝危险路径，也能放行合法工作；在仓库中让四类请求撞上规则。

## L03｜Spec 驱动

1. **事故**｜运营、仓库、财务给出三种“可用库存”。
2. **证据**｜词语相同，来源、时点、预占和估值口径不同。
3. **决策**｜谁签字、哪些未决问题会阻止开工、哪些只是实现细节？
4. **后果与交接**｜Spec 不是愿望整理，而是授权边界；生成 L03 局部合同并做歧义对抗。

## L04｜Codex 最小变更

1. **事故**｜Agent 一次改了 18 个文件，并报告“所有测试通过”。
2. **证据**｜需求只授权库存导出，额外重构无法从验收合同推出。
3. **决策**｜A 因全绿签收；B 全部拒绝；C 检查能力信封、Diff 与独立复验。
4. **后果与交接**｜交付价值来自可解释的最小变更；在限定写集完成第一次真实红→绿。

## L05｜失败优先 Eval

1. **事故**｜同一入库回调重放后，库存凭空翻倍。
2. **证据**｜现有测试只证明正确代码能过，没有证明错误代码会被抓住。
3. **决策**｜先修业务还是先冻结失败？怎样证明失败可重复且未污染权威状态？
4. **后果与交接**｜先保存事故，再允许修复；连续制造两次相同红灯后再改代码。

## L06｜Harness 证据汇总

1. **事故**｜单测绿、秘密扫描黄、库存不变式红，团队给出三个结论。
2. **证据**｜检查项、等级、总决策和进程退出码没有统一合同。
3. **决策**｜哪一盏灯能阻断？observing 是否影响退出码？
4. **后果与交接**｜Harness 统一判决而不编造根因；构造三种信号并做三角校验。

## L07｜Codex Hook

1. **事故**｜Eval 已经存在，但一次匆忙提交根本没有运行它。
2. **证据**｜“记得检查”是一条依赖人类记忆的脆弱流程。
3. **决策**｜Hook 何时运行、信任谁、超时后放行还是阻断？
4. **后果与交接**｜Hook 复用 Harness，只负责本地时机与消息；让合法/非法订单分别放行和阻断。

## L08｜CI 远程复验

1. **事故**｜PR 徽标是绿色，但没有报告、退出码和可下载 Artifact。
2. **证据**｜Workflow 把失败步骤忽略了，本地和远端还运行了不同入口。
3. **决策**｜这个绿色能否合并？修门禁和修业务能否放在同一次提交？
4. **后果与交接**｜远端可信来自同入口和证据信封；完成 A 假绿、B 可信红、C 可信绿。

## L09｜失败转修复任务

1. **事故**｜取消订单后预占未释放，报告附带 6000 行日志。
2. **证据**｜日志描述事实，却没有定义允许写集、禁止事项和复验入口。
3. **决策**｜把整份日志交给 Agent，还是先压缩为最小修复授权？
4. **后果与交接**｜Repair Task 是授权对象而非摘要；生成任务并只修取消释放。

## L10｜有界 Loop

1. **事故**｜第三轮仍是同一失败，自动修复器却准备开始第四轮。
2. **证据**｜轮数下降不等于进展，失败签名可能完全没有变化。
3. **决策**｜何时继续、何时停止、何时交给人？跑满预算能否写成成功？
4. **后果与交接**｜Loop 的核心能力是安全停止；同时生成收敛和未收敛 History。

## L11｜Subagents 并行

1. **事故**｜三名 Agent 同时修改采购服务，结果都“局部正确”。
2. **证据**｜角色名不同，但写集重叠，合并后业务事实冲突。
3. **决策**｜哪些调查可并行，哪些实现必须串行，谁承担最终结论？
4. **后果与交接**｜先并行证据，再串行事实；画冲突图后才启动子任务。

## L12｜Graph 与人工审核

1. **事故**｜质量全绿，采购申请仍没有具名批准人。
2. **证据**｜Agent 流程状态、ERP 采购状态和审核责任被混成一个布尔值。
3. **决策**｜能否自动入库？崩溃后如何恢复到等待同一位人审的位置？
4. **后果与交接**｜Graph 表达可恢复控制流，人承担不可委托责任；运行批准、打回和匿名失败路径。

## L13｜任务 API

1. **事故**｜客户端收到 `202 Accepted`，立即通知客户“12 台已在路上”。
2. **证据**｜任务只是被接收，尚未执行、验收或批准。
3. **决策**｜哪些状态可对外显示为完成？重复请求和服务重启后如何保持事实唯一？
4. **后果与交接**｜API 暴露任务事实而不是包装同步命令；用两个客户端检验幂等与恢复。

## L14｜Web 状态面板

1. **事故**｜昨天的绿色仍显示在今天的页面上，用户继续发货。
2. **证据**｜DOM、API、SQLite 与 ERP 业务对象指向不同时间和不同 Task ID。
3. **决策**｜页面应该显示失败、未知还是旧数据？哪种文案不会诱导错误动作？
4. **后果与交接**｜Web 的首要职责是说真话；用同一 Task ID 完成四方对账和故障注入。

## L15｜摘要与反馈

1. **事故**｜用户只说“财务页面很难用”，团队准备新增 blocking Eval。
2. **证据**｜反馈没有角色、场景、期望、影响和复现，可能是产品问题也可能是噪声。
3. **决策**｜接受、追问、拒绝还是转成观察项？谁有权升级 Spec 和 Eval？
4. **后果与交接**｜反馈先治理再进化；保存原文、具名判定和独立验证任务。

## L16｜冷启动答辩

1. **事故**｜作者退出操作位，陌生评审者抽到一个此前未实现的小需求。
2. **证据**｜终态绿灯不能证明陌生环境、动态需求和失败路径可复现。
3. **决策**｜先补文档、先写代码还是先新增本次需求专属红灯？哪些风险必须当场披露？
4. **后果与交接**｜结业不是演示旧答案，而是现场关闭一条新证据链；完成动态 Eval、最小实现、人审与发布索引。

## 课件验收

逐讲 PPT 成品必须能回答四个问题：学生在哪一页第一次签字；哪一页才揭示方法；哪一页明确切换到 VS Code；课后可凭哪个 Markdown 小节独立复盘。若答案指向同一页，说明课件仍在堆内容而没有设计学习过程。
