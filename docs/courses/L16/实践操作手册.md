# L16｜在新环境接手，并完成现场新需求

先阅读[辅导资料](辅导资料.md)，再按下面七步行动。**你要交付的是：同伴能接手旧版本，并能通过工作台完成一项现场出现的新需求。** 启动两张页面只是起点；本讲要继续走到范围内实现、失败打回、独立复验和人的决定。

每步把实际记录填入 [SUBMISSION.md](SUBMISSION.md) 的同名节。长命令集中在本文末尾，按步骤打开对应命令区；Windows 只执行 PowerShell 块，macOS 只执行 zsh 块。命令完成后立即记录退出码：PowerShell 用 `$LASTEXITCODE`，zsh 用 `echo $?`。服务一直运行而不返回提示符是正常现象，另一项操作需要新终端。

## 这讲你要亲手交什么

最后一讲把前面建成的能力用在一次未预演交付上。你负责澄清、授权、操作、纠偏和解释；Codex 在你确认的范围内写检查与实现，同伴负责接手和独立复验。按下面四件工作推进，七步正文和 A～M 命令区提供具体操作。

| 要亲手完成的工作 | 在哪做、你要动手做什么 | 留下可检查的产物 | 卡住后回哪一步 |
|---|---|---|---|
| 1. 把旧系统交给另一人 | 在两个作者仓库核对版本，编辑交接说明；由同伴在新目录启动、初始化并操作旧能力 | 两个版本、修订前后说明、同伴首次输出与重做记录 | 缺材料回第 1 步；启动或初始化失败回第 2 步 |
| 2. 把新请求变成真正的工作 | 在工作台登记事项，本人向需求方追问并确认 Spec；只在检查候选新增验收，亲自运行旧绿、新红 | 请求与决定、六段 Spec、目标缺失报告、检查提交 | 已有功能或检查失真回第 3 步重新调查 |
| 3. 交付一份真实修改 | 从控制实例授权 `course-submit`，核对它产出的正式候选 Diff；对真实打回写出修订决定，再沿相同检查重试或安全停止 | Task ID、源码 Diff、失败报告、修订前后候选 | 实现失败回第 4 步；需求或裁判变更回第 3 步 |
| 4. 让成果经得起接手与追问 | 请同伴复验同一正式候选，由实际审核者具名决定；做恢复实验、导出和反馈回查，再用五分钟讲清两项成果与下一事项 | 复验与决定、恢复报告、导出/反馈、答辩稿及全课程复盘 | 不合格回第 4 步；缺记录回第 6 步；解释不清回第 7 步 |

## 本讲交付什么

工作台验证交接、受控执行、复验、人审、摘要与反馈能否连续工作；FlowERP 形成一项此前未实现、可以现场观察的增量；你用自己的首次判断、失败、修订和迁移说明证明学习达成，覆盖 CLO-1～6。

课程四项合同如下，沿用大纲原文：

- **核心内容**：容器化、健康检查、回滚意识、演示叙事和技术债说明。
- **演示结果**：从干净环境启动系统，展示一次成功任务、一次失败打回、一次结果导出和一次反馈写入。
- **课内增量**：完成结业检查表与五分钟答辩稿。
- **通过标准**：需求能生成 Spec 和代码；阻断级 Eval 全部通过；Loop 收敛或如实安全退出；Graph 审核结论可追踪；摘要和反馈能够正确生成；干净环境可启动且仓库无密钥。

### 这次怎样调用全课程能力

前面每讲留下的能力，到了本讲要能解释它解决了哪一步的问题。下表用本次七步重新串起 L01～L15；缺失能力须记录实际状态并补做，不能把参考实现改写成本人的建设成果。

| 本次步骤 | 要调用的前面课程能力 | 在这次交付里解决什么、查什么证据 |
|---|---|---|
| 1. 交接版本 | L01 项目与命令证据账；L02 权限规则与完成定义 | 接手者拿到哪个项目、可改哪里；核对版本、依赖、数据边界和交接说明 |
| 2. 新环境启动 | L13 Task API 的持久身份；L14 工作台与客户 Web 的状态核对 | 新实例能否操作，任务与客户业务是否各有归属；核对地址、数据目录和首次操作 |
| 3. Spec 与检查 | L03 六段 Spec；L05 失败优先 Eval；L06 Harness；L15 反馈分诊 | 将请求收窄成可判定目标，用可信的新红证明缺口；核对来源、反例、名称、报告与退出码 |
| 4. 实施与返工 | L04 授权与受控写入；L09 Repair；L10 有界 Loop；L11 子任务合同 | 只改允许的文件，把具体失败变成修订任务；查 Task、Diff 和停止理由。确有独立读写边界才委托 Subagents |
| 5. 独立复验与人审 | L06 Harness；L07 Hook；L08 CI；L12 Graph 与具名人审；L14 页面与数据对账 | 复用同一质量入口，独立检查候选与业务状态；查实际运行记录和具名决定。Hook/CI 的旧结果只能说明旧版本 |
| 6. 恢复与反馈 | L13 任务查询与结果；L15 Feedback 的原文、分诊与后续任务 | 导出可追溯成果，让真实意见进入下一轮判断；查版本、恢复边界、导出内容及反馈回查 |
| 7. 答辩与迁移 | L01～L15 的工作台建设、产品交付与个人判断 | 用两项成果讲清因果关系：本人建了什么工作台能力，它怎样帮助交付 FlowERP，换条件后怎样重新验收 |

本题不要求把每个任务拆成并行任务，也不要求重跑全部历史流水线。Loop/Graph 的参考运行用于机制核对；第 4 步的实际失败、修订和同候选复验才支持本次返工结论。

**控制实例与候选使用的源码可能不同。** 当前控制实例通过进程调用独立 FlowERP；本仓库目前的 `course/l16-start` 是保留 `flowerp/`、`web/` 的旧课程组合快照。组合源码只存在于隔离候选中，不复制回控制实例，不改测原客户库来补候选结果。每次运行先看实际目录与模块来源。

本次证据统一放在冷启动工作台运行目录下的 `l16-evidence/`。报告、文字记录、截图和导出文件可放这里；两套数据库保留在各自运行目录中，密码和认证文件不进入提交材料。独立源码环境、同伴操作、陌生机器和容器空卷是不同的观察范围，分别记录。

## 1. 交接已有版本

**目标：**让接手者知道拿到什么版本、怎样启动、怎样判断它正常。

**位置与动作：**在作者原环境分别记录 CodexFDE、FlowERP 的绝对路径、提交号、未提交修改、Python 版本和依赖；用[命令 A](#commands-a)核对。整理两套启动命令、地址、初始化方法、数据归属和失败处理，交给同伴。若有未提交内容，明确交接快照及文件指纹；一个提交号不能代表没有被提交的文件。

先亲自跑版本检查，再把实际输出交给 Codex 整理：

```text
根据我刚运行的两个仓库版本与环境输出，协助整理一份同伴可照做的交接说明：源码版本、依赖、启动/初始化、地址、各自数据目录及常见失败处理。未知项列待核对。我确认内容并交给同伴操作后，再按同伴实际追问修订；不要代写同伴的操作结果。
```

先写本人的交接风险预测，例如“对方可能不知道工作台需要 Git 历史”。**此时现场新需求尚未提出，不提前选题或代替需求方作决定。** 交接材料还应包含课程标签、当讲手册与 `examples/restore_lab.py` 等实验附件；本地未被 Git 跟踪的资料不会随克隆自动出现，缺失时如实登记并补齐版本来源。

**预期结果：**同伴仅凭说明可以定位两份源码、建立环境并知道如何检查。

**失败处理：**源码、依赖或附件不全时补交接说明；保存修订前版本。不能借用作者已启动的服务和 `.venv` 充当接手者重建。

**完成判断与记录：**两套版本和重建条件明确，首次风险预测已保存。填模板第 1 节。没有实际同伴时，同伴接手项记“未验证”，自己的重建另记范围。

## 2. 在新环境启动双系统

**目标：**检验交接说明是否足以让另一人从新环境启动并操作旧版本。

**位置与动作：**接手者在全新目录取得第 1 步冻结的两份 Git 源码，分别建立 `.venv`，设置独立 FlowERP 路径，使用两个未用过的数据目录启动服务。完整的本机操作在[命令 B](#commands-b)。这里以工作台 `18161`、FlowERP `18160` 为教学端口；使用前确认空闲，端口变化同步修改客户链接。

同伴从交接说明重建两套环境，再操作两张页面。核对源码与数据归属时，可查[辅导资料的新环境交付图](辅导资料.md#environment-checks)。两套健康检查均通过后，继续完成下面的初始化与商品建档抽查。

本讲的完整编码路线使用带课程历史和标签的本机控制实例。容器路线按[部署与回滚说明](../../../deploy/ROLLBACK.md)构建、启动、初始化和检查两个服务，记录新 Compose 项目名、空卷、镜像及端口。**只读容器镜像没有本机 Codex 认证和课程历史，不能接着在里面运行第 3～4 步编码。** 容器运行的发布验证与本机控制实例的代码交付分别留证。没有容器引擎时，保留容器构建与空卷启动“未验证”的结论。

给 Codex 的提示词：

```text
核对我交接的两个源码版本、依赖、初始化、地址和数据归属，帮助接手者按说明从新环境启动。只采用本次独立目录或新 Compose 项目，保留旧状态。记录首次失败、说明修订和再次操作。分别报告服务启动、健康检查、页面初始化和业务操作的结果。不要在记录中写密码，不删除数据卷。
```

健康接口成功后，打开工作台根首页和 FlowERP 客户页。首次客户页需要操作者设置组织、管理员和密码；初始化页可访问不等于业务已通过。做一项旧能力抽查：

1. 在“商品档案”新增 SKU `COLD-16`、名称“隔离启动核对商品”。
2. 再用同一 SKU 提交名称“重复提交不应覆盖原商品”。预期拒绝创建。
3. 关闭表单并刷新，确认只有一条记录、原名称未变；重新登录同一组织再回查。

**预期结果：**两套健康检查通过，页面指向本次实例；商品建档成功，重复 SKU 被拒绝且旧记录未变。这项抽查验证旧交付，不是现场新需求。

**失败处理：**先保存首次错误和实际命令，再区分源码、Git 信息、依赖、端口、代理、初始化或业务规则问题。真实克隆保留历史；仅 `git init` 得到的空仓库不能替代课程标签。按同伴的实际追问修订说明，再由同伴重做失败步骤。可查[冷启动观察](examples/cold-start-observation.md)及[商品建档复验](examples/初始化与商品建档复验.md)。

**完成判断与记录：**同伴实际重建、初始化、旧能力成功与拒绝后状态都有证据，环境边界明确。填模板第 2 节。

## 3. 确认现场新需求并建立检查

**目标：**把现场请求变成可以区分正确和错误实现的验收，先证明能力确实缺失。

**位置与动作：**回到冷启动工作台首页“事项与决策”，登记需求，记下事项编号及工作台运行目录。先调查当前代码和页面，再由需求方确认角色、场景和范围，将需求写成六段 Spec：来源、目标、非目标、约束、验收用例、完成定义。

先用下面的提示词辅助追问和调查，再由本人确认范围。这次不要直接让 Codex 实现：

```text
围绕本次使用者原请求，帮助我查清当前版本是否已满足、还差什么，以及最小可观察变化是什么。每次只追问影响范围或验收的关键歧义；整理六段 Spec 初稿，标出待本人或需求方决定的项。此时只做调查与文档，不改实现；新增检查在课程检查候选中单独授权，正式实现由 course-submit 执行。
```

贯穿教学例是周宁提出：“库存列表有多页，希望按商品名关键词查找本组织的全部库存。”关键词为“螺栓”，目标“蓝色螺栓”在第 2 页，另一组织也有同名商品。检查要能发现漏掉后续页、混入另一组织数据、查询改变库存和空结果无提示等错误。**这只是用来说明怎样设计检查。** 实际版本若已有该能力，先判断测试是否过弱，再换一个真实未满足的小需求；不能照搬已实现的[库存筛选案例](../cases/L16-库存余额筛选真实执行案例.md)。

先在当前冷启动版本确认请求未满足，再在工作台准备的课程检查候选核对目标能力及业务源码。两处版本若不同，记录差异并确认题目仍成立；不能只看当前页面缺功能，就推定旧课程候选也缺同一能力。

按[命令 C](#commands-c)读取 L16 合同、验证课程标签、准备检查候选。`TASK-PREP-…` 只用来给检查目录命名，不是正式交付 Task ID。进入返回的 `path` 后保存初始差分，再给 Codex：

```text
在我提供的 L16 检查候选中，只新增本人确认版 Spec 所需的 Eval 与必要测试，不实现目标功能，不改旧检查和业务源码。
读取该候选的 eval.harness 发现入口，在 EVALS 中登记本次新增名称、blocking 等级与检查函数。检查应操作这份候选的实际业务，比较独立预期，并返回可回查的输入与状态；不满足要求时报告具体差异。保持课程合同的旧项不变。未知名称、导入失败、缺依赖或固定抛错都不是目标能力缺失。
给出登记文件、真实用例名称、断言与范围内 Diff，等待我实际运行。
```

用[命令 D](#commands-d)核对模块来自检查候选，分别运行旧项和新增项。Eval 是验收检查；`blocking` 表示失败会阻止接受交付。把实际新增名称逐字写入本人 Spec 的“验收用例”段。有多项时分别运行，后续正式提交重复提供 `--eval-case`。

**预期结果：**旧项退出 `0`；新增项退出 `1`，报告指出本题能力缺失。例如“蓝色螺栓”位于第 2 页，而关键词查询只检查当前页，所以真实结果漏项。

**失败处理：**旧项不绿先排查基线；新增项因环境、未知用例或检查自身错误失败，先修正检查环境。新增项已绿则重查目标是否已实现、断言是否充分。不要为了获得红灯删业务代码。准备器若删除教师门闩 `PROGRESSION.json`，只记为起点差分，不当作学生实现，也不恢复或暂存它。

**完成判断与记录：**检查覆盖本人 Spec 的正常路径、边界和失败后状态，旧绿与新红原因可信。库存教学例对应跨页查找、组织隔离、查询只读和空结果提示；本题涉及应拒绝的请求时，另查拒绝后状态。按[命令 E](#commands-e)只提交新增检查和必要测试，保存真实提交 SHA。实现尚未开始。填模板第 3 节。

## 4. 通过工作台实施与返工

**目标：**让工作台按已确认的 Spec 和写入范围调用 Codex，保留实际执行与打回过程。

**位置与动作：**从检查候选回冷启动控制实例，沿用原工作台运行目录。运行[命令 F](#commands-f)：核对检查提交在控制实例同一 Git 库可解析、位于 `course/l16-start` 之后；给出本人 Spec、实际新增 Eval 名称及必要实现文件，明确授权本次执行。写入范围只允许 L16 合同中的 `flowerp/`、`workbench/`、`eval/`、`web/`、`tests/`，再收窄到本题文件；冻结检查不属于实现授权。

`course-submit` 会另建正式交付候选，重新检查起点，再让 Codex 实现和复验。保存它返回的 Task ID、`isolation.path`、执行前后报告和真实 Diff，并关联原事项。CLI 使用原运行目录，首页才能回查同一任务；CLI 不自动补全事项关联，尚未关联时如实记录。

**预期结果：**实现检查通过时，返回 `implementation_evidence: true`，任务处于 `review`，即“等待人审”。这证明实际调用、范围内差分和检查结果满足课程执行条件，尚未代表人已接受或代码已发布。

**失败处理：**退出非零先回查原 Task 和报告，区别起点无效、执行器失败、越界、后验失败或人审打回。保留原报告及候选，写明如何修订。若需重试，重新确认范围和授权，沿冻结检查基线再运行 `course-submit`，把新 Task 与原 Task 关联同一事项，并保存新正式候选。当前通用 `task-run` 不保证沿用本题的 L16 检查集合，不能用它替代这条课程重试路线。检查或需求口径变化时返回第 3 步重建真实起点。

失败打回必须是本次研发交付确实未满足验收而进入返工或安全停止。重复 SKU 的业务拒绝、断网、参考 Graph 的自动拒绝不能代替它。没有真实打回证据时，明确留下缺项，由复验者检查本题反例与边界，不补写虚构失败。

**完成判断与记录：**本次执行、范围、结果和任务身份可回查；失败与后续修订未被覆盖。填模板第 4 节。

## 5. 复验同一候选并由人决定

**目标：**让未参与实现的人检查正式候选，实际操作新需求，再作出可追踪决定。

**位置与动作：**复验者在新终端输入原控制解释器、原运行目录、新增检查名称和正式 `isolation.path`，按[命令 G](#commands-g)核对源码来源，运行指定检查与完整阻断 Eval。不要回到检查候选，也不要把原独立 FlowERP 的通过结果补成候选通过。

再按[命令 H](#commands-h)预览这份正式候选，使用全新客户数据目录。当前固定课程标签采用旧组合源码，客户入口是候选中的 `workbench.cli serve`；控制实例当前的同名命令则转交独立 FlowERP。命令先验证真实入口再启动。若实际候选已采用独立入口，按 [L14 候选预览](../L14/实践操作手册.md#candidate-business-preview)第 5.2 节核对，直接使用本次 `isolation.path`，不查其他日常交付包。

复验者按本人 Spec 操作正常与边界输入，检查操作后的状态。教学例要用“螺栓”实际找到第 2 页的“蓝色螺栓”，排除另一组织同名商品，核对空结果提示与查询前后库存不变；若本题包含应拒绝请求，另查拒绝后状态。记录对象、响应、候选版本及数据目录；服务检查绿而未操作页面，页面验收仍未完成。

按[命令 I](#commands-i)核对测试、Loop 和 Graph。Loop 是有轮数上限的返工循环；默认命令不执行 Codex 修改，起点已绿时只能说明检查收敛。Graph 是保存节点、等待和审核决定的流程；开启人审并使用本轮新状态文件，待审退出 `3` 是等待人决定。两者的记录属于机制复验，不能代替第 4 步的真实任务执行与人的接受。

**预期结果：**指定检查与本轮完整阻断报告退出 `0`，业务正常和拒绝后状态满足同一 Spec；复验者明确接受、打回或待补证。

**失败处理：**先保存红报告、实际对象及理由；新候选仍红回第 4 步返工。Graph 等待时沿同一状态文件提交实际审核决定，不改 JSON 冒充完成。正式 Task 与 Graph 状态文件是两个审核对象，分别留决定；新候选不能继承旧版本的签字。

**完成判断与记录：**复验者本人完成操作并限定结论范围，按[命令 J](#commands-j)在控制实例记录正式 Task 决定。没有实际复验者或决定时保留待审。填模板第 5 节。

## 6. 验证恢复、导出与反馈

**目标：**让交付可以回查、恢复并接收后续使用意见。

**位置与动作：**回冷启动控制实例，用[命令 K](#commands-k)做独立恢复实验。先预测：8 件时备份，随后增加到 10 件，恢复副本应是多少？报告应确认恢复为 8 件、源库仍为 10 件；重复恢复拒绝覆盖、损坏备份被拒绝且目标未生成。此脚本使用独立 FlowERP 环境，属于教学恢复实验；它不证明本次候选兼容性或生产回滚。解释真实交付的上一已验证版本、恢复点与剩余风险，参照[部署与回滚说明](../../../deploy/ROLLBACK.md)。

给 Codex 的提示词：

```text
先记录我对恢复点的预测，再检查本次独立实验的源库、恢复数量、事件键及拒绝后的状态。解释后来新增的 2 件为什么不在备份中。结合本人交付版本，指出仍需验证的数据兼容与恢复条件。不要将教学实验写成容器冷启动、候选恢复或生产回滚完成。
```

完成以下三个独立动作，命令在[命令 L](#commands-l)：

1. 导出真实任务结果，核对 Task ID、结果摘要、检查结论、范围和风险。已经具名接受的候选可用 `course-candidate-export` 导出完整 Patch；拒绝或待审候选不能当作已接受成果。
2. 请实际试用者描述这项需求的使用情况，保存角色、场景、原话、你的解释和下一步；写入同一工作台的反馈库，再从同运行目录回查。反馈是意见记录，不会直接改成阻断 Eval。
3. 将冷启动记录、产品对账和风险文件放在本次 `l16-evidence/`，运行 `course-release-index` 建立证据索引；检查每一项 `evidence_gaps`，随机回到一份原始报告核对。

**预期结果：**恢复点实验结论可解释；结果导出内容能回查；实际反馈写入并可检索；索引指出已具有和仍缺的材料。索引是路径、指纹和任务记录的目录，不能代替导出、反馈、接受或发布。

**失败处理：**恢复兼容不明时停止进一步发布，不覆盖唯一数据。实验目录已存在时换新目录并保留旧结果。索引报路径错误时，核对证据是否在原工作台运行目录中。反馈为空时检查数据归属；当前控制 `demo` 委托独立 FlowERP，不能据旧演示推定工作台自动增加一条反馈。历史差异可查[命令与同目录反馈对照](examples/五条命令与同目录反馈对照.md)，以本次实际代码和记录为准。

**完成判断与记录：**恢复、导出、实际反馈和索引分别有原始证据；发布、容器或真实候选恢复的未验证项明确保留。填模板第 6 节。

大纲的五个最终验收入口都要有实际观察：Eval、Loop、Graph 已在 G／I 区核对；参考 `demo` 在[命令 M](#commands-m)用独立演示目录运行；反馈使用 L 区的显式运行目录回查。记录每个入口的来源与结果，演示不能替代本题成功、打回或实际反馈。

## 7. 答辩并说明迁移

**目标：**用五分钟解释这一项需求如何被交付，以及换一个条件后怎样继续判断。

**位置与动作：**在模板第 7 节准备答辩稿，与辅导资料采用同一顺序：0:00～0:45 请求与 Spec；0:45～1:30 冷启动与真实缺口；1:30～2:30 任务、Diff 与修订；2:30～3:30 同候选复验、失败打回与人审；3:30～5:00 恢复、导出、反馈、风险与迁移。每段只引用本次真实对象和证据，讲清一次纠偏、一个未解决技术债及下一步。

先做一次全课程个人复盘，填入模板第 7 节的“我在全课程亲手建成什么”。拿实际文件与记录回答以下三行，准备成答辩中的证据；不按 16 讲逐页念术语。

| 复盘对象 | 本人要回答的问题 | 拿出来核对的材料 |
|---|---|---|
| 个人工作台 | 我从哪版开始，亲手确认并建设了哪项能力？它在哪个后续任务真正起作用？ | 本人实现的版本/Diff、前后检查及采用该能力的真实 Task |
| FlowERP | 通过这个工作台实际交付了什么变化？哪次失败迫使我改变判断？ | 工作台事项与 Task、Spec、候选 Diff、产品前后状态及独立接受 |
| 下一事项 | 哪个结论仍未被证据支持？下一项需求会复用哪条经验，何时要重验或停用？ | 真实缺口、经验来源与版本、适用边界及下一步检查 |

参考仓库有实现，可以作为对照；它不能证明你已经亲手建设。本人已实现的能力、只复验过的参考能力、尚待完成的能力要分别写清。全课程成果至少能沿着“工作台能力 → 实际任务 → FlowERP 变化”查回真实材料。

让同伴改变一个未预演条件。以关键词查询为例，可以改成只读账号、不同分页规模或另一种关键词；说明哪项旧流程可复用、哪项业务预期要重写，以及新增什么检查。引用实际采用的一条旧经验，交代来源、版本、适用边界及本次复验；只有口头说“可复用”不能证明跨事项闭环。

需要辅助检查时，可选使用以下提示词；这项 Skill 复核不新增必交材料：

```text
请使用 examples/skills/release-evidence-review/SKILL.md，审查本人冷启动、现场需求、检查起点、真实调用、Diff、打回与修订、同候选复验、人审、恢复、导出和反馈。只引用可读取的原始材料，指出结论超出证据及具体缺项。帮助我核对五分钟答辩，不替我补写本人判断、同伴操作或人的接受。
```

**预期结果：**听者可以沿同一事项和候选追到每项关键结论，理解你如何纠偏及在哪里停止。

**失败处理：**缺证据回对应步骤续做；尚未完成的人审、容器和迁移实践保留真实状态。Skill 的审查意见须由你判断采用或反驳，不能当成最终接受。

**完成判断与记录：**七步记录相互引用，真实接受范围明确，未验证项没有写成完成。提交模板与所引用证据，不提交数据库、密码或认证文件。

### C. 准备检查候选（第 3 步，控制实例）

第 C～F 区在同一操作终端续做。本人六段 Spec 放在本次运行目录的 `l16-evidence/`。准备退出 `0` 后保存返回的 `path`、`baseline_commit`，且 `baseline_semantics` 应为 `tagged_start`；缺标签退回 `progression_gate` 只可预习，不进入真实执行。本路线不用 `--source working-tree`，因为那种双仓快照另有 Git 库，不能直接作为本路线的会话提交。

```powershell
$l16Control = (Get-Location).Path
$l16Python = (Resolve-Path '.venv/Scripts/python.exe').Path
$l16Item = Read-Host '首页实际事项编号'
$l16Runtime = [IO.Path]::GetFullPath((Read-Host '原工作台运行目录'))
$l16Evidence = Join-Path $l16Runtime 'l16-evidence'
New-Item -ItemType Directory -Path $l16Evidence -Force | Out-Null
$l16Spec = (Resolve-Path -LiteralPath (Read-Host '本人六段 Spec 绝对路径')).Path
& $l16Python -X utf8 -m workbench.cli course-contract --lesson 16
& $l16Python -X utf8 -m workbench.cli spec $l16Spec
if ($LASTEXITCODE -ne 0) { throw '先修正本人 Spec' }
git rev-parse --verify 'refs/tags/course/l16-start^{commit}'
if ($LASTEXITCODE -ne 0) { throw '缺课程标签，停止准备' }
$l16PrepId = 'TASK-PREP-L16-' + [guid]::NewGuid().ToString('N')
& $l16Python -X utf8 -m workbench.cli course-prepare --lesson 16 --task-id $l16PrepId --runtime-dir $l16Runtime
if ($LASTEXITCODE -ne 0) { throw '保留准备错误，先排查' }
$l16CheckCandidate = (Read-Host '刚返回的检查候选 path').Trim().Trim('"')
Set-Location -LiteralPath $l16CheckCandidate -ErrorAction Stop
```

```zsh
prepare_l16_checks() {
  l16Control="$PWD"; l16Python="$PWD/.venv/bin/python"
  [ -x "$l16Python" ] || return 1
  printf '首页实际事项编号：\n'; read -r l16Item || return 1
  printf '原工作台运行目录：\n'; read -r l16Runtime || return 1
  l16Runtime="$("$l16Python" -c 'from pathlib import Path; import sys; print(Path(sys.argv[1]).resolve())' "$l16Runtime")" || return 1
  l16Evidence="$l16Runtime/l16-evidence"; mkdir -p "$l16Evidence" || return 1
  printf '本人六段 Spec 绝对路径：\n'; read -r l16Spec || return 1
  "$l16Python" -X utf8 -m workbench.cli course-contract --lesson 16 || return 1
  "$l16Python" -X utf8 -m workbench.cli spec "$l16Spec" || return 1
  git rev-parse --verify 'refs/tags/course/l16-start^{commit}' || return 1
  l16PrepId="TASK-PREP-L16-$("$l16Python" -c 'import uuid; print(uuid.uuid4().hex)')"
  "$l16Python" -X utf8 -m workbench.cli course-prepare --lesson 16 --task-id "$l16PrepId" --runtime-dir "$l16Runtime" || return 1
  printf '刚返回的检查候选 path：\n'; read -r l16CheckCandidate || return 1
  cd "$l16CheckCandidate" || return 1
}
prepare_l16_checks
```

### D. 运行旧绿、新红（第 3 步，检查候选）
