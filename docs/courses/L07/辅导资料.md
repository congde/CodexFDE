# L07｜用 Codex Hooks 建立本地护栏

L06 已经能把多项检查汇成可信结果。现在 FlowERP 开始处理订单：创建草稿时，要把每行“数量×单价”加起来，并且暂不预占库存。我们会用同一质量入口检查这些要求。

但检查再可靠，也可能在修改后忘了运行。上午的版本通过，下午又改了金额计算，旧报告就不能替新版本作证。**本讲解决的是调用时机：让关键工作事件触发已经接好的检查。**

你决定事件、命令和失败处理规则，Codex 协助接入与修复，工作台保留事件与检查记录。先手动确认检查能抓住错误，再验证自动触发；不要把“配置写好了”当成“当前版本查过了”。


## 1｜把上午和下午分成两个版本

订单有两行：2 件商品，每件 30 元；3 件商品，每件 20 元。总金额应为 2×30＋3×20＝120 元。

上午，版本 V1 正确计算出 120，检查通过。下午，Codex 修改计算逻辑得到 V2，却漏乘数量，只算 30＋20＝50。随后它说“完成了”，没有重新运行检查。

问题在哪里？先在 **V2** 上手动运行原检查：如果能指出“预期 120，实际 50”，说明检查有用，这次缺的是及时调用。若手动也发现不了，先补检查；若运行在 V1 的目录，先修路径。只有分清这三种情况，才知道该改哪一层。

本讲产品目标还包括正确建立订单草稿。草稿只是记录购买意向，正常建立时不应提前预占库存；金额算对只是其中一项要求。

## 2｜让关键事件调用已有的检查

**Hook** 是某个事件发生时被调用的处理程序。这里使用工具工作过程中的事件，例如准备结束本次工作时，调用项目自己的质量检查。所谓“生命周期”，就是这些开始、运行、准备结束等工作阶段。

![Hook 触发、Harness 执行、Eval 判断](assets/reading-figures-v2/key-example.png)

**图 7-1　Hook 触发、Harness 执行、Eval 判断**

沿图看一次调用：准备结束的事件发生 → Hook 调用统一入口 → Harness 选择并运行检查 → Eval 判断金额是否为 120 → 结果返回，决定是否仍需处理。

Hook 不另写一套金额公式。否则原检查后来补了“草稿不预占库存”，Hook 内复制的版本却没补，同一个项目就出现两套标准。本讲应先确定一个统一入口，让人工运行和事件触发使用同一套要求。

L06 库存实验修复的是 `eval/l06_runner.py`，本讲命令入口是 `eval.harness`。两者不是同一个文件，需要先按[检查接入手册](L06检查接入手册.md)把个人 L05、L06 检查及运行器合同登记到统一入口；接入脚本也会加入本讲三个订单检查。先核对七项指定检查确实运行，再复验完整阻断集合，最后配置 Hook。这样复用的是原检查函数和标准，而不是复制一份旧绿报告。

Git Hook 的触发源不同：它在 Git 操作时运行，例如提交前。会话结束可能还没提交，提交前也可能又改过代码。因此“提交前查过”和“结束工作时查过”要分别说明；两者都需要对应被检查的实际版本。

本讲讨论课程参考处理器的判断方法。具体宿主是否支持、如何加载事件和响应协议，应按[实践操作手册](实践操作手册.md)及其官方来源核对，不能把参考适配器当成所有版本的通用行为。

## 3｜接入前，先读它到底会执行什么

Hook 会启动命令，因此配置本身也是需要审查的代码。先查项目配置的来源，再沿命令看到实际脚本，确认工作目录指向 V2 所在候选、调用统一 Harness、使用正确环境。

同时确认等待多久，是否有联网、读敏感信息、修改文件等副作用，以及异常时怎样处理。一个只需检查订单的命令，不应因为藏在项目配置里就自动获得其他授权。

可以把接入任务交给 Codex：

> 按本讲手册检查项目级 Hook 的来源、目标事件和参考处理器。让它调用【当前候选的统一 Harness 入口】，保留原检查。说明工作目录、超时和失败响应。先展示配置到实际命令的调用关系，再按宿主要求接入；分别记录手动测试与真实事件结果。

接入以后，仍需要逐层取证：文件存在只证明写了配置；配置被加载才可能生效；真实事件调用了它，才说明触发发生；宿主按失败响应停止结束流程，才说明阻断生效。

## 4｜为什么检查失败，处理器却可能退出 0

这里的**宿主**指加载配置、触发事件并接收响应的工具；**处理器**指事件触发后运行的脚本。处理器要把检查结果翻译成宿主能理解的响应。因此有两个不同的问题：“业务检查通过了吗？”和“处理器成功交付响应了吗？”

在课程参考处理器中，可能出现以下组合：

| 层次 | V2 金额错误时的结果 | 表达的意思 |
|---|---|---|
| Harness | 金额检查失败，退出 1 | 业务要求未满足 |
| Hook 处理器 | 返回合法的阻断响应，自身退出 0 | 成功告知宿主应阻断 |
| 宿主工具 | 收到响应后按协议处理 | 需要实际事件证据确认 |

所以处理器退出 0 并不自动等于金额正确。反过来，也不能要求所有层都退出 1；要按各层协议看失败有没有完整传到下一层。若处理器把失败翻译成普通成功，或者宿主根本没收到响应，这次护栏就没有完成它的职责。

手动输入一个示例 Stop 事件，能检查翻译逻辑，但不能证明真实宿主加载过配置。教学演示和真实事件记录应分开保存。

*读图：课程参考协议中，退出 1 表示业务检查失败，处理器退出 0 表示成功送出阻断响应。最右侧的宿主行为仍需用真实事件验证。*

## 5｜用同一个错误做阻断，再用修复做恢复

现在保持 V2 的错误，按手册触发目标事件。应能串起同一次运行的三份材料：当前候选的失败报告、处理器的阻断响应、宿主的实际反应。如果只看到金额失败，却找不到后两项，先查触发与响应链，别急着改业务来消除红灯。

确认真实阻断后，再让 Codex 在授权范围修复金额。保留原检查，得到 V3，并触发同类事件。这样红与绿各自对应明确版本，可以解释变化来自什么修改。

“阻断结束”并不意味着自动撤销之前写过的文件；检查是否导致回滚，要看具体实现。超时也只说明等待到期，不能由此推断子进程已全部退出。没有有效结果时保留未验证状态，检查进程与报告，再决定重跑或人工处理。

参考处理器还有避免反复调用的重入分支，遇到相应标记会跳过。**跳过没有生成新的通过证据。** 最终交接仍要找到当前版本的有效检查，尤其是最近一次检查之后又改过文件时。

## 6｜从“金额正确”走到“订单草稿可验收”

修复后换输入：3 件每件 25 元，加 2 件每件 18 元，应为 111 元。这可以排除直接返回课堂答案 120 的实现。

还要复验草稿的正常与失败路径：合法商品和数量能建立正确草稿；0、负数量或无效商品被拒绝，相关草稿和明细不留下错误记录；正常草稿也不提前预占库存。原有收货等回归检查继续执行，确认本次修改没有破坏以前功能。

按[实践操作手册](实践操作手册.md)第 1～2 步准备与确认规则，第 3 步看处理器，第 4～5 步接入并交付草稿，第 6 步记录真实事件的阻断与恢复，第 7 步独立复验。缺少真实事件记录时，明确写“适配器手动测试完成，宿主触发待验证”。

交接时用自己的材料回答：哪个版本错成 50？哪个事件实际运行了检查？失败怎样传给宿主？最终 120 和迁移输入 111 对应哪个版本？这些回答证明你能把触发、检查和版本连起来。


触发方式、检查入口与证据细节按需查阅[实现细节与扩展阅读](实现细节与扩展阅读.md)及[参考详解](参考详解.md)。
