# L07｜实现细节与扩展阅读

本页保留原有详细说明与操作示例，供按需查阅。首次学习先读[辅导资料](辅导资料.md)，实际执行以[实践操作手册](实践操作手册.md)为准。文中教学预期不替代个人实测。

**本讲只追问一件事：检查明明能抓错，为什么这次修改还是没有被检查？**

原理在本文，操作按[实践操作手册](实践操作手册.md)。完整适配器解释、参考实测与来源见[参考详解](参考详解.md)。

## 1｜上午检查通过，下午改了代码，还能算通过吗

**检查必须对应修改后的版本；旧版本通过不能替新版本通过。**

> **案例｜订单金额应为 120 元**
>
> 一张订单有两行商品：第一行 2 件，每件 30 元；第二行 3 件，每件 20 元。订单金额应为 **2×30＋3×20＝120 元**。

> **案例｜上午通过，下午改完却没有重查**
>
> 错误实现只把两个单价相加，得到 50 元。你已经有能发现这个问题的检查。上午运行过，结果正确；下午 Codex 修改了金额计算，随后说“完成了”，但没有再运行检查。

上午的绿灯能证明下午的新代码吗？不能。这里缺的未必是新的测试，而是**在应当检查的时候，确实调用已有检查**。

L06 建好的 Harness 是统一质量入口。本讲复用它，在关键生命周期节点触发检查，而不是再写一套订单金额判断。

你确认触发时机、来源和允许行为；Codex 协助配置处理器、修复订单；工作台保留检查证据；复验者核对真实触发是否发生。FlowERP 的交付目标是正确建立订单草稿、计算金额，并保持草稿阶段不预占库存。

## 2｜先分清 Hook、Harness 和 Eval

**Hook** 可以理解成某个事件发生时被调用的处理程序。这里的事件来自 Codex 工作过程的生命周期，例如准备结束一次工作时。它负责“什么时候叫检查”。

**Harness** 负责选检查、运行检查、记录结果和汇总。**Eval** 负责判断具体要求有没有满足，例如金额是不是 120。

![Hook、Harness 与 Eval 分别负责什么](assets/reading-figures-v2/key-example.png)

*读图：上半图看三者分工，下半图看版本变化后为什么必须重查。*

Hook 发出调用，Harness 选择检查、逐项运行并汇总，Eval 用订单数量与单价核对结果。三个部分分工不同，但复用的是同一个质量入口。

上午被检查的是版本 V1，下午修改后是版本 V2。旧版本的绿灯不能证明新版本；应在 V2 上重新运行原检查，而不是为它降低标准。

Hook 不会自动让一个弱检查变强。它也不会因为名字叫“护栏”，就阻止所有危险动作。若触发点在会话结束前，之前已经发生的文件修改并不会因此自动回滚。

### 先诊断，再决定是不是需要 Hook

假如订单金额错了，先问：

1. 手动运行检查也发现不了？先补 Eval，自动运行弱检查没有用。
2. 检查运行在错误目录或旧候选上？先修候选与入口。
3. 手动检查能抓到，但关键节点没有运行？这才是触发问题。
4. 命令报错且没有有效报告？先修环境，不能把“检查没完成”当作通过。

这样做能避免“出问题就再加一个 Hook”，最后却无人知道哪一套检查真正有效。

## 3｜Hook 与 Git Hook，不是同一个时机

Git Hook 是 Git 操作触发的处理程序，例如提交前执行检查。生命周期 Hook 则由相关工具的工作事件触发。两者可以调用同一个 Harness，但不能互相冒充。

一段修改可能发生了，却还没有 Git 提交；因此提交前检查不能证明会话结束时已经检查。反过来，会话结束时运行过，也不能自动证明后来准备提交的内容没有继续改变。

本讲采用项目级质量 Hook，是为了把项目自己的质量要求接到明确节点上。**配置文件存在、工具加载配置、用户信任配置、真实事件触发成功，是四件不同的事。**

配置和事件协议可能随工具版本变化，安装及字段以实践手册和相应官方说明为准。本文讲判断方法；下面的退出码转换指课程参考处理器，不推广为所有 Hook 的通用协议。

### 调用之前，先检查它会执行什么

Hook 能启动命令，就存在信任边界。使用前要看来源、实际命令、工作目录、环境变量、等待上限和副作用：

- 来源是否是你检查过并同意使用的项目配置？
- 运行的是当前候选的统一入口，还是陌生脚本或另一份副本？
- 是否会联网、读取敏感信息或修改无关文件？
- 超时、异常、报告缺失时，是否保留“未验证”，而不是继续声称完成？

“项目里带着这个配置”不是自动授权。护栏本身也需要可检查。

## 4｜最容易混淆的地方：为什么有两个退出码

参考处理器处在 Harness 和宿主工具之间，负责把检查结果翻译成宿主能理解的响应。一次业务失败要沿三层追踪：

| 层次 | 要确认的事实 | 不能拿什么替代 |
|---|---|---|
| Harness 检查层 | 发现订单错误，返回失败和有效报告 | 只有终端里一行“失败” |
| Hook 处理器层 | 按约定协议表达“阻断” | 只看处理器自身退出码 |
| 宿主事件层 | 真实事件调用了处理器，并按阻断响应处理 | 手动喂一个示例事件 |

在课程参考处理器中，Harness 可以退出 1，而处理器为了成功交付一份合法的“阻断”响应，自己退出 0。这里的 0 表示响应按协议交付，不是订单业务通过。

所以不能机械地要求“每一层都必须退出 1”，也不能看见处理器退出 0 就说放行。要继续读响应中的阻断含义，并核对宿主是否真的接收和执行了它。

反过来，如果处理器吞掉失败，只返回普通成功，那就是失败传递丢失。判断的核心是业务失败有没有沿调用链被保留下来，而不是某个数字孤立地长什么样。

## 5｜要做一次真实阻断，再做一次真实恢复

先在授权候选中保留金额错误，确认原检查能定位“应为 120，实际为 50”。再让目标生命周期事件真实触发，核对检查运行记录、处理器响应和宿主反应。

然后修复金额实现，保持检查标准不变，重新触发同类事件并运行最终检查。一次完整交接需要把“错误时阻断”和“恢复后通过”对应到各自的代码版本。

手动给处理器输入一个 Stop 事件，适合检查适配逻辑；它并不能证明真实宿主已经加载配置或触发过事件。讲师参考截图也不能替代你的事件记录。

参考处理器还有防止重复进入的分支：遇到相应重入标记时会跳过再次检查。这是避免反复触发的安排，**跳过不等于得到一份新绿报告**。最终交付仍要确认当前候选有有效复验。

超时也一样。外层等待到期只说明这次等待结束，不能据此声称子进程都已安全退出，更不能把没有结果写成“通过”。应保留当前状态，检查进程和报告后再决定继续还是人工接管。

## 6｜不要只修出一个“120”

订单草稿不仅有金额。数量为 0 或负数、商品无效等输入应被拒绝，失败后不应遗留不该存在的草稿或明细；正常建立草稿也不应提前预占库存。

> **案例｜换输入，排除写死答案**
>
> 换一组数据：3 件每件 25 元，另 2 件每件 18 元，总额应为 **111 元**。如果实现永远返回 120，第一组示范会“成功”，这组就能揭穿它。

迁移检查不是擅自扩张项目，而是在相同规则下换输入，验证你理解的是“逐行数量乘单价再求和”，不是一个课堂常量。

这次产品增量是可正确使用的订单草稿；工作台增量是关键节点复用同一质量入口的触发能力。二者有因果关系：真实订单修改暴露了“改完忘了查”的风险，Hook 用于减少漏检，而不是替代业务检查和人工验收。

## 7｜现在去实践手册做什么

打开[实践操作手册](实践操作手册.md)：

1. 实践 1～2：准备环境、看清订单规则。先知道 120 从哪里来，以及草稿不应改变什么。
2. 实践 3：检查参考处理器的输入与响应。分清业务结果和适配协议。
3. 实践 4～5：接入自己的 Hook，并在授权范围内交付订单草稿。
4. 实践 6：取得真实宿主事件的失败与恢复证据，不能停留在手动模拟。
5. 实践 7：让他人按当前候选复验，保留未验证项。

自测：上午绿、下午改过，能直接交付吗？不能。配置文件存在，能证明事件触发吗？不能。处理器退出 0、响应明确阻断，能只凭这个 0 认定业务通过吗？不能。

遇到具体协议、重入或来源问题，再查[参考详解](参考详解.md)。本讲应记住的是：**该检查的版本，在该检查的时机，确实调用同一个质量入口；失败要被如实传到作出下一步决定的人或程序。**
