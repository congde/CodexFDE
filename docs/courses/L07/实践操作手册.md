# L07 实践操作手册｜让检查真的发生

> 本资料由 AI 辅助整理，为课程赠送资料，用来辅助你实践练习，非必读资料。

本实践需要区分三种证据：真实业务服务的结果、处理器协议的分支、真实 Codex 事件的触发。阅读[讲义](辅导资料.md)后，先填写[提交模板](SUBMISSION.md)的首次预测，再运行实验。

按“业务要求 → 漏检诊断 → 机制观察与设计 → 生成待审文件 → 安装后真实事件 → 最终复验与效果判断”执行。`hook_staging/` 属于本次候选中的待审产物，不是现成附件；文件生成前不要调用它，也不要直接改活动 Hook 来绕过准备过程。

开始操作前，遇到解释器、路径或输出问题，按[执行与排错说明](../../reference/实操手册执行与排错.md)核对。

## 2. 先看业务状态

<!-- step-guide-2 -->
> **一句话说明：**先观察真实订单创建的成功和失败状态，再把这些业务事实变成候选中的检查。

**运行前确认：** 在 CodexFDE 中通过项目登记或 `FLOWERP_PROJECT_ROOT` 指定独立 FlowERP 仓库的绝对路径，完成[客户环境检查](../../reference/实操手册执行与排错.md#product-environment)。下面命令仍从 CodexFDE 运行，`order_state_lab.py` 会自动使用独立 FlowERP 的解释器运行业务观察。第 2.1 节检查模板仍须接入自己的候选，由候选统一入口运行，并核对业务源码来源。

![订单实验需要观察的金额与业务状态](assets/diagrams/01-order-state.png)

先手算图中金额，再运行实验。特别检查失败请求没有留下订单或明细，以及创建草稿前后库存不变。

```bash
python -X utf8 docs/courses/L07/examples/order_state_lab.py
```

阅读脚本，找到独立预期 `12000`、两行明细和失败后状态的断言。预期草稿订单总额为 12000 分，库存不变，数量为零与第二行不存在分别被拒绝且没有残缺记录。输出是实际参考服务的观察。

将例子改成另一组数量和单价前，先手算金额。不要仅让“总额等于程序返回明细之和”作为唯一检查：如果二者共用错误公式，它们可能一起出错。

本讲允许零库存创建草稿；创建并未预占。不要沿用旧行动卡中的“缺货不能创建任何订单”。库存原子预占属于 L08。

### 2.1 把观察变成候选中的真实检查

先执行[L06 检查接入手册](L06检查接入手册.md)：使用自己的 L06 库存实验当前绿报告，经来源复核后，将原检查与本讲三个订单检查登记进独立 L07 候选。保存注册回执，核对七项指定阻断检查，再运行完整集合。旧导入 session 不适用；不要将小运行器文件直接重命名为 `eval.harness`。

[order_contract_checks.py](examples/order_contract_checks.py)提供三个参考函数：`draft_amount`、`rejected_order_has_no_residue`、`amount_transfer`。接入脚本已将这三个函数登记到当前候选的统一入口；这里阅读实现并核对实际执行结果，不再重复注册。保留既有检查；不要把参考终态导入个人候选来冒充本人的实现。该文件不自动添加控制仓库的搜索路径，运行时仍须核对实际加载的 `flowerp` 与 `eval.harness` 来源。

两行金额预期为 12000 分；失败用例比较订单头、明细、库存三张表的前后状态；迁移用例手算 3×2500+2×1800=11100 分。检查自己的注册表，确保这三项确实被选中，而不是只运行原有一行金额用例。

### 2.2 对个人候选作出首次诊断

本节先调查，不提前制造缺陷。若个人候选还没有草稿订单实现，记录“功能待实现”，在第 5 节形成候选后回到本节完成诊断，再进入安装验证。

1. 记录最后一次订单修改的版本与 Diff，找到最后一份检查报告，核对两者先后及报告来源。
2. 在该候选自己的虚拟环境中运行 `python -X utf8 -m eval.harness --suite blocking`，立即记录退出码，并核对第 2.1 节的实际用例名。参考脚本输出不能替代这次运行。
3. 对照[辅导资料](辅导资料.md)第 1～2 节的版本与调用判断，分别判断覆盖是否充分、对象是否正确、检查是否完成、结束时是否遗漏调用。环境失败单独记录。
4. 在提交模板保留首次判断和调查后的修订。只有检查能发现当前业务错误，才进入“自动触发是否补上遗漏”的验证；未发现业务错误时，第 5.1 节另建授权教学副本作对照。

这里要交出的决定是“改哪里以及为什么”。缺断言就补 Eval，测错代码就纠正环境，漏调用才增加事件连接；多种问题并存时列出修复顺序。

## 3. 检查适配器的六种输入

<!-- step-guide-3 -->
> **一句话说明：**用六种输入检查 Hook 适配器，分清真实失败、空输出、错误格式和运行异常。

![三层证据分别支持什么结论](assets/diagrams/02-protocol-layers.png)

本节只验证中间的适配层。输出中的模拟业务结果与模拟事件，都不能替代第 6 节的真实触发记录。

以下命令调用真实参考处理器，但用替身代替其子进程，不执行 Harness，也不启用 Hook：

```bash
python -X utf8 docs/courses/L07/examples/hook_protocol_lab.py pass
python -X utf8 docs/courses/L07/examples/hook_protocol_lab.py block
python -X utf8 docs/courses/L07/examples/hook_protocol_lab.py reentry
python -X utf8 docs/courses/L07/examples/hook_protocol_lab.py malformed
python -X utf8 docs/courses/L07/examples/hook_protocol_lab.py timeout
python -X utf8 docs/courses/L07/examples/hook_protocol_lab.py command-error
```

| 模式 | 关键观察 | 你的解释任务 |
|---|---|---|
| pass | 调用 1 次，处理器返回 0，continue 为 true | 区分协议完成与真实业务通过 |
| block | 调用 1 次，处理器返回 0，decision 为 block | 解释为何退出 0 仍要求续跑 |
| reentry | 调用 0 次，返回避免重复续跑信息 | 说明为何不能给当前修复盖绿章 |
| malformed | JSONDecodeError，调用 0 次 | 定位输入故障，不能归因金额公式 |
| timeout | TimeoutExpired，没有合法响应 | 替身抛错不证明真实宿主超时行为 |
| command-error | FileNotFoundError，没有合法响应 | 记录未完成验证，不能借用旧报告 |

包装实验完成观察时本身可以返回 0。要检查 JSON 内的 `handler_return`、`exception`、`response` 与调用次数。`subprocess_timeout_configured=false` 表明参考适配器没有向内部调用传入超时值。

保留完整 stdout；尝试将其作为一个 JSON 解析。不能从混有日志的字符串里截出看似正确的一段当协议成功。


## 4. 在自己的候选中建设 Hook

<!-- step-guide-4 -->
> **一句话说明：**在个人候选中建设 Hook，让提交前检查与正式 Eval 使用同一套判定入口。

先使用[调查提示词](prompts/01-确认事件与来源.md)检查候选中的 `.codex/hooks.json` 和 `.codex/hooks/quality_gate.py`。从配置沿调用链读到统一 Harness，记录实际命令、解释器、工作目录、来源与内容指纹。审查前不要复制粘贴启用未知脚本。

参考配置依赖 PATH 中的 Python。你可以在隔离练习副本中改为显式调用项目解释器。以下是配置中两个字段的示例，保留现有外层 `hooks/Stop/hooks` 结构；没有自动写入你的项目：

```json
{
  "command": "\"$(git rev-parse --show-toplevel)/.venv/bin/python\" \"$(git rev-parse --show-toplevel)/.codex/hooks/quality_gate.py\"",
  "commandWindows": "powershell -NoProfile -Command \"$r = git rev-parse --show-toplevel; & (Join-Path $r '.venv/Scripts/python.exe') (Join-Path $r '.codex/hooks/quality_gate.py'); exit $LASTEXITCODE\""
}
```

这两个字段只解决解释器与脚本定位。还需要在处理器中验证候选目录，将内部 `subprocess.run` 的 `cwd` 明确指向该候选。不要盲信任事件里任意目录：将解析后的路径与本次授权候选比较，不一致就报告配置问题。

用[实现提示词](prompts/02-连接检查与候选.md)补齐自己的处理器：保持调用同一 Harness，诊断送 stderr，stdout 只返回当前协议；设计内部超时与外层时限，异常时保留“未验证”原因；明确重入跳过后如何触发最终复验。内部超时值应小于外层时限并留出输出余量，不能只修改一个数字就声称能终止进程树。

对自己的处理器重做六类测试。课程脚本默认读取仓库参考处理器，不会自动测试另一个目录的个人实现；在自己的测试中明确加载个人文件，记录其路径和指纹。另用短时本地等待程序验证真实内部超时与进程结束，将它和替身实验分开记录。

Codex 将待审查配置与处理器写入 `hook_staging/hooks.json` 和 `hook_staging/quality_gate.py`。暂存目录不会被宿主当成项目 Hook 自动加载；活动 `.codex` 仍受执行保护。先只读检查本次课程范围：

```bash
python -c "from workbench.course_mainline import LESSONS; from workbench.execution import normalize_write_scope; print(normalize_write_scope(next(x.write_scope for x in LESSONS if x.number == 7)))"
```

应显示 `flowerp`、`eval`、`tests`、`hook_staging`，含义是上述隔离候选的写入范围。旧版本曾把 `.codex/hooks` 放进写集，导致任务创建即报受保护路径；遇到该错误先更新控制工作台的课程投影。不要取消 `.codex` 全局保护。

在沿用的控制运行目录中提交真实执行：


返回后按[提交结果与续做说明](../../reference/实操手册执行与排错.md#course-result)先保存退出码、任务编号和候选路径，再查看候选的 `.course/product-source.json`，核对客户源码是否来自本次指定的独立 FlowERP。退出 0 且状态为 `review`、来源正确，才继续候选复验；非零先查原任务错误，不重复提交，不用控制仓库替代缺失候选。

课程默认投影主要选 `order_total_matches_lines`，这个用例只覆盖一行金额。检查自己的候选是否已经增加本章多行和失败后状态用例；仅默认通过不代表新增要求全部执行。

在候选自己的虚拟环境中先运行已知入口：

再运行你新增用例的实际命令及完整阻断套件。记录用例名称、数量、报告和进程退出码。PowerShell 在运行后立即查看 `$LASTEXITCODE`；macOS/Linux 查看 `$?`。环境缺失引起的失败不能写成目标业务红灯。

### 5.1 再看真实子进程，不混淆手工输入与宿主事件

参考 [完整失败记录](assets/latest/hook-red.json)使用手工 Stop 输入启动真实处理器，内部确实运行候选 Harness。它不同于上面的替身实验，但仍不是宿主自动触发。

![真实检查产生 block 协议](assets/latest/hook-red.png)

图 3｜两项金额失败，一项状态检查通过；外层处理器退出 0，响应为 block。先核对内部结果，再解释外层退出码。

先核对第 5 节返回的实际候选及 `hook_staging/quality_gate.py`，审查源码后再调用。若该候选仍有实际业务失败，先显式运行 Harness 确认目标红灯；若已经通过，不要改坏正式交付候选，应另建明确授权的隔离教学副本，保留同版处理器，再注入教学缺陷。记录副本来源、允许文件和预期，手工故障实验与正式任务复验分别留证。PowerShell 切换至本次实验的实际目录，确认解释器与源码位置后运行：

```powershell
$taskCandidate = (Get-Location).Path
if (-not (Test-Path -LiteralPath 'hook_staging/quality_gate.py' -PathType Leaf)) { throw '尚未生成个人处理器，请先完成第 5 节并核对实际候选' }
@{ hook_event_name='Stop'; cwd=$taskCandidate; stop_hook_active=$false } | ConvertTo-Json -Compress | python -X utf8 hook_staging/quality_gate.py
$LASTEXITCODE
```

这个命令只验证手工输入链路；安装后的真实事件必须另做第 6 节。保持缺陷不变，把输入改为重入，检查个人策略。参考实现会跳过，再显式运行 Harness 仍失败：

![重入跳过没有修复业务错误](assets/latest/explicit-still-red.png)

图 4｜重入返回 continue 与本图的退出 1 可以同时成立。复核报告指纹和原始输出，不能把跳过改名为通过。

最后在同一实验副本修复公式并运行原检查，保留失败前后来源。参考实验由教师注入并恢复；学生须记录自己的实际操作，参见 [完整证据说明](assets/README.md)。第 6 节回到正式交付候选，核对待安装处理器的版本；教学副本的绿灯不能替它签收。

## 6. 取得真实事件的失败与恢复证据

<!-- step-guide-6 -->
> **一句话说明：**制造一次真实 Hook 失败并修复，在同一候选中保留失败和恢复两份证据。

先在返回的实际候选目录中审查 `hook_staging/hooks.json` 和 `hook_staging/quality_gate.py`，核对配置指向安装后的处理器、统一 Harness、解释器及 cwd。记录任务编号、候选版本、暂存文件的内容指纹与实际审查者。处理器本身的改进仍应在暂存文件中完成，并先测试这份个人实现。

人工将两个已审查文件分别安装到 `.codex/hooks.json` 和 `.codex/hooks/quality_gate.py`。已有配置时先保留原件，逐项合并，不直接覆盖其他规则。以下 PowerShell 步骤仅适用于两份目标文件都不存在的候选，并在存在时停止：

```powershell
Get-Location
Get-FileHash -Algorithm SHA256 hook_staging/hooks.json, hook_staging/quality_gate.py
if ((Test-Path -LiteralPath '.codex/hooks.json') -or (Test-Path -LiteralPath '.codex/hooks/quality_gate.py')) { throw '目标已存在，请先保留原件并审查合并' }
New-Item -ItemType Directory -Path '.codex/hooks' -Force | Out-Null
Copy-Item -LiteralPath 'hook_staging/hooks.json' -Destination '.codex/hooks.json'
Copy-Item -LiteralPath 'hook_staging/quality_gate.py' -Destination '.codex/hooks/quality_gate.py'
Get-FileHash -Algorithm SHA256 .codex/hooks.json, .codex/hooks/quality_gate.py
```

macOS/Linux 可用编辑器完成相同的两份文件安装与合并，并用 `shasum -a 256` 比较暂存和安装后的内容。安装不等于获得宿主信任，也不会替你验证事件。保留安装前后内容、审查决定及最终指纹，在提交包中将这项人工操作与原任务关联；不把它伪称为 Codex 写集内的改动。


工作台提交成功不自动证明 Hook 已被安装或触发。完成上述人工安装步骤后，在对应候选中使用支持当前 Hooks 的 Codex CLI 检查 `/hooks`，核对配置来源、审查和信任状态。以当前安装版本及[官方说明](https://learn.chatgpt.com/docs/hooks)为准。

先在隔离候选保留一个能够被统一 Harness 发现的金额缺陷。若是人为注入，标为教学缺陷并记录最小 Diff。安排一次正常的结束尝试，保留宿主实际事件、处理器输出、检查结果与续跑记录。手工输入同样 JSON 只算协议测试，不能算此步骤完成。

先保持金额缺陷与断言不变，比较显式调用与真实事件调用是否得到同一业务失败；保留处理器版本、运行环境及报告来源，才能把差异归因到触发连接。

修复缺陷后显式重跑同一 Harness，记录最终候选。参考处理器在重入时会跳过检查，所以“结束了”不足以证明“修好了”。同时取得正常通过的真实触发记录，并比较失败、恢复两次的来源和实际运行命令。

如果当前宿主没有可用 Hooks、未取得真实事件，或非交互执行没有加载项目配置，记录具体版本和现象，继续完成业务与适配器测试；真实事件项保持未完成。不要生成事件记录补位。

| 常见现象 | 调查方向 |
|---|---|
| 文件存在却没有触发 | 宿主版本、项目来源、信任状态、事件是否发生 |
