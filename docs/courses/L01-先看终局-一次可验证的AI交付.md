# L01｜先看终局：一次可验证的 AI 交付怎样完成

- **核心内容**：课程最终成品、四周路线、生成完成与验收完成的区别。
- **演示结果**：输入一个小型真实需求，依次看到 Spec、代码变更、测试结果和交付摘要。
- **课内增量**：运行环境检查，并让 Codex 输出“结构、约束、验证命令、风险”四段式接手报告。
- **通过标准**：环境检查通过；接手报告能指出真实的仓库命令和一项风险。

> 课程建设状态说明：本讲教学目标、活动、产物与评价规则属于已经形成的课程设计；学生学习记录、达成率、增值数据和教学效果属于待真实开课采集的证据。不得用参考仓库运行结果或模拟数据替代学生达成证据。

## 大纲锚点与前沿校准（2026-08-19）

- **大纲锚点**：环境检查和四段式接手报告是唯一课内增量；通过线只看真实命令与具体风险。
- **前沿采用**：采用证据优先、只读探索、最小权限和不受信任输入防护；结构化输出只用于稳定记录，不替学生核验。
- **不越界**：不以新模型、新工具或页面效果替代“Spec—Diff—测试—摘要”证据链，不在本讲编码。
- **链路交接**：把接手中发现的跨会话风险交给 L02 判断是否晋升为仓库规则。详见[16 讲主线与前沿校准矩阵](./16讲主线与前沿校准矩阵.md)。

### 可观察学习成果

完成本讲后，学生应能：

1. 用一句话说明四周最终作品以及 V0—V3 的累积关系；
2. 沿同一个需求身份指出 Spec、Diff、测试结果和交付摘要；
3. 区分生成完成、运行完成、验收完成和发布完成；
4. 独立运行课程环境检查，保留命令、关键输出和退出码；
5. 提交四段式接手报告，并对 AI 初稿作至少一项有证据的修订；
6. 复核同伴的一条命令和一项风险，并识别同提示 AI 输出的至少一处分歧，给出“证据支持、仅为推断或当前未知”的判断。

## 大模型编程使用规范基线

本讲采用以下八条工作约定。它们是 OpenAI、Anthropic 与 GitHub 官方实践中相互印证的工程共识，不宣称是统一国家标准：

1. **先探索，后修改**：先理解职责、调用链、校验点和风险，再决定是否授权写入；
2. **任务必须有合同**：明确目标、上下文、允许动作、禁止动作、输出证据和停止条件；
3. **权限必须可执行**：用 Sandbox、工作区和审批策略强制边界，不能只在提示词里写“不要修改”；
4. **坚持最小化**：只提供任务需要的上下文、工具、网络和写入范围；
5. **区分发现与验证**：模型发现一条命令，不等于已经运行；模型运行成功，也不等于完成验收；
6. **AI 输出只是候选产物**：学生必须核验、修订并接受独立复核，模型不能给自己的工作签收；
7. **保护数据与知识产权**：不输入密钥、个人信息、客户数据和未经授权的私有材料；
8. **诚实处理不确定性**：证据不足时写“未知”并说明缺口，不推测、不补造、不跨级宣布完成。

### 六段式 AI 任务合同

后续课程中的每次 AI 编程委托，至少回答六个问题：

| 合同项 | 必须回答的问题 |
|---|---|
| 目标 | 要形成什么可检查结果，为什么需要它 |
| 上下文 | 哪些文件、目录、Issue、Spec 或既有模式与任务相关 |
| 允许动作 | 可以读取、搜索、执行或修改什么 |
| 禁止动作 | 不得联网、写入、安装、扩范围或触碰什么数据 |
| 输出与证据 | 用什么结构返回，哪些声明必须附路径、命令、状态或 Diff |
| 完成与停止 | 什么条件算完成；何时必须写未知、请求确认或安全停止 |

提示词负责表达意图，权限配置负责限制能力，测试与人工复核负责判断结果；三者不能互相替代。

## 本讲行动工单：在作者缺席时完成一次可信接手

学员不是参观 FlowERP，而是在 45 分钟内接手一个陌生仓库：建立环境指纹和命令证据账，让 Codex 生成四段式初稿，至少找出一条无证据、过期或完成等级错误的结论并修订，再把报告交给同伴冷复现。讲师必须准备一条“发现了命令但未执行”或“运行成功却被写成发布完成”的诱饵；若所有信息都已在讲解中揭晓，本讲降级为导览，不得判定达成。

- **工作台增量**：仓库接手协议、证据账、完成等级判定和风险表达；
- **FlowERP 产品状态**：只读建立业务基线与产品路线，业务账不变；该基线必须能支撑 L04 首个库存导出增量；
- **失败证据**：AI 初稿中至少一条结论被仓库事实反驳，保留修订前后版本；
- **迁移证据**：在个人仓库重做四段式报告，指出至少一项环境或验证入口差异；
- **不付费也能得到的内容**：目录介绍、最终页面截图和讲师口述——这些不能计入学生作品。

## 二、课前准备与学情诊断

### 讲师课前硬门槛

讲师必须准备一套固定的 L01 终局演示证据包。四类材料必须属于同一个小型需求，并使用同一个需求编号：

| 材料 | 最低要求 | 课前核验方式 |
|---|---|---|
| Spec | 有目标、非目标、约束和可执行验收项 | 抽查一条验收项能否定位后续证据 |
| Diff | 有明确基线版本和交付版本，只包含该需求的最小变化 | 记录两个版本标识；不使用无法复原的临时工作区 |
| 测试结果 | 包含真实命令、关键断言、运行环境和退出码 | 课前在授课环境重新运行 |
| 交付摘要 | 列出修改文件、验证命令、已验证范围和剩余风险 | 检查每条结论能否回指前三类材料 |

当前仓库尚未提供独立、冻结的 L01 演示证据包时，该项应标记为“待建设”，不能用讲师口述、绿色截图或不相关需求的材料临时拼接。

### 学生课前诊断

学生在使用 Codex 前独立提交三道诊断题，不按答案正确率简单计分：

1. “模型已经生成代码”能否说明需求已经完成？为什么？
2. 看到测试退出码为 0，还需要知道哪些信息才能判断验收范围？
3. 打开陌生仓库后，你会先查哪三类信息？

诊断结果用于分层支持：

- 起点 A：命令行或仓库导航困难，提供路径定位卡和结对运行支持；
- 起点 B：能够运行命令但风险表达空泛，提供“对象—证据—影响—反证条件”句式支架；
- 起点 C：能够完成基线任务，增加个人仓库迁移和反例质询任务。

线上精讲负责问题框架、核心模型和关键示范，不替代线下实际运行。

| 时间 | 学习活动 | 学生当场证据 |
|---:|---|---|
| 0—5 分钟 | 判断冲突：只有生成结果或绿色页面，能否签收 | 首次完成等级判断 |
| 5—12 分钟 | 浏览固定证据包：Spec—Diff—测试—摘要 | 四类产物定位表 |
| 12—18 分钟 | 反推四周 V0—V3 工作台路线 | 版本累积关系图 |
| 18—25 分钟 | 建立四层完成状态模型并处理三个反例 | 修订后的完成等级判断 |
| 25—30 分钟 | 示范接手四段式，发布线下任务与硬性退回项 | 线下行动清单 |

### 1. 终局不是页面，而是一条证据链

讲师输入一个范围小、能够快速理解的真实需求，只展示已经准备好的终局结果，不在 L01 现场实现。演示顺序固定为：

| 环节 | 要看的对象 | 它回答的问题 |
|---|---|---|
| Spec | 目标、非目标、约束和验收项 | 到底承诺交付什么 |
| Diff | 与 Spec 对应的最小代码变化 | 实际改变了什么 |
| 测试结果 | 命令、断言、环境和退出码 | 当前证据支持哪些验收项 |
| 交付摘要 | 修改文件、验证结果和剩余风险 | 下一位评审者怎样复验 |

演示必须守住四条证据规则：

- 四类产物具有同一个需求身份；
- Diff 能回指验收项，不靠口头补充范围；
- 测试展示真实命令和退出码，不只展示绿色截图；
- 摘要同时写明已验证范围、未验证事项和剩余风险。

### 2. 四周不是四个独立 Demo

| 周次 | 版本 | 本周解决的问题 | 主要产物 |
|---:|---|---|---|
| 第一周 | V0 单 Agent 最小交付 | 把模糊需求变成可验收任务 | 仓库约束、Spec、执行入口和摘要 |
| 第二周 | V1 自动质量流水线 | 让关键要求能够自动复验 | Eval、Harness、Hook 和 CI 报告 |
| 第三周 | V2 可控多 Agent 协作 | 让修复和协作有边界、有停止条件 | Repair Task、Loop、Subagents 和 Graph |
| 第四周 | V3 可演示工作台 | 让链路服务化、可视化并留下反馈 | Task API、Web、摘要、反馈和冷启动 |

```text
仓库约束 → Spec → 最小变更 → Eval → Harness → Hook/CI
→ Repair Task → Loop/Subagents/Graph → API/Web → 摘要/反馈 → 冷启动
```

### 3. 四层完成状态

| 状态 | 可以诚实声明什么 | 不能据此声明什么 |
|---|---|---|
| 生成完成 | 已产生候选 Spec、代码或文档 | 不能证明可以运行 |
| 运行完成 | 某条命令在明确环境中执行过 | 不能证明覆盖了验收项和失败路径 |
| 验收完成 | 已声明的验收项有可重复证据支持 | 不能外推到所有未知场景 |
| 发布完成 | 他人能在受控环境部署、运营和回滚 | 不能证明天然合规或永不失败 |

快速反例：

1. 只有生成代码，没有运行命令：生成完成。
2. 命令退出 0，但不知道对应哪条验收项：运行完成。
3. Spec、Diff、测试和摘要能相互追溯：可以在已声明范围内判断验收完成。
4. 页面显示成功但没有权威状态和后端证据：不能提高完成等级。

## 四、线下行动课：60 分钟完成第一次仓库接手

线下任务不再重复讲四层状态，而是让学生实际运行、取证、反证和修订。

| 时间 | 学生活动 | 形成性证据 |
|---:|---|---|
| 0—10 分钟 | 检查工具、仓库基线、运行位置和只读权限 | 版本、提交、权限、网络和退出码记录 |
| 10—20 分钟 | 先手写仓库判断，并追踪一条 `doctor` 调用链 | 首次判断与调用链草图 |
| 20—36 分钟 | 用六段式合同委托 Codex 只读接手 | AI 初稿、运行溯源与引用路径 |
| 36—48 分钟 | 学生核验并标注证据、推断、未知和执行状态 | 修订说明与报告第二版 |
| 48—56 分钟 | 同伴复核命令、风险及两份输出的差异 | 复核记录、反证条件和分歧判断 |
| 56—60 分钟 | 完成离场票并提交待解决问题 | 完成等级判断与问题单 |

### 1. 建立课程环境基线

先把“只读”变成真实权限边界：

- Codex 桌面端或 IDE：在权限设置中切换到只读模式，记录运行位置与网络状态；
- Codex CLI：使用 `read-only` Sandbox；审批策略不得允许静默扩大权限；
- 其他代理工具：使用其等价的只读工作区或隔离环境，并记录具体配置；
- 无法证明只读边界时，不运行 Agent，只完成学生人工仓库检查。

然后在仓库根目录执行基线检查：

```powershell
python --version
git --version
codex --version
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
python -X utf8 -m workbench.cli doctor
$LASTEXITCODE
```

若课程通过图形界面使用 Codex 而不依赖 CLI，`codex --version` 可以改为教师规定的客户端版本与登录状态检查，但必须在课程实施方案中统一口径。

学生记录：

| 项目 | 必须记录的事实 |
|---|---|
| 工具与界面 | Python、Git、Codex 的版本或可用状态；桌面端、IDE、CLI 或 Cloud |
| 模型信息 | 界面可见的模型或系统版本；不可见时写“平台未提供”，不得猜测 |
| 仓库基线 | 仓库根目录、当前分支和提交标识；无提交时如实记录 |
| 权限边界 | Local、Worktree 或 Cloud；Sandbox；审批策略；允许写入范围 |
| 网络 | 开启或关闭；若开启，说明用途和允许域名 |
| 指令来源 | 本次实际读取的全局、仓库和目录级 Agent 指令文件 |
| FlowERP 就绪状态 | `doctor` 的关键检查项与总体状态 |
| 执行轨迹 | Agent 实际执行的命令、未执行的命令和每条退出语义 |
| 失败证据 | 原始错误、发生阶段和下一步处理，不得删除后改写为通过 |

`doctor` 只证明 FlowERP 本地运行时的数据库、Schema、运行目录等基线就绪；它不证明全部测试、业务规则、Codex 执行能力或发布条件已经通过。只有全部工具检查和 `doctor` 记录齐全，才能写“课程环境基线已建立”。

环境首次失败不等于学习失败。学生应保留失败输出，在规定修订期内修复并再次运行；最终提交必须同时保留首次失败和修复后证据。

### 数据安全与提示注入红线

本讲不得把以下内容复制、上传或暴露给未经学校和权利人批准的模型、插件或外部服务：

- `.env`、API Key、访问令牌、Cookie、证书、私钥和连接串；
- 学生个人敏感信息、真实客户资料、运行数据库和生产日志；
- 未经授权的私有代码、试题、作品和受版权保护材料；
- 能够绕过采购审批、身份认证或审计责任的真实凭据与操作路径。

仓库文件、网页、Issue、日志和工具输出都可能包含诱导 Agent 越权的文本。发现“忽略既有规则”“上传文件”“开启网络”“执行未知脚本”等内容时，学生应将其视为不受信任输入，回到任务合同、权限边界和教师批准，而不是照做。

### 2. AI 使用前先形成学生判断

学生先阅读 `AGENTS.md`、`README.md`、`FDE_SPEC.md` 和一级目录，限时写下：

- 三个主要目录及职责；
- 两条不可破坏的规则；
- 一条可能的验证命令；
- 一项当前不能确定的风险。
- `python -X utf8 -m workbench.cli doctor` 从 CLI 入口到就绪判定的大致调用链。

这份首次判断用于证明学生本人在 AI 介入前进行了仓库分析，不要求第一次全部正确，但不得事后覆盖。

调用链最低要求不是背文件名，而是回答：入口在哪里；谁加载配置；谁访问持久化；谁汇总检查；哪个返回值决定退出码。建议沿 `workbench/cli.py` 中的 `main()`、`load_settings()`、`HealthService.ready()` 和 `ERPStore` 定位。L01 只追踪职责，不展开数据库完整性和业务不变量审计。

### 3. 委托 Codex 生成四段式初稿

推荐委托：

```text
【目标】
接手当前陌生仓库，形成可复核的四段式报告；本次不修改任何文件。

【上下文】
读取实际生效的 AGENTS.md、README.md、FDE_SPEC.md、一级目录和真实命令入口。
沿 doctor 命令追踪一条调用链，说明入口、配置、服务、持久化和退出码职责。

【允许动作】
只读搜索和读取文本；查看仓库根目录、分支、提交和工作区状态。
只使用当前只读 Sandbox 已允许的工具。

【禁止动作】
不写文件，不安装依赖，不提交或推送，不开启网络，不读取密钥、运行数据库或个人数据，
不执行会改变业务、运行时或外部系统状态的命令，不自行扩大范围。

【输出与证据】
按“结构、约束、验证命令、风险”四段输出。
结构中包含 doctor 调用链；每项关键结论附文件路径和可定位位置。
验证命令分别标记：仅发现、已执行、执行失败、未执行。
风险使用“对象—证据—影响—反证条件”结构。
另附运行溯源：界面/工具版本、仓库提交、Sandbox、网络、加载的指令来源和实际命令。

【完成与停止】
证据充分时给出限定范围的结论；证据不足时写“未知”和缺少的证据。
若任务需要写入、联网、安装、读取敏感数据或扩大范围，立即停止并说明原因。
```

### 4. 学生核验和修订 AI 初稿

学生不能直接提交 AI 初稿。每一项关键结论必须标注：

| 标注 | 使用条件 | 学生动作 |
|---|---|---|
| 证据支持 | 文件、命令或状态直接支持 | 保留证据位置 |
| 仅为推断 | 结论合理但只有间接证据 | 降低表述强度并写反证条件 |
| 当前未知 | 当前材料不能判断 | 明确缺少什么证据 |

验证命令还必须单独标注执行状态：

| 执行状态 | 含义 | 可以声明什么 |
|---|---|---|
| 仅发现 | 在文档、脚本或配置中找到入口 | 只能声明“仓库定义了该命令” |
| 已执行 | 本人在明确环境中运行并保留输出与退出码 | 可以声明该次运行事实 |
| 执行失败 | 命令实际运行但非零退出或环境异常 | 保留失败，不得写通过 |
| 未执行 | 因权限、时间、风险或依赖未运行 | 写明原因和所缺证据 |

合格风险使用“对象—证据—影响—反证条件”结构。例如：

> 对象：库存预占。证据：`AGENTS.md` 要求预占原子化且可用库存不得为负。影响：若实现先写部分明细再检查余量，订单状态可能与库存流水不一致。反证条件：事务边界和并发失败测试能够证明整个预占过程要么全部成功、要么全部回滚。

“项目可能有 bug”“库存有风险”均不可核验，不计入达成。

### 5. 同伴反证与离场票

同伴只复核三项：

1. 任选一条验证命令，确认入口真实存在、用途描述正确，并写出可能使该命令失效的环境条件；
2. 任选一项风险，确认有直接证据或明确标为推断，并写出能够推翻当前判断的条件。
3. 比较两份针对同一仓库的 AI 初稿，找出至少一项不一致，判断它来自证据差异、表达差异还是模型不确定性。

离场票回答：

- 你的报告目前支持哪一层完成状态？
- AI 初稿中哪一项被你修订，依据是什么？
- 下一讲必须把哪类规则写入仓库，才能让新会话继续守住边界？

## 五、形成性评价量规

本讲采用“硬性门槛 + 四级量规”。量规结果按课程总评方案折算，不在本讲另造一套与课程总评冲突的百分制。

### 硬性门槛

以下任一情况出现，作品退回修订：

- 未运行规定检查，或退出非 0 却写“已通过”；
- 把“仅发现”或“未执行”的命令写成“已执行”或“已通过”；
- 只在提示词中写“只读”，却未记录或无法证明实际权限边界；
- 编造命令、文件、测试结果、版本或风险证据；
- 输入、暴露或提交密钥、个人信息、客户数据、运行数据库或未经授权材料；
- 直接提交 AI 初稿，没有学生核验与修订记录；
- 把生成完成或页面成功写成验收完成、发布完成；
- 删除首次失败、初稿或同伴反馈。

### 四级量规

| 评价维度 | 优秀 | 达成 | 发展中 | 未达成 |
|---|---|---|---|---|
| 结构与约束 | 职责和规则准确，能说明边界与依赖 | 至少三个目录职责和两条规则准确 | 有事实错误或只抄目录名 | 主要内容来自猜测 |
| 验证命令 | 命令、用途、来源和退出语义完整，可复现 | 至少一条真实命令可复制运行 | 命令存在但用途或结果表述不清 | 命令虚构或未运行 |
| 风险判断 | 风险具体，区分证据、推断和未知，并给出影响与反证 | 至少一项风险有对象、证据、影响和反证条件 | 风险空泛或证据仅间接却未降级 | 无风险或编造证据 |
| 权限与溯源 | 运行位置、Sandbox、网络、指令来源、提交和命令轨迹完整 | 能证明只读边界并记录主要溯源字段 | 只写“只读”但配置或轨迹不完整 | 无权限证据或发生越权 |
| 学生修订 | 能指出 AI 初稿问题并依据仓库事实修订 | 至少完成一项有效修订 | 只有文字润色，没有判断变化 | 直接提交 AI 初稿 |
| 同伴复核与表达 | 复核可复现，能解释完成等级和责任边界 | 完成命令、风险和输出分歧三项复核 | 复核只有“同意/通过” | 无复核或无法解释 |

达成判定：六个维度均不低于“达成”，且硬性门槛全部满足。未达成学生依据原失败证据修订后可再次提交。

## 六、持续改进数据口径

本讲只定义数据口径；没有真实开课数据时必须标记“待采集”。

| 指标 | 计算口径 | 对应教学调整 |
|---|---|---|
| 完成等级误判率 | 首次判断中跨级声明完成的人数 ÷ 有效提交人数 | 增加状态反例和完成边界支架 |
| 虚构命令率 | 含不存在或不可定位命令的初稿数 ÷ 有效初稿数 | 加强命令入口定位与复验示范 |
| 风险具体率 | 达到“对象—证据—影响—反证条件”标准的风险数 ÷ 风险总数 | 增加风险句式和正反样例 |
| 修订改善率 | 修订后提升至少一个量规等级的人数 ÷ 完成修订人数 | 判断同伴反馈与教师支架是否有效 |
| 起点增值 | 按课前诊断分组比较首次与二次量规变化 | 调整 A、B、C 三类分层支持 |
| 权限证据完整率 | 完整记录运行位置、Sandbox、网络和审批策略的人数 ÷ 有效提交人数 | 改进权限配置演示和检查表 |
| 执行状态误判率 | 把“仅发现/未执行”写成“已执行/已通过”的报告数 ÷ 有效报告数 | 强化发现、运行、验收三层区分 |
| 输出分歧识别率 | 能发现并正确分类同提示输出差异的人数 ÷ 完成同伴复核人数 | 增加非确定性与交叉验证支架 |

每期课程至少保留匿名化的首次判断、初稿、修订稿、反馈类型和量规结果。不得只用满意度、平均分或参考仓库测试结果证明本讲有效。
