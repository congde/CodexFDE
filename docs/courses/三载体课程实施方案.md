# 三载体课程实施方案｜PPT 引导决策，Markdown 承载教材，VS Code 完成行动

> 本方案是课程大纲的教学投影，不是第二份大纲。16 讲标题、产品增量、工作台增量和通过标准仍以 [`课程大纲`](../课程大纲-Codex-FDE行动营-个人研发自动化工作台.md) 为唯一事实源。

## 一、三个载体不是三份重复内容

这门课的基本教学单元不是“知识点”，而是一次可追溯的工程判断：学生先在信息不完整的现场作出决定，再获得方法和材料，最后进入仓库承担决定的后果。

| 载体 | 唯一职责 | 课堂中必须发生的事 | 禁止退化为 |
|---|---|---|---|
| PPT | 暴露冲突、控制信息、迫使学生签署首次判断 | 学生在看到参考答案前选择做/不做、范围、风险、责任人与证明方式 | Markdown 摘要、代码截图合集、讲师提词器 |
| Markdown | 解释为什么、拆解证据、保留完整教材与修订路径 | 学生用正文和证据附件修订首次判断，并能在课后独立复习 | PPT 逐字稿、术语百科、教师评分表堆叠 |
| VS Code | 在真实仓库中制造失败、修改、复验和交付 | 学生运行同一入口，保留红灯、Diff、绿灯、权威状态和个人说明 | 教师演示录像、复制最终答案、只看终态绿灯 |

三者的顺序是课程合同：

```text
PPT 现场证据 → 第一次签字 → Markdown 查证与建模 → VS Code 主动失败与实现
→ Harness/权威状态复验 → 第二次签字 → Markdown 形成个人证据 → 下一讲 PPT 新冲突
```

## 二、每讲的固定节奏

### 课前：Markdown 只给背景，不给结论

学生阅读连续案例的时间、地点、人物和已知证据，完成 3～5 分钟的术语预检。不得提前展开参考实现、教师量规和最终结论。

### 线上精讲：每讲使用独立 PPTX，围绕四个核心决策节点展开

正式课件是 16 个独立 PPTX，每讲页数不设统一上限。四个节点是内容覆盖合同，不是四页上限；可以增加事故背景、概念解释、证据拆解、失败路径、状态图和复盘页，只要它们帮助学生完成本讲判断。第一次签字必须出现在第 2～4 页并早于方法答案，末页负责切换到 VS Code 和提示第二次签字。

1. **事故镜头**：一张页面、日志、请求或状态快照，说明“现在必须决定什么”。
2. **证据镜头**：只展示足以形成分歧的证据，不替学生解释。
3. **决策镜头**：给出 2～4 个都有诱惑力的选项，学生必须写下选择、依据和最大风险。
4. **后果镜头**：揭示错误路径的代价，命名本讲方法，然后把控制权交给 VS Code。

PPT 不替代任务卡展示完整命令序列，也不堆放无法讲解的长代码。讲师在学生提交第一次签字前不得切到 Markdown 的参考答案。

### 行动课：VS Code 完成五次可观察动作

1. 查看本讲机器合同；
2. 运行或构造稳定红灯；
3. 在受控写集内完成最小变更；
4. 用同一入口复验并核对 ERP 权威状态；
5. 保存 Diff、退出码、证据 ID 和失败后不变状态。

### 课后：Markdown 收束第二次签字

学生回到讲义解释：首次判断哪里对、哪里错；证据如何改变了决定；哪些建议被拒绝；换一个同构项目时哪些规则仍成立。最终证据进入 `lesson-NN-submission/`，不能覆盖首次版本。

## 三、16 讲端到端载体地图

| 讲 | PPT 的决策问题 | Markdown 的教材任务 | VS Code 的关键行动 | 离场证据 |
|---:|---|---|---|---|
| L01 | 页面能打开、测试能绿，是否足以签收陌生系统？ | 建立“可运行、可解释、可复验、可接手”四层终局坐标 | `course-status`，只读检查环境与终局，记录未验证项 | 首次完成度判断、环境记录、真实风险 |
| L02 | “先把库存改成 100”是合理救火还是越权？ | 把安全、业务不变式、写入边界和 DoD 写成可冲突规则 | 对危险/合法请求做规则对抗，修改并复验 `AGENTS.md` | 规则补丁、拒绝理由、合法替代路径 |
| L03 | 三个角色说的“可用库存”都对，谁有权定义合同？ | 从来源、目标、非目标、用例、失败语义和证据定义 Spec | 生成并解析 L03 局部 Spec，补齐用例矩阵，不写业务代码 | 初稿、歧义标注、签字版 Spec |
| L04 | Agent 改得更多、测试也绿，是否更值得签收？ | 解释能力信封、最小 Diff、独立复验和剩余风险 | 在限定写集实现库存导出，检查执行前红、Diff、执行后绿 | 能力信封、范围内 Diff、正反复验 |
| L05 | 一个只在正确代码上通过的测试，真的会抓错吗？ | 从业务损失反推失败优先 Eval 与失败后权威状态 | 对重复入库连续造红，再实现幂等并用同命令转绿 | 两次稳定红灯、库存未污染、同入口绿灯 |
| L06 | 五个检查给出三个结论，谁有最终放行权？ | 区分 case、suite、Harness、等级、decision 与退出码 | 构造 pass/block/observing 信号，核对 JSON、结论和退出码 | Harness 报告、三角校验、分级理由 |
| L07 | 规则和 Eval 都存在，为什么提交仍会漏检？ | 解释 Hook 的时机、信任边界、超时和可操作消息 | 让合法订单放行、非法订单阻断，并验证失败后无残留订单 | Hook 前后状态、消息、正反订单路径 |
| L08 | CI 是绿色但没有 Artifact，能否作为远端验收？ | 建立本地/远端同入口、证据信封和供应链边界 | 修复会撒谎的 Workflow，完成 A 假绿、B 可信红、C 可信绿 | 三次 Run、Artifact、同伴法证记录 |
| L09 | 6000 行日志能否直接授权 Agent 修改整个仓库？ | 把事实压成可追溯、最小写集、可复验的 Repair Task | 从取消未释放报告生成任务，只修授权范围并复验 | `repair-task.json`、写集、修复前后状态 |
| L10 | 跑满三轮应该算成功、失败，还是需要人工接管？ | 建立预算、无进展、振荡、风险和收敛五类停止条件 | 运行收敛与不收敛轨迹，核对失败签名和停止理由 | 两类 Loop History、预算、诚实停止原因 |
| L11 | 三名 Agent 同时写同一文件，是并行还是制造事故？ | 用读写集、子任务合同和主 Agent 责任组织跨团队协作 | 先画冲突图，再并行只读调查，最后串行集成采购申请 | 冲突图、原始子报告、主 Agent 结论 |
| L12 | 质量全绿后，采购能否由模型自动批准入库？ | 分离 Agent 状态、ERP 状态、证据状态与具名人审责任 | 跑批准、打回、匿名失败和崩溃恢复路径并对账 | Graph Trace、具名决定、ERP 前后状态 |
| L13 | API 返回 `202`，是否等于 12 台补货已经完成？ | 区分接收、执行、审核、完成与失败的任务状态语义 | 用两个客户端测试幂等、非法迁移、重启恢复和事件链 | Task ID、状态事件、并发/重启证据 |
| L14 | 昨天的绿色仍显示在页面上，用户会做出什么错误决定？ | 建立状态文案、空/错/旧数据、深链接和四方对账方法 | 启动真实 Web，核对 DOM/API/SQLite/ERP，注入服务失败 | 同一 Task ID 四方对账、错误态、走查记录 |
| L15 | 一句“很难用”应直接变成 blocking Eval 吗？ | 把反馈分诊为产品、工作台、教学或噪声，并治理资产晋级 | 保存原文、判定、生成候选 Spec/Eval，完成独立验证 | 原始反馈、审核决定、Spec/Eval Diff |
| L16 | 拿走作者电脑和记忆，陌生人还能交付未预演需求吗？ | 组织冷启动、发布证据索引、迁移说明和工程答辩 | 陌生环境抽题，新增动态 Eval，现场红→绿→人审→发布 | 全链证据、风险答辩、迁移与剩余边界 |

## 四、载体间必须传递的对象

| 交接 | 必须传递 | 不得传递 |
|---|---|---|
| PPT → Markdown | 学生的第一次选择、依据、最大风险、仍缺证据 | 参考答案、教师评分锚点 |
| Markdown → VS Code | 签字版合同、允许写集、验收矩阵、失败语义 | 大段概念摘要、未验证猜测 |
| VS Code → Markdown | 命令、输入、退出码、报告 ID、权威状态、Diff | “AI 说完成了”、只有最终截图 |
| 本讲 → 下一讲 | 一个仍未解决且由本讲证据暴露的工程矛盾 | 为了串课而虚构的新事故 |

## 五、课程文件怎样对应三个载体

```text
docs/courses/PPT逐讲决策脚本.md          # 16讲核心决策节点母稿，不限制成品页数
docs/courses/ppt/LNN-*.pptx             # 16个独立正式课件
docs/courses/LNN-*.md                   # 学员教材正文与教师附录
course/FlowERP-AI研发工作台.code-workspace # VS Code统一入口
course/tasks/LNN-*.md                   # 行动卡、命令卡、验收卡
workbench/course_mainline.py            # 机器可执行课程合同
```

讲师备课必须同时打开对应的 PPT 镜头、Markdown 讲义、任务卡和机器合同。任何一个载体修改了产品增量、工作台增量或通过标准，都必须回到课程大纲复核；不能让三份材料各讲一套。

## 六、发布门槛

每讲发布前逐项回答：

- PPT 是否只有一个真正需要学生决定的问题，且没有提前泄露答案；
- Markdown 是否能脱离录屏独立学习，并保留首次判断、失败与修订；
- VS Code 是否使用 `.venv`、真实仓库、受控写集和同一个 Eval 入口；
- FlowERP 权威状态是否真的变化，或本讲明确保护了什么不变状态；
- 工作台能力是否被当讲事故触发，并回到 ERP 中验证；
- 陌生人能否只凭任务卡复验，而不依赖讲师口头补充。

满足这些条件，三种载体才组成一讲；任一载体单独“看起来完整”都不算课程完成。
