# L11｜用 Codex 原生 Subagents 并行处理独立任务

**FDE 判断提示**：采购申请涉及哪些业务与研发职责，哪两项工作确实独立，为什么本次值得并行？执行前保留自己的理由，交接时用产品前后状态说明判断是否成立。详见[实践手册](实践操作手册.md)。

本讲通过采购申请建设可追溯的并行协作。人确定接口、范围和接受标准；主 Agent 组织两个原生子代理，分别补测试与只读审查风险；两者完成后主 Agent 串行整合，统一 Harness 检查最终候选。

## 本次要交付什么

FlowERP 保存采购申请的 SKU、数量、原因和稳定身份；合法申请成功，非法输入不产生记录，申请不改变库存。工作台保存两份子任务合同、读写冲突判断、原始结果和主结论来源。采购场景同时需要测试与风险判断，因而检验任务是否真正独立、是否能汇合为同一交付。

按[实践操作手册](实践操作手册.md)推进，在[提交模板](SUBMISSION.md)留存：

1. 首次业务预期、第一次排程和接口决定。
2. 十种声明实验与七种采购实验的个人观察。
3. 固定候选、两份输入输出验收清楚的子任务合同。
4. 实际原生子任务活动、各自原始结果和产物。
5. 一次冲突声明被拒绝，以及修订后的安排。
6. 主 Agent 回查、分歧处理、串行整合与统一复验。
7. 同伴反馈及一次个人项目迁移；Skill 的真实响应与修订。

单 Agent 与多 Agent 的耗时、Token、质量对照是挑战任务。未做对照时不声称已经证明提效。

## 自查标准

| 维度 | 达成证据 | 仍需补做的情况 |
|---|---|---|
| 业务判断 | 申请字段正确，库存不变，拒绝后五表一致 | 只查新增一行或只查异常 |
| 独立性 | 真实读取、写入、版本及共享资源清楚 | 只比较输出文件名 |
| 协作 | 两个原生子任务的合同和实际活动可查 | 只有角色名或串行摘要 |
| 主结论 | 每条发现可回到原始输出和文件依据 | 直接拼接摘要 |
| 整合 | 最终候选运行新增检查与统一 Harness | 引用旧版本局部绿灯 |
| 迁移 | 能解释新场景哪些工作必须等待 | 仅更换角色名称 |

本讲对应 CLO-5。形成性评价比较首次判断、反例后的修订、实际协作和同伴反馈；参考仓库运行结果不代替个人达成。

## 正式大纲合同

- **核心内容**：可并行任务识别、上下文隔离、结果汇总、冲突风险与额外 Token 成本。
- **演示结果**：测试补全与风险审查并行执行，由主 Agent 汇总结论。
- **课内增量**：为两个无文件写入冲突的任务定义清晰输入、输出和验收标准。
- **通过标准**：子任务边界清晰；主 Agent 能追溯每个结论；有写入冲突的任务不强行并行。
