# L11｜用 Codex 原生 Subagents 并行处理独立任务

**本讲只追问一件事：两项工作交给两个 Agent，同时做就一定更好吗？**

本文先教你判断是否独立，再解释委托、汇总与复验。操作见[实践操作手册](实践操作手册.md)，完整案例和成本讨论见[参考详解](参考详解.md)。

## 1｜先把采购申请做对，再谈怎样分工

**提出采购、批准采购和实际收货，是不同的业务动作。**

> **案例｜创建采购申请，不等于货已入库**
>
> 仓库实物有 10 件，已有订单预占 2 件，可用量为 8 件。现在有人提出采购 7 件。

**采购申请**是提出“希望补货”的请求，不是货已入库。创建申请后，实物库存仍为 10，原预占仍为 2，可用量仍为 8；申请应处于待审批的状态，不能凭空出现审批人或收货流水。

同样，批准申请也不等于实际收货。申请、审批、收货是不同动作，不能为了让演示显得完整而跳过人工审批。真正的审批与后续状态控制还要按后续课程规则继续建设。

本讲要交付采购申请创建，并检查非法数量、空理由、未知商品等输入能被拒绝，失败后不污染申请和库存状态。另一张已有申请 OTHER 也应保持不变。参考入口对重复申请编号的处理不能擅自说成收货式的幂等重放，要以实际合同为准。

这项工作有两件可分出的任务：补充测试、审查风险。L10 的 Loop 解决前后多轮如何继续；本讲尝试让独立工作同时进行。但要先判断独立，不能先启动两个 Agent 再碰运气。

## 2｜不写同一个文件，也可能互相干扰

**能否并行取决于读写依赖，不只是修改的文件是否重名。**

> **案例｜没有改同一个文件，仍可能冲突**
>
> 假设甲正在把接口参数 quantity 改名为 units。乙没有碰实现文件，只在另一个测试文件里按 quantity 写调用。两人没有同时写同一个文件，结果仍然可能冲突：乙读取的接口依据在过程中变了。

![接口读写冲突与固定版本后的安全分工](assets/reading-figures-v2/key-example.png)

*读图：上半图是接口依赖冲突，下半图先固定输入再分工。*

甲改变接口，乙仍按旧参数写测试，这是“一方修改、另一方依赖”的冲突。

先固定候选 V1 和接口约定。甲只改指定测试，乙只读实现并报告风险；完成后由主 Agent 依次整合，再检查最终版本。图中的 api.py、service.py、test_api.py 是依赖关系示意，实际文件以采购实验合同为准。

判断时用两个简单概念：

- **读集**：任务必须读取、依赖哪些内容。
- **写集**：任务会修改哪些内容。

两个任务都只读同一份固定代码，通常可以共享。两个任务同时写同一处，或者一方写另一方正在读的内容，都要重新安排：固定输入、隔离副本，或改为串行。

文件之外也有共享资源。两项测试即使代码文件不同，若共用同一个数据库、缓存或报告路径，也可能相互覆盖。数据库与输出目录的隔离也要进入任务边界。

## 3｜Subagent 是独立执行的子任务，不是两个角色名

本讲所说的原生 **Subagent**，是由主 Agent 委托、在自己的执行上下文中承担明确子任务的 Agent。

在同一段回答里写“测试专家认为……审查专家认为……”，不等于真的启动了两个独立子任务；用普通程序并行跑两段函数，也不自动等于原生 Subagents。

“上下文独立”同样不等于“文件天然隔离”或“权限天然受限”。两个子任务可能仍看到同一工作区。边界必须写清，执行后还要检查，不能寄希望于名称或角色设定。

本讲的真实协作证据需要能追溯子任务身份、输入版本、执行记录和结果。两段顺序生成的文字不能冒充实际并行。若当前环境无法执行原生子任务，应标记这部分待完成，不编造活动记录。

具体启用与调用方式按配套手册及对应工具说明执行，本文不把某一版本的界面布局当成固定知识。

## 4｜给两个子任务各写一份小合同

在采购申请的稳定候选 V1 上，可以这样分工：

| 项目 | 子任务甲：补充测试 | 子任务乙：风险审查 |
|---|---|---|
| 共同输入 | 已固定的采购规则、候选 V1、接口约定 | 同一规则、同一候选 V1 |
| 读取内容 | 实现接口、已有测试和必要规则 | 实现、相关约束与必要记录 |
| 允许修改 | 指定采购测试文件 | 不修改项目代码，只在独立证据位置输出报告 |
| 输出 | 测试差异、运行命令、实际结果 | 风险位置、触发条件、依据与复现建议 |
| 停止条件 | 需要改业务实现或接口时先返回 | 证据不足时标记待核实，不自行修实现 |

实际委托必须使用真实路径，而不是“测试相关文件”这种模糊范围。例如配套采购实验指定的测试文件，只能在确认的候选中修改；不要把图里的示意文件名复制过去。

“只读审查”指不改项目实现，不是说报告不能落盘。若要保存报告，为它分配独立路径，并明确这项输出权限。

主 Agent 同时也受约束：子任务执行期间，不擅自改变它们正在依赖的候选接口。发现需要改，先协调停止或更新输入版本，不能让两个结果各自基于不同事实。

课程中的声明检查器可以检查你写下的读写集合是否冲突，但不能证明所有隐含依赖都已声明，也不能当作运行时权限隔离。最终仍须检查真实行为和差异。

## 5｜两份报告回来了，为什么还不能直接宣布成功

甲说“测试全部通过”，乙却指出“创建申请时可能提前改库存”。两份结论并不一定互相矛盾：甲的测试可能只检查申请被创建，没有覆盖库存保持不变。

先追查两份报告是否来自同一版候选，再看各自检查了什么。若乙给出了可复现条件，主 Agent 应验证该风险，必要时补充原本缺失的断言。不能按“一票通过、一票反对”投票决定业务事实。

**汇总不是拼接摘要。** 主 Agent 要把每个结论对应到输入版本、文件位置、检查方法和证据，并标明已证实、待核实或未覆盖。

需要修订时，先完成范围确认，再串行整合。整合后的最终候选必须重新运行有关检查。甲在旧候选上的绿灯，不能证明后来改动后的版本。

这也是子任务结束与交付结束的区别：两个子任务都返回了，只说明各自工作到达终点；主任务还要整合、复验和交人审核。

## 6｜并行值不值得，要算到可接受结果

并行可能缩短两项独立工作的等待时间，但会增加委托、上下文重复、结果核对和返工的成本。

假如测试补全与风险审查各用 10 分钟，同时进行并不保证 10 分钟交付。还要加上拆分任务、解释输入、整合和最终复验的时间。一旦共享输入不断变化，协调成本可能比节省的时间更多。

Token 用量也通常要汇总各子任务与主任务，不能只看某一个窗口。记录真实可取得的用量；没有数据就写未取得，不用估算伪装实测。

比较串行与并行时，任务范围、起点与质量要求应尽量一致。一个方案少做了失败路径或省掉独立复验，就不能凭用时更短宣布更优。公平成本比较可以作为进阶挑战，不能取代本讲基本的真实协作证据。

选择并行的理由应是任务独立且有收益，不是“Agent 越多越先进”。有写入冲突就不强行并行，本身就是本讲要求的正确判断。

## 7｜这次交付分别留下什么

FlowERP 留下可创建、可校验的采购申请，并保持库存、预占、收货流水和其他申请的约定状态。

工作台留下可复用的协作方法：判断依赖、固定输入、定义委托、追溯结果、串行整合与同版复验。两个 Agent 的名字不是能力成果，这些可检查的组织动作才是。

你本人要留下首次并行判断、两份任务合同、真实执行记录、各自结果、主 Agent 的取舍、整合后的检查和人工结论。参考仓库的现成文件或讲师截图不能替代这些材料。

把同样的方法用于另一组任务时，应重新检查读写依赖，而不是直接复用“总开两个 Agent”的结论。若新任务会互相改变输入，就改为串行，说明理由。

## 8｜现在去实践手册做什么

打开[实践操作手册](实践操作手册.md)，按当前步骤推进：

1. 实践 1～2：准备项目，先判断两项工作会不会互相干扰。
2. 实践 3：理解真实采购实验，算清申请前后哪些状态不该变。
3. 实践 4：固定候选，为两个子任务写完整输入、输出与验收标准。
4. 实践 5：完成真实并行，保留可追溯的活动和结果。
5. 实践 6：串行整合，在最终版本上重新检查。
6. 实践 7：独立复验；按条件完成成本比较等挑战。

自测：只要写的文件不同就能并行吗？不能，还要看读写依赖和共享资源。两份报告都说完成，主任务就结束了吗？没有，还要整合复验。创建采购申请后实物库存增加了 7，是否正确？不正确，申请不等于收货。

更深入的同版红绿对照、委托细节和成本分析见[参考详解](参考详解.md)。本讲最重要的不是多启动几个 Agent，而是：**让独立工作真正独立，让每个结论有出处，让最终版本重新接受检查。**
