# 并行任务审查

当用户要求审查并行分工、子任务合同或主 Agent 汇总时使用。审查既有材料，不自动启动子代理，不用角色数量评价质量。

## 读取输入

找到目标 Spec、候选身份、接口约定、每项任务读写范围和接受标准。结果复核还需要原始子任务输出、实际 Diff、命令、报告与整合版本。缺失时说明具体缺口以及它阻止哪项判断，不编造版本和活动。

## 委派前检查

1. 检查共享写入及双向读写依赖，包括目录覆盖、路径别名、默认报告和临时数据。
2. 比较声明与任务实际需要读取的实现。声明检查器只检查输入，漏报读取不能成为允许并行的依据。
3. 检查版本、接口、单位、数据状态、数据库和端口等非文件依赖。
4. 区分上下文安排、工作区隔离和实际权限。提示词中的只读要求不等于已落实只读执行。
5. 给出每对任务可并行、需等待或材料不足的结论，解释具体依赖及最小调整。不得为完成并行形式而删除真实依赖。

## 返回后复核

逐条回查结论来源与版本。区分测试覆盖范围、已复现问题、待验证风险和未决需求；矛盾先比较输入与路径，再复现，不直接拼接摘要。检查整合后是否运行新增检查与统一验收。旧版本局部通过不能替最终候选作结论。

同一版本也可能产生局部通过与业务失败。先比较服务身份，再检查实际断言；例如申请字段检查不包含库存不变，不能用它否定提前入库的状态快照。保留两份原报告，定位被遗漏的业务承诺，整合后运行两类检查。可参考[同版实验记录](../../assets/latest/integration/index.json)，其顺序进程不是原生子代理活动。

判断原生并行时，核对实际子任务身份、父子关系、输入版本、活动和时间重叠；报告标题、角色名称、两个进程或提示词不能单独证明原生委派。缺活动记录时保留已验证的业务结论，同时明确尚未证明的协作行为。

保留异常和部分产物，明确需串行处理的事项。成本比较要有相同起点与范围，包含启动、汇总、返工和复验；用量缺失就写缺失，避免重复计数。

若结果主张工作台已经实现经验或流程复用，检查前一事项来源、经验边界与有效状态、后一事项召回及采用记录、明确流程版本，以及本次 Harness 和具名审核。登记资产或后续任务通过不能单独证明实际采用；复用失败应保留并推动修订或停用。建设计划不得当成已实现能力。

## 输出

用简短表格给出任务对、具体依赖、证据、安排建议；再列主结论的来源核对、未完成项与下一步。不要制造已经执行或已经提效的结论。

用 [审查反例](references/review-cases.md)检验真实响应，保留漏判与修订。参考答案不是模型已经通过的证明。
