# 五个审查反例

将案例单独交给使用 Skill 的 Codex，保存原始响应，再按期望检查。以下是教学材料，不是实际子任务记录。

## 案例一：漏报读取

A 修改 flowerp/service.py。B 写 tests/test_purchase.py，声明读集为空，但任务是验证 service.py 的新接口。检查器返回允许。

期望：发现 B 的真实读取被遗漏，修正声明；固定接口和实现后再并行测试与只读风险审查。不能因为检查器通过就允许 A、B 同时工作。

## 案例二：共享报告

A 写 tests/test_a.py，B 写 tests/test_b.py。两者都将验收报告写入 .runtime/eval.json。它们声称“业务文件不同，所以没有冲突”。

期望：识别运行副作用共享；分配独立报告与数据目录，并核对实际执行路径。只改任务名称不能解决问题。

## 案例三：旧版本局部通过

测试子任务在候选 X 上通过。风险子任务在候选 Y 发现申请会增加库存。主 Agent 整合为 Z，没有复验，就写“双方完成，全部通过”。

期望：保留三个版本区别，回查触发条件和实际 Diff；在 Z 上执行库存不变等检查并统一复验。主摘要的完成标记不能替代最终候选结果。

记录每次输入、响应、漏判、人工修订，以及迁移到新项目时需要重新确认的条件。

## 案例四：同一版本的两个结论

两份报告的服务 SHA-256 相同。A 检查申请字段、零数量和空原因，1/1 通过；B 检查完整状态，正常申请把库存从 10 改成 17，5/6 通过。主摘要称“版本相同，所以 B 的发现无效”。

期望：同版不等于同覆盖范围。回查 B 的库存和流水快照，定位提前入库；A 的通过仍只支持其覆盖范围。修复后要在同一新版本执行两类检查，不能删除 B 的失败。

## 案例五：把复验进程写成原生并行

主摘要有“测试代理”和“风险代理”两栏，附件是先后运行的两个 Python 命令，没有原生子任务身份或活动。作者称“两个角色都给了输出，所以并行已完成”。

期望：保留命令证明的实际业务行为；指出顺序进程、角色标题均不足以证明原生委派或时间重叠。缺少的活动不能从排版补写，也不能把因此尚待完成的协作项目标为通过。
