# L11 实现细节与扩展阅读

先读[辅导资料](辅导资料.md)，看懂本讲案例；准备实现或排查具体问题时，再按需查本文。这里保留控制规则、源码边界与实验入口，不要求先读完才能开始。

## 怎样判断两项工作能否并行

先看一个错误安排。甲修改采购接口，把 quantity 改名为 units；乙在另一份文件里编写测试，仍按 quantity 调用。没有同时写同一文件，测试却立刻过时。

![接口读写冲突与固定版本后的安全分工](assets/reading-figures-v2/key-example.png)

*读图：先看上半图的一方修改、一方依赖；再看下半图如何固定接口，把测试与只读审查分开。*

判断独立性要列两类范围：**读集 R** 是完成任务依赖的内容，**写集 W** 是任务会修改的内容。对于甲、乙两项任务，逐项问三次：

| 比较 | 若有交集，意味着什么 | 采购例子 |
|---|---|---|
| 甲写集与乙写集 | 同时修改同一处，结果可能互相覆盖 | 两人都改 service.py |
| 甲写集与乙读集 | 甲正在改变乙的依据 | 甲改接口，乙按接口写测试 |
| 乙写集与甲读集 | 乙正在改变甲的依据 | 乙改验收规则，甲按旧规则实现 |

两人只读同一份固定代码通常不冲突。用集合写，就是 `W甲∩W乙`、`W甲∩R乙`、`W乙∩R甲` 都应为空。这里的交集还要包含目录覆盖关系：允许甲修改整个 flowerp 目录，就包括乙正在读的 service.py。

文件之外也有资源。两项测试写同一个数据库或报告路径，仍可能覆盖结果；一个任务修改公共配置，也可能改变另一个任务的运行条件。因此，要同时检查代码、数据库、输出目录和公共配置，而不是只看两个输出文件名。

### 把错误安排改成可执行安排

先完成采购接口并固定候选 V1，再安排：

- 甲读取 V1 的实现和接口，只写指定采购测试文件，在自己的临时数据库中运行测试。
- 乙读取同一个 V1 的实现和业务规则，不读取甲尚在变动的测试，只把风险发现写到独立报告位置。
- 主 Agent 在两人返回前不改他们依赖的实现；两份结果回来后再串行整合。

“固定”不是在提示词里写 V1 就够了。应能定位到提交或文件指纹；若工作区还有未提交修改，需要记录这些修改，或用受控副本固定输入。即便两个任务各用一份副本，也要约定共同起点和接口，否则最后仍可能合不起来。


## 一份子任务委托，应该短到能读完，细到不用猜

本讲的 Subagent 是主 Agent 实际委托出去的独立执行子任务。它有自己的任务上下文和结果，不能用同一条回答里的“测试专家认为”“风险专家认为”来代替。

上下文独立也不自动带来文件隔离。本讲先按共享工作区的保守方式设计边界。以下是**委托示例**；路径以手册建立的实际候选为准，flowerp 路径指客户代码或记录过来源的课程候选，不是要求向本控制仓库添加业务包。

| 项目 | 甲：补充测试 | 乙：风险审查 |
|---|---|---|
| 输入 | 采购规则表、V1 身份、接口、已有测试 | 同一规则表与 V1 身份、服务及存储实现 |
| 目标 | 检查正常创建、非法输入拒绝和状态不被污染 | 找出能破坏采购规则的具体路径 |
| 读集 | `flowerp/service.py`、`flowerp/store.py`、现有测试 | `flowerp/service.py`、`flowerp/store.py` |
| 写集 | `tests/test_l11_purchase.py` 及甲专用输出目录 | 仅乙专用审查报告，不改项目代码 |
| 返回 | 测试 Diff、命令、实际结果、未覆盖内容 | 位置、触发条件、预期与实际或待验证假设 |
| 停止条件 | 需要改实现或接口时交回主 Agent | 证据不足则标待核实，不自行修改实现 |

两份委托都应附上实际工作目录、Python 入口和独立输出路径。主 Agent 还要明确本次完成条件：拿到结果、核实风险、整合到同一候选、复验，再交人接受。否则子任务很容易把“我这部分写完”理解为整个功能完成。

还可以在委托中明确一条响应规则：“发现问题先给最短复现，不扩大任务。”例如乙发现库存提前增加，应交回触发路径和数量变化，而不是顺手重构整个库存模块。这样发现问题的人可以贡献判断，修改仍由主任务统一安排。


## 并行节省多少，要算到最终可接受的结果

并行的主要收益，是把独立工作的等待时间重叠起来；它通常不减少总工作量，还会增加委托、重复上下文和整合成本。

用一个估算例子计算。补测试需要 12 分钟，风险审查 8 分钟，两种方案都需要 5 分钟整合与复验。并行还多花 3 分钟拆任务：

```text
串行：12 + 8 + 5 = 25 分钟
并行：3 + max(12, 8) + 5 = 20 分钟
预计节省：5 分钟
```

如果协调和冲突返工又花了 7 分钟，并行就变成 27 分钟，反而更慢。这里是规划估算，不是实测提效数据。

因此，小到几分钟就能完成、输入仍在频繁变化、或两个任务都必须修改同一核心方法的工作，通常先串行更容易控制。固定版本上的测试补全与只读审查，更适合尝试并行。

Token 成本要计入主 Agent、各子任务和返工。耗时减少并不代表用量减少。做挑战比较时保持相同起点、任务范围和质量要求，记录真实可取得的时间、用量和漏检情况；缺少数据就标未知，不把少做了一项检查算成效率提升。


## 先练依赖判断，再执行一次真实协作

在课程根目录的 PowerShell 中，用已有 `.venv` 运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 docs/courses/L11/examples/schedule_lab.py independent
.\.venv\Scripts\python.exe -X utf8 docs/courses/L11/examples/schedule_lab.py read-write
.\.venv\Scripts\python.exe -X utf8 docs/courses/L11/examples/schedule_lab.py undeclared-read
```

第一种声明测试与只读审查，预期 `observed` 为 allowed；第二种存在读写依赖，应为 rejected；第三种故意漏报测试对实现的读取，检查器会返回 allowed，但这恰好暴露了声明不完整的问题。

这三个结果说明 [agent/schedule.py](../../../agent/schedule.py) 能检查已声明的路径关系，不能自动发现所有隐含依赖，也不负责锁住文件。它没有启动任何 Agent。实际协作仍需按[实践操作手册](实践操作手册.md)第 4 步固定候选，第 5 步委托两个真实子任务，第 6 步串行整合，第 7 步复盘迁移。当前环境不支持真实委托时，将该项记为待完成。

**迁移练习**：甲修改库存导出字段，乙更新依赖这些字段的报表。即使文件不同，也应先完成并固定字段合同，再安排后续工作。若甲改为只读检查权限，乙只读检查金额计算，两者基于同版输入并各用独立输出，则可以尝试并行。说明改变了哪一条依赖，才算把方法迁移过去。
