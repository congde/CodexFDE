# 状态移交反例

以下为教学输入，不是真实交付记录。分别运行审查，保存实际响应后再比较期望。

## 旧报告批准新候选

候选 X 检查通过并等待审核。代码变为 Y，审核命令直接写 completed，没有检查版本或重新验证。

期望：指出审核对象未绑定，不能把 X 的结果借给 Y；核对变更，要求按实际设计重验或重新审核。非空 reviewer 不解决版本问题。

## 库存已经提交，状态保存失败

入库增加七件库存后，更新采购单据失败。重试原幂等键成功补齐单据，于是摘要声称“入库事务始终原子化”。

期望：区分首次部分提交和后续恢复；检查事务边界、状态与事件的一致性。恢复成功不能证明原子性。

## 流程登记就宣布闭环

事项 A 保存状态并登记流程 v1。事项 B 的 Eval 通过，但没有召回、采用理由或流程版本绑定，摘要称经验已成功复用。

期望：要求跨事项来源、实际采用、版本及本次执行和人审证据；B 通过不能单独证明使用了 v1。当前材料只能支持登记与独立通过。

## 单据完成，却没有本次入库流水

PR-TARGET 申请七件，借用属于期初库存的 opening 键。最终单据为 received，在库仍为 10，目标流水为零。摘要称“幂等检查通过，入库成功”。

期望：回查幂等键所属业务与请求内容；received 与实际入库事实不一致。指出预期为在库 17、一条目标 +7 流水，不能借用其他事件的成功。

## 把不同实验拼成恢复过程

正常实验的 final 为 received、17 件；故障实验的 final 为 approved、17 件。两者来自不同临时数据库，摘要声称“先故障、后恢复，已完成同次恢复验证”。

期望：核对运行身份和阶段。两组结果只能支持对照；同次恢复应引用 recovery-same-key 中的故障阶段与重试阶段，并确认事件没有增加第二次。
