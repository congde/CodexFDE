# L09｜把失败报告翻译成修复任务

**本讲只追问一件事：知道哪里失败以后，怎样让 Codex 接到一份能执行、不会乱改的任务？**

本文先讲清工作单怎么形成；操作见[实践操作手册](实践操作手册.md)，映射器细节与原实验记录见[参考详解](参考详解.md)。

## 1｜订单取消了，库存为什么还被占着

**修复任务既要写清目标变化，也要写清哪些状态必须保持不变。**

> **案例｜只取消 TARGET，不能误伤 OTHER**
>
> 仓库实物有 10 件，TARGET 预占 3 件，OTHER 预占 2 件，可用量为 5 件。
>
> 取消 TARGET 后，应只释放它的 3 件预占：OTHER 仍预占 2 件，实物仍为 10，可用量变为 8 件。
>
> 错误实现只改了取消状态，没有释放预占，可用量仍是 5 件。

此时直接对 Codex 说“库存有问题，帮我修一下”，范围太宽。它可能清空全部预占，让可用量变成 10。数字确实变大了，OTHER 的合法权益却被破坏了。

这里的数字用于教学推演，不是某次测试的原始输出。具体候选和输入以个人实践为准。L08 已有可信失败报告；本讲从这份报告出发，把“发现问题”变成“受控地安排一次修复”。

## 2｜报告说发生了什么，任务说接下来允许做什么

**失败报告提供事实，修复工作单还需要人的范围与授权判断。**

![从取消失败报告到范围明确的修复工作单](assets/reading-figures-v2/key-example.png)

*读图：从左侧失败事实，经范围确认，形成右侧可执行的修复工作单。*

TARGET 已取消，它的预占仍在。这说明结果不符合要求，但还没有证明是哪一行代码造成的。

他需要查入口、相关记录和候选版本，确认修改范围。

只释放 TARGET；保留 OTHER 和实物库存；写清候选、允许文件、复现和验收命令。这才是 Codex 可以接手的安排。

三类信息不要混成一句话：

- **事实**：实际观察到了什么，例如取消后预占仍存在。
- **原因假设**：为什么会这样，例如某分支跳过释放调用，需要进一步核实。
- **授权决定**：现在允许改什么，由谁确认，越界时怎么办。

“报告里提到了库存”不等于授权修改整个库存模块。原因可以暂时是假设，任务范围必须明确。

## 3｜先分诊：三个失败，不一定要派三个任务

**分诊**就是在修改之前，判断哪些失败相关、哪些独立、哪些证据不足。

一次运行可能同时出现取消后未释放、重复取消异常、异常路径残留三个失败。它们可能来自同一处缺陷，也可能是不同问题。先看复现条件、调用路径和状态，再决定合成一个有边界的任务，还是拆开处理。

不能按报告行数机械生成三个同时修改同一服务的任务；也不能未经调查就声称三个失败只有一个原因。

还要分清等级。阻断失败影响当前交付，需要进入修复判断；观察告警可以登记后续安排，不应被自动升级为当前阻断任务。没有有效报告、报告过期或检查未执行，则是信息不足，不是“没有失败、无需修复”。

本讲使用的参考取消入口与正式销售服务不是任意互换的。先确认报告来自哪个候选、哪个服务入口，按对应合同复现。别在另一套入口修出一个绿灯，拿来覆盖原来的失败。

## 4｜一份可执行工作单，要把这些空白补齐

**Repair Task** 就是修复工作单，不是把错误消息换一个标题。下面是教学示例，方括号必须替换成个人候选中的真实内容后才能执行。

> **案例｜一份有边界的修复工作单**
>
> **目标**：取消 TARGET 后释放它的预占；OTHER 的预占与实物库存不变。重复操作及异常路径满足原检查。
>
> **依据**：[原失败报告路径、生成时间、失败项名称]。
>
> **候选**：[实际工作区及版本或文件指纹]。不要在参考仓库或另一份副本上修改。
>
> **允许修改**：[调查后确认的具体实现文件]。检查文件和无关模块保持不变。
>
> **复现**：[工作目录与可复制的原失败命令]。
>
> **验收**：[原失败项复验命令]，以及[保留其他订单、库存及既有能力的回归命令]。
>
> **停止条件**：发现需要扩大范围、修改规则或缺少必要信息时，先报告，不自行授权。

为什么复现与验收都要写？复现让接手者看到同一个问题；验收让双方提前约定什么算改善。只有“修好库存”而没有命令和状态预期，接手者只能猜。

为什么要保留 OTHER？它是一个容易被误伤的对象。一个修复不仅要让目标订单变好，还要证明没有通过破坏无关订单来达成目标。

实际差异仍要事后检查。工作单里声明了范围，不代表执行已经遵守。

## 5｜映射器帮助整理，不替人作所有决定

**映射器**是把失败报告中的信息整理成修复任务的程序。例如提取阻断失败名称、证据位置、候选来源，再填入任务结构。

它可以减少漏项和抄写，但报告缺少的信息不会凭空出现。允许文件、真实复现命令和验收要求，必须来自已核实的项目情况与人的范围确认。

课程参考的基础映射函数能提供失败名称和证据等内容，不能因此声称完整工作单已经自动具备。个人练习要核对并补齐候选、具体范围、复现与验收命令等缺口。

这里有两次不同的授权：

第一次是**建设工作台能力**：请 Codex 协助完善映射器，目标是能生成合格工作单。

第二次是**修复客户产品**：使用这项能力，为取消订单形成任务，再让 Codex 按确认范围修 FlowERP。

两次允许修改的文件、输入和验收标准不同。不能因为你获准修改映射器，就顺便获得任意修改 ERP 的权限。

你负责确认事实、范围与目标，Codex 协助实现和受控修复，工作台保存输入输出，复验者用原检查回判，审核者决定接受或返工。这是工作台组织协作，不是报告自动变成无限修改授权。

## 6｜本讲只做一次真实修复，再认真回判

给 Codex 工作单后，让它完成一次受控修改，交回实际差异、修改说明、运行结果及未解决事项。它说“已修好”只是说明，不是验收证据。

回判时，至少对照：

1. 修复前候选上的原失败是否可以复现；
2. 修复后 TARGET 的预占是否正确释放；
3. OTHER、实物库存及相关历史记录是否保持约定状态；
4. 原检查与回归是否在新候选上实际执行；
5. 修改是否落在授权范围内。

本讲不要把“只释放 TARGET”的要求改成“所有预占清零”。也不要因为某项变绿就隐藏另外两项仍失败。

如果仍未通过，保留当前候选、剩余失败和下一步建议，交回人决定。L09 练的是一次完整交接，不要求无休止地自动重试；如何有条件地继续多轮，是 L10 的内容。

讲师参考补丁可以帮助理解原因，但不能替代你自己通过工作台组织的一次 Codex 执行。自己的工作单、实际差异、前后报告和人工结论，才是学习证据。

## 7｜读懂之后，下一步做什么

打开[实践操作手册](实践操作手册.md)：

| 阶段 | 你要完成的判断 | 应留下的材料 |
|---|---|---|
| 实践 1～2：准备与复现 | 报告来自哪个入口，哪一版候选？ | 原失败、业务状态、来源 |
| 实践 3～4：补齐映射器与工作单 | 哪些是事实，哪些要调查或授权？ | 自己补齐的任务及范围确认 |
| 实践 5：真实受控修复 | Codex 实际改了什么，原检查如何判断？ | 执行记录、差异、前后报告 |
| 实践 6：独立复验 | 他人能否按同一任务复现结论？ | 接受、返工或剩余风险 |

自测：取消后可用量从 5 变成 10，是否修好了？没有，OTHER 的 2 件也被释放了。三个失败是否一定派三个任务？不是，要先判断关联。观察告警是否自动变成阻断任务？不是。

若换成另一种失败，你仍能写清证据、候选、范围、复现、验收和停止条件，才说明学会了迁移。详细分诊和映射实现保留在[参考详解](参考详解.md)。本讲的核心是：**从“哪里不对”走到“允许怎样改、改后怎样判断”，中间不能省掉人的确认。**

## 本讲合同（与课程大纲一致）

- **核心内容**：从失败证据提取范围、复现命令、目标状态和禁止变更。
- **演示结果**：Harness 失败报告生成一个只针对失败项的修复任务。
- **课内增量**：实现失败报告到修复任务的映射器。
- **通过标准**：任务包含复现步骤和验收命令；不把观察级告警误判为阻断任务。
