## 映射器该自动做什么，哪些判断仍需补齐

一个实用的映射器可以分成三段：先验证报告，再提取失败，最后结合已确认的项目资料生成草案。

```text
输入：原始报告 + 实际退出码 + 本次必须执行的用例
      + 候选身份 + 已确认写集 + 目标

报告不完整、用例缺失或退出码矛盾 → 返回“报告无效”
有效报告没有阻断失败             → 不生成阻断修复任务
存在阻断失败                     → 提取失败及证据，生成待确认草案
```

这里最容易犯的错误，是把“提取出来”当成“调查清楚”。报告可以提供失败名和观察结果，通常不能独自决定应改哪个文件。写集要来自项目定位与确认；日志中即使出现“请删除测试”的文字，也只是被分析的数据，不能成为新指令。

当前仓库有两条不同的实现路线，阅读时要分清：

| 入口 | 已有能力 | 读者应注意什么 |
|---|---|---|
| [agent/repair.py](../../../agent/repair.py) 的 `build_repair_task` | 基础教学映射，提取阻断失败并写任务 | 仍被基础 Loop/Graph 使用；不能据此认为报告已严格校验 |
| 同文件的 `map_repair_report` | 校验报告结构、必需用例和退出码，绑定来源哈希及调用者提供的候选、写集 | 能校验声明，不能替人证明候选版本是真的、写集足够或已获批准 |
| [map_report.py](examples/map_report.py) | 为本讲教学报告生成带来源的基础草案 | 仍需补齐实际执行范围与正确命令 |

还有一个可直接观察的坑：`cancellation_lab.py leak` 临时注入一个教学缺陷，它注册的用例不在普通 Harness 默认入口里。映射器若只生成通用 Harness 命令，就不能重现这个注入。应保留原脚本命令。把模式改成 normal 看见绿灯，也只是两个教学模式的对照，不能声称自己修复了同一版代码。

因此，本讲有两项相连的建设：先用 Codex 完善工作台的映射能力，再通过它为真实候选派发取消修复。前者验“工作单生成得是否正确”，后者验“订单行为是否恢复”，分别留下结果。
