- 看不懂业务规则或判断理由：回到辅导资料的对应案例。

### 从真实转换器观察六种输入

[映射实验](examples/repair_mapping_lab.py)调用仓库真实的 `agent.repair.build_repair_task`，输入明确标记为教学合成报告，输出只写临时目录。它不运行 Codex，也不修改订单或库存。

在项目根目录激活本项目 `.venv` 后执行，将最后一个参数替换为表中的模式：

```bash
python -X utf8 docs/courses/L09/examples/repair_mapping_lab.py mixed
```

| 模式 | 输入条件 | 当前实现的实际观察 |
|---|---|---|
| mixed | 阻断失败、观察失败、阻断通过各一项 | 只选择阻断失败 |
| empty | 空对象，没有 results | 仍生成 scope 为空的任务 |
| missing-passed | 阻断项缺少 passed 字段 | 被当成失败选中 |
| string-false | passed 是字符串 "false" | 被排除，未当成布尔假值 |
| missing-evidence | 失败项缺少 evidence | KeyError，未生成输出 |
| instruction-text | evidence 含“删除测试”的教学攻击文本 | 原样复制到证据，禁止事项仍在 |

六种模式均已在参考实现上运行。脚本退出 0 表示观察符合表中预期，不表示这六种处理都是正确设计。尤其是空对象和错误字段类型，说明转换前还需要验证报告，不能由“选出的失败为零”推导“全部检查通过”。

### 为什么字符串 false 会漏掉

参考代码用 `not r.get("passed")` 判断失败。Python 中非空字符串具有真值，因此字符串 `"false"` 取反后为假；缺失字段则得到 None，取反后为真。两者都不是对布尔协议的严格验证。应先检查字段存在且类型符合报告约定，再决定业务分类。不能通过把所有输入转换成字符串比较来掩盖协议错误。

### 用例范围与文件权限是两个决定

生成任务中的 `scope` 是用例名称列表，回答“哪些失败需要处理”。它不包含可写文件，也不会阻止修改其他目录。执行前应调查相关实现，把修复目标映射到经确认的文件范围，再由执行器实际限制。即使任务包含“禁止删除 Eval”的文字，也仍要检查改动与检查入口是否被削弱。

日志中的指令性文本同样属于证据内容。实验只证明转换器复制了它，不能证明下游模型会忽略它。需要在后续任务构造与实际行为验证中检查：模型是否把证据当成授权、是否提出越界操作，以及执行器是否阻止越界。不能把输出中有禁止事项当成整条链路安全的证据。

### 把观察推进成自己的设计

先写下自己会接受和拒绝的输入，再查看源码。为缺字段、错误类型和正常阻断失败分别说明处理方式；为取消订单写出状态前后变化、复现步骤和验收命令。保留原报告来源与候选版本，让新修复结果可以回指这次失败。下一步需要用真实取消场景验证这份任务确实限定了所需修复，而不仅是字段齐全。
