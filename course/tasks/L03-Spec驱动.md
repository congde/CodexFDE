# L03｜把模糊需求变成可验收 Spec

- **核心内容**：目标与非目标、正常与错误路径、边界条件、可执行验收项、最小变更原则。
- **演示结果**：把“增加导出功能”拆成结构化 `FDE_SPEC.md`。
- **课内增量**：实现 Spec 模板与最小解析器，只负责生成和校验结构，不执行编码。
- **通过标准**：Spec 至少包含目标、非目标、约束、验收用例和来源；缺失必要字段时返回明确错误。
- **挑战任务**：从 Issue 或需求文档导入并保留来源追踪信息。

## 项目主线与评价证据

- **FlowERP 现场问题**：本讲由 FlowERP 真实交付暴露可重复工程问题，用于触发工作台能力验证。

- **ERP 产品增量**：完成“库存导出”的具名产品决策与可验收合同；产品代码暂不变化。
- **工作台增量**：形成 Spec 模板、结构解析和来源追踪，不执行编码。
- **双线因果**：ERP 需求的对象、字段、权限和失败行为存在歧义，迫使工作台先形成机器可检、人能签字的 Spec 能力。
- **ERP 验收证据**：库存导出的字段、排序、空集、权限、写失败和失败后不变状态全部进入已签字 Spec。
- **学生学习证据**：Spec、正反用例矩阵、解析失败和跨组反向复述记录。
- **形成性评价**：机器评价结构，人和同伴评价语义；两类评价均通过才达成。

## 付费行动课交付合同

本讲不是写需求文档。学员必须亲手交付：导出需求歧义账；具名来源与决策记录；结构化 `FDE_SPEC.md`；最小解析器及缺字段/错顺序/未知章节测试；正常、失败、边界和失败后不变状态矩阵；另一组只看 Spec 的盲验收与修订；迁移到第二需求的差异表。

只把 AI 初稿润色成完整文档、解析器只检查标题存在、或另一组仍需作者口头解释，均按未完成处理。

## 主次边界

- **FlowERP 产品状态**：库存导出从模糊愿望晋级为已签字合同，L04 必须消费该合同完成实现；
- **工作台主产物**是可复用 Spec Schema、解析器、来源追踪与评审协议；
- **迁移证明**使用补货或个人项目需求，但不能取代大纲规定的导出基础案例。

## 课前独立诊断

调用 AI 前提交且不得覆盖：

1. “增加导出功能”至少缺少哪五项产品决定？
2. 为什么“调用 `export_csv()` 成功”不是合格验收项？
3. 失败时除了错误消息，还应规定哪些状态不得变化？

## 混合式学习流程

| 场域 | 学习任务 | 必须留下的证据 |
|---|---|---|
| 线上 30 分钟 | 建立六段合同、Given–When–Then 和结构/语义双校验 | 歧义清单、合同定位表、反例预测 |
| 线下 70 分钟 | 谈判导出 Spec，做字段删除和语义反例实验，跨组反向复述 | 初稿、两类失败、Review Record、终稿 |
| 课后迁移 | 将同一方法迁移到补货或个人仓库需求 | 来源、决策人和目标仓库特有用例 |

## AI 使用与证据边界

- AI 可协助列问题、检查结构和生成反例，不得替业务责任人决定导出对象、权限、字段或口径；
- 本讲只读需求和实现 Spec 解析，不授权业务功能编码；若模型开始写实现应立即停止；
- 所有 AI 补充内容必须标记来源：原始需求、具名澄清、仓库事实或模型建议；模型建议不能伪装成已确认需求；
- 输入需求材料前先移除个人信息、客户数据、密钥和未经授权内容。

## 本讲主线

运营只说“增加库存导出”，仓库、财务和开发却对导出对象、可用量口径、字段、排序、格式、权限和失败行为给出不同解释。学员必须把争议收敛为一份只允许一种产品口径的 `FDE_SPEC.md`。本讲产出合同，不写实现；缺货补货作为课后迁移案例。

## 大纲与前沿硬校准

- **必须完成**：围绕“增加导出功能”生成并校验 Spec，保留来源、非目标、正反/边界用例与结构失败证据。
- **当前做法**：结构化输出只保证字段完整，人类通过跨组复述与反例签署业务语义。
- **退回条件**：开始写实现、让模型决定业务口径、用补货迁移案例替代大纲导出案例。见[校准矩阵](../../docs/courses/16讲主线与前沿校准矩阵.md)。

## 必须教会的知识

1. **六段合同**：来源、目标、非目标、约束、验收用例、完成定义各自解决什么问题。
2. **结果而非实现**：验收描述库存、订单、审批和证据结果，不把函数名当需求。
3. **正反用例**：Given-When-Then 同时覆盖正常、失败、取消、审批与幂等重放。
4. **失败后不变状态**：拒绝动作不仅要报错，还要明确哪些字段和事件不能变化。
5. **变更分层**：口径不清退回需求；实现违约进入缺陷；不要用代码修补需求歧义。

python -X utf8 -m workbench.cli course-contract --lesson 3
python -X utf8 -m workbench.cli course-spec --lesson 3
python -X utf8 -m workbench.cli spec .runtime/course/L03/FDE_SPEC.md
```

- 代码入口：`workbench/spec.py`；样例：`FDE_SPEC.md`。
- 正常路径：授权用户导出 `sku/on_hand/reserved/available`，可用量口径唯一且记录来源时间。
- 边界路径：空库存仍输出合法表头；SKU 含逗号、引号或中文时格式可解析；相同数据输出顺序稳定。
- 失败路径：不支持的格式、无效目标或写入失败返回明确错误，且不留下可误用的半成品。
- 结构失败实验：删除“非目标”章节，解析器必须指出缺失章节。
- 语义失败实验：写一条结构完整但允许部分预占的用例，由同伴评审退回。

python -X utf8 -m workbench.cli spec FDE_SPEC.md
```

## 独有产物与验收

提交 Spec、五场景用例矩阵和 Review Record。另一组只看验收项，必须能一致还原导出对象、字段、可用量口径、排序、空集和失败行为。解析通过只证明结构完整，不等于业务语义正确。

## 提交证据包与四级量规

证据包包含课前歧义判断、需求来源、待澄清清单、Spec 初稿、解析红灯、语义反例、具名决策、跨组复述、修订稿和迁移 Spec。

| 维度 | 优秀 | 达成 | 发展中 | 未达成 |
|---|---|---|---|---|
| 范围合同 | 目标、非目标、约束与来源互相一致且不绑实现 | 六段必要内容完整 | 有字段但边界含糊 | 缺必要章节或来源虚构 |
| 正反验收 | 正常、失败、边界和失败后不变状态形成闭环 | 至少一组正反路径可执行 | 只有 happy path 或错误难定位 | 用实现步骤冒充验收 |
| 语义协商 | 跨组复述一致，冲突有具名决定 | 核心口径唯一 | 仍需讲师口头补充 | 多种相反实现都能通过 |
| 学生修订 | 能区分结构缺陷与语义缺陷并实质修订 | 至少一项有证据修订 | 只让解析器变绿 | 直接提交 AI 生成 Spec |

硬门槛：编造需求来源、让 AI 代替业务签字、解析通过即宣称可验收，或在本讲越权编码，直接退回。

## 持续改进与迁移

记录字段缺失率、失败后不变状态覆盖率、跨组复述一致率和首次/修订量规变化，均须来自真实学生记录。迁移任务必须出现目标仓库独有对象与风险，不能替换标题后沿用 FlowERP 用例。
