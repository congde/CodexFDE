# L15｜生成交付摘要并采集真实反馈

- **核心内容**：文档和周报导出、运行反馈、失败样本回流，以及反馈与自动改代码之间的人工边界。
- **演示结果**：生成一次交付摘要并写入一条结构化反馈。
- **课内增量**：实现摘要导出和反馈记录，不在本节增加新的 Agent 编排。
- **通过标准**：摘要可追溯到任务和 Eval 报告；反馈包含来源、结论和下一步；原始反馈不会未经审核直接成为阻断 Eval。
- **挑战任务**：增加仓库问答 Bot 或脚手架生成器，作为独立扩展而非结业必做项。

## 项目主线与评价证据

- **FlowERP 现场问题**：本讲由 FlowERP 真实交付暴露可重复工程问题，用于触发工作台能力验证。

- **ERP 产品增量**：从 L14 真实页面走查中形成新版 Spec/Eval，并用独立 Task 交付一个受控改进。
- **工作台增量**：增加交付摘要导出和结构化反馈记录，不新增 Agent 编排。
- **双线因果**：页面反馈若只停在聊天中，ERP 不会进步；若直接改裁判又会失控，迫使工作台建立 Feedback/Evolution 治理后再交付改进。
- **ERP 验收证据**：源 Task 不能自证；新版 Spec/Eval 先红；独立候选 Task 完成 Diff、blocking 报告和具名验收后才记为 verified。
- **学生学习证据**：可追溯摘要、Feedback、来源/结论/下一步和人工边界说明。
- **形成性评价**：同伴随机抽取摘要结论回查 Task 与报告，不可追溯项退回。

## 付费行动课交付合同

本讲不是让模型写周报。学员必须亲手交付：摘要 Schema 与导出器；每项结论回指 Task/Eval 的随机抽查；原文/解释/决定分层存储；pending/accept/reject 与匿名/重复审核测试；原始反馈不可变证明；反馈直达 blocking 的失败注入；具名分诊和独立后序验证计划；脱敏/删除边界；迁移到第二类反馈源。

生成一篇漂亮摘要、覆盖用户原话、accepted 后自动改代码，或把模拟意见写成真实采用，均按未完成处理。

## 主次边界

- **FlowERP 产品状态**：源 Task 产生反馈，具名分诊后形成新版资产，再由不同候选 Task 完成一个可验收改进；
- **工作台主产物**是摘要、反馈状态机、来源追踪、人工晋级和持续改进数据入口；
- **迁移证明**要接入第二类反馈源并保持相同治理合同，不新增 Agent 编排。

## 课前独立诊断

调用 AI 生成摘要或分诊反馈前提交且不得覆盖：

1. “页面不好用”中哪些是用户原话，哪些是工程解释，哪些仍需复现？
2. accepted 反馈为什么不能自动成为 blocking Eval？
3. 源 Task 为什么不能为反馈改进是否有效自证？

## 混合式学习流程

| 场域 | 学习任务 | 必须留下的证据 |
|---|---|---|
| 线上 30 分钟 | 建立摘要回链、反馈三层记录、三态审核和人工晋级边界 | 首次分诊、状态责任图、错误晋级预测 |
| 线下 70 分钟 | 导出真实摘要、处理 accept/reject/pending、注入违规晋级并设计后序验证 | 回链、审核事件、失败证据和候选计划 |
| 课后验证 | 用独立后序 Task 验证 accepted 候选 | 新旧证据或明确负迁移结论 |

## AI 使用与证据边界

- AI 只能根据 Task、Harness 和事件生成候选摘要；每项结论必须回指 ID，不能编造测试、反馈或用户采用；
- 用户原话不可被模型润色后覆盖；工程解释可修订；审核决定必须由有权限的人具名作出；
- 原始反馈不得直接改代码、改变 blocking 等级或覆盖旧报告；只能进入待审 Spec/Eval/产品候选；
- 反馈最小化采集个人信息，支持去重、访问控制和删除请求，不把敏感原文复制给无授权模型。

## 本讲主线

L14 发现“列表已完成、详情待启动”的真实裂缝。学员保留用户原话，将事实、工程解释和审核决定分开，经复现与具名评审后进入下一版 Spec/Eval 候选，并用独立后序 Task 验证改进。本讲允许系统学习，不允许反馈自行改裁判。

## 大纲与前沿硬校准

- **必须完成**：导出可回指 Task/Eval 的摘要，记录包含来源、结论和下一步的结构化反馈并保留人工边界。
- **当前做法**：隐私最小化、三层记录与版本化 Eval Dataset 候选服务持续改进；主动选样不替代审核。
- **退回条件**：新增 Agent 编排、自动改代码、反馈直达 blocking、覆盖用户原话或虚构真实采用。见[校准矩阵](../../docs/courses/16讲主线与前沿校准矩阵.md)。

## 必须教会的知识

1. **三层记录**：反馈原文不可覆盖；工程解释可修订；审核决定必须具名并有理由。
2. **反馈状态机**：`pending_review → accepted/rejected` 与交付审核是两个对象、两套权限和两条事件链。
3. **分诊顺序**：先复现、去重、判断业务/工作台归属与风险，再决定进入 Spec、Eval 数据集或产品待办。
4. **受治理晋级**：accepted 不等于用户方案正确，更不允许自动降低或新增 blocking 规则。
5. **独立后序验证**：源 Task 不能为资产升级自证；新 Task 必须给出旧版本红/新版本绿或明确无效、负迁移结果。

## 课堂任务

```powershell
python -X utf8 -m workbench.cli course-contract --lesson 15
python -X utf8 -m workbench.cli course-spec --lesson 15 --eval-case feedback_rule_is_enforced
python -X utf8 -m workbench.cli course-submit --lesson 15 --execute-code --eval-case feedback_rule_is_enforced --session-baseline-ref refs/heads/l15-session-red
python -X utf8 -m workbench.cli course-eval --lesson 15 --case feedback_rule_is_enforced
python -X utf8 -m workbench.feedback add --task TASK-ID --source demo --conclusion "审批边界有效" --next "增加多仓 Eval"
python -X utf8 -m workbench.feedback review --id FB-ID --reviewer reviewer-a --decision accept --note "证据有效"
python -X utf8 -m workbench.feedback summary
```

- API：`GET/POST /api/v1/feedback`、`POST /api/v1/feedback/{id}/review`。
- 正常路径：pending 反馈复现后具名 accept，关联下一资产和独立验证 Task。
- 失败路径：无法复现则保留 pending 或具名 reject；重复审核、匿名审核失败。
- 不变状态：原始反馈、旧报告和原 Eval 不被覆盖或删除。

## 独有产物与验收

提交 Delivery Summary、至少一条 accepted、一条 rejected/待定反馈，以及 Feedback → Spec/Eval 候选 → 独立 Task → Harness 的证据链。用户抱怨直接改代码、反馈自动变 blocking、源 Task 自证或重复审核成功，均退回。

## 提交证据包与四级量规

证据包包含课前分诊、Delivery Summary、随机回链、反馈原文/解释/决定、三态样本、具名事件、错误晋级实验、隐私清单、候选资产和独立后序验证。

| 维度 | 优秀 | 达成 | 发展中 | 未达成 |
|---|---|---|---|---|
| 摘要真实性 | 每项结论回指 Task/Eval/事件并声明未验证范围 | 关键结论可追溯 | 个别结论只有叙述 | 编造通过、覆盖失败或无 ID |
| 反馈治理 | 原文、解释、决定分离，三态和权限完整 | 来源、结论、下一步齐全 | 理由或身份不完整 | 自动审核、重复决定或篡改原文 |
| 晋级与验证 | 候选经具名审核并由独立 Task 复验 | 不直达 blocking，后序计划清楚 | 只生成待办、未闭环 | 反馈直改代码/裁判或源 Task 自证 |
| 隐私与修订 | 最小化采集并由反例推动实质修订 | 无敏感泄露且有一项修订 | 隐私说明笼统 | 泄露个人/客户数据或伪造反馈 |

硬门槛：伪造用户反馈或审核人、原始反馈直达 blocking、源 Task 自证、覆盖原话或泄露敏感信息，直接退回。

## 持续改进与迁移

记录摘要不可追溯项、未经审核晋级数、反馈原文保真率、独立复验率、隐私过采集数和修订增值。满意度与反馈数量不能单独证明课程或产品有效。
